# 学籍业务学院化与转专业流程精简设计

## 1. 目标与范围

学籍具体业务下放给学院管理员，学籍管理员转为学院管理员治理者，同时保留全校转专业批次的创建、时间配置和启停。所有学院范围由服务端依据当前有效绑定解析，客户端提交的学院编号不能作为授权依据。

本次覆盖学生档案、学籍变更、资料审核、组织维护、培养方案、成绩、转专业和学院管理员治理。学生、教师、其他模块管理员和超级管理员的既有业务边界保持不变。

## 2. 角色职责

| 角色 | 允许 | 禁止 |
| --- | --- | --- |
| `STUDENT_ADMIN` | 查询、分配、调动和停用学院管理员；创建、修改、启停全校转专业批次 | 查询或修改具体学生；查看具体转专业申请、附件或审核记录；维护专业名额；参与审批和生效 |
| `COLLEGE_ADMIN` | 管理本学院学生、专业与班级、资料审核、培养方案和成绩；维护本学院转专业招生选项；处理与本学院有关的已提交申请 | 管理学院实体；访问其他学院学生；查看任何草稿；修改全校批次；治理学院管理员 |
| `STUDENT` | 既有本人学籍、成绩、培养方案和转专业自助能力 | 管理员能力 |
| 其他角色 | 保持既有能力 | 因管理员身份自动获得学籍能力 |

学院管理员只能维护自己学院下的专业与班级，不能新增、修改、启停学院。学生创建、批量导入、查询、修改、状态变更和资料审核均以学生当前所属学院为范围。培养方案以所属专业的学院为范围，成绩以目标学生当前学院为范围。

## 3. 学院管理员治理

复用 `tblStudentCollegeAdministrator` 和现有治理服务，补齐公共 DTO、查询、Handler、客户端服务及页面。交互参考超级管理员的模块管理员权限页，支持：

- 查看学院、有效管理员、账号状态和乐观锁版本；
- 将未分配的预设 `COLLEGE_ADMIN` 分配到学院；
- 将管理员从一个学院原子调动到另一个学院；
- 停用学院管理员资格；
- 禁止让任何启用学院失去最后一名有效管理员。

写操作使用既有请求去重、稳定锁顺序、单事务乐观锁和脱敏审计。分配变化成功后撤销受影响账号的全部会话，使新范围在重新登录后生效。只有 `STUDENT_ADMIN` 能调用这些治理命令。

## 4. 统一学院范围授权

服务端提供窄接口的学院范围授权组件，按请求实时读取当前有效绑定，不把学院范围视为会话快照。

- 学生目标：通过学生当前班级、专业解析学院。
- 专业、班级和培养方案目标：通过所属专业解析学院。
- 转专业申请：使用申请保存的原学院快照和招生选项的目标学院。
- 转专业附件：先解析所属申请，再执行同样的申请范围校验。

列表必须在仓储查询中带学院条件，不能读取全量数据后只依赖客户端过滤。详情与写命令在 Handler 边界校验；写服务在同一资源锁和事务内重新解析目标范围及业务状态，避免授权检查与修改之间发生变化。

不存在和无权访问对客户端统一返回 `COMMON_FORBIDDEN` 或既有安全错误，不泄露 SQL、数据库路径、内部异常或目标是否存在。

## 5. 学籍功能迁移

学院管理员客户端获得当前学籍管理员的具体业务页面，但页面数据和可选项均限制在本学院：

1. 学生查询、建档、批量导入和学籍变更；
2. 学籍资料审核；
3. 本学院专业与班级维护；
4. 本学院培养方案维护；
5. 本学院学生成绩管理；
6. 转专业招生选项与相关申请处理。

`STUDENT_ADMIN` 客户端只保留“学院管理员管理”和“转专业批次管理”。原先混合批次、招生选项和申请处理的转专业管理页拆分角色能力，避免仅靠隐藏按钮形成权限边界。

## 6. 转专业可见性与流程

管理员列表、详情、附件和审核记录一律排除 `DRAFT`。学生本人仍可保存和查看自己的草稿。

已提交申请只有在当前管理员学院等于申请原学院或目标学院时才可见：

- 原学院在 `SUBMITTED` 阶段执行转出审批；
- 目标学院在 `SOURCE_APPROVED` 阶段执行资格审核；
- 目标学院在 `QUALIFIED` 阶段录入或批量导入成绩；
- 目标学院在 `ASSESSED` 阶段直接终审，通过后进入 `PENDING_EFFECTIVE`；
- 目标学院执行转专业，成功后进入 `EFFECTIVE`，失败进入 `EXECUTION_FAILED` 并允许在相同范围内重试。

学籍管理员只维护全校批次，不得列出、读取或处理具体申请。转入学院只能在既有全校批次下维护目标学院属于自己的招生专业、名额和考核规则。

## 7. 删除拟录取阶段

删除 `PROPOSED` 状态、生成拟录取命令、排名结果协议、服务方法、Handler 路由和客户端入口。状态机改为 `ASSESSED -> PENDING_EFFECTIVE`，由目标学院管理员直接终审。

种子数据中原 `PROPOSED` 申请转换为 `ASSESSED`，表示等待目标学院终审；对应拟录取审核记录移除或改为不依赖拟录取语义的既有考核记录。发布数据库从更新后的 schema 与 seed 在临时路径重建、校验后替换，不能直接手工修改生产副本。

## 8. 客户端与协议

学籍管理员页面包含：

- 学院管理员治理页；
- 全校转专业批次页。

学院管理员页面包含完整学院内学籍工作台。客户端可以隐藏无权操作和限制选择项，但服务端仍独立执行角色、学院范围、状态和版本检查。

公共查询 DTO 只表达业务筛选，不接受可信的“当前管理员学院”。学院范围由认证主体在服务端解析。新增或调整的公共类型、构造器和方法均提供有效 JavaDoc。

## 9. 测试与交付

按测试驱动方式先增加失败测试，再做最小实现。至少覆盖：

- 任意管理员列表、详情和附件都不能看到 `DRAFT`；
- 学院管理员只能查询、创建和修改本学院学生及其资料、培养方案和成绩；
- 跨学院直接 ID 访问和伪造筛选均被拒绝；
- 学籍管理员不能访问具体学生或具体申请，但能治理学院管理员和维护全局批次；
- 学院管理员只能维护本学院招生选项，并按原学院/目标学院阶段处理申请；
- `ASSESSED` 可由目标学院终审并执行，拟录取协议和入口不存在；
- 管理员调动后旧学院权限失效、新学院权限生效，最后管理员保护仍有效；
- 数据库生成器、种子快照和发布 Access 数据库状态一致；
- JDK 21 下相关聚焦测试与 `mvn test` 通过，或明确区分本分支已有的无关基线失败。

当前 `nineloong` 基线在 JDK 21 下服务端测试通过；客户端已有 5 个失败和 1 个错误，集中在主框架、组织管理、登录布局和登出 UI 测试。本次修改不得新增无关失败，并应修复因本次页面职责调整而受影响的断言。
