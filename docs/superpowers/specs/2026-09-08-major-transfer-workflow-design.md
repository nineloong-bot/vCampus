# 本科生转专业业务流程设计

## 1. 依据与目标

本设计参考项目根目录中的《东南大学关于做好 2025-2026 学年本科生转专业工作的通知》（校机教〔2026〕2号），将转专业实现为独立于普通学籍资料修改的业务流程。

系统目标是覆盖申请批次、开放专业、资格审核、考核成绩、拟录取、终审公示、延迟生效和学籍异动留痕。普通学籍资料申请仍只负责个人资料和就读方式，不允许借其直接修改学院、专业或班级。

## 2. 第一版范围

第一版只支持全日制本科生，每名学生在一个批次中只能申请一个目标专业，不进行专业间调剂。支持普通转专业和学困生转专业两类申请。

第一版包含：

- 管理员创建批次并配置报名、审核、公示和生效时间；
- 管理员为批次配置开放专业、接收名额、面试名额、适用年级、考核规则和申请要求；
- 学生查看资格检查结果、暂存申请、维护附件、提交和有限条件下撤回；
- 管理员依次完成原学院审核、转入学院资格审核、成绩录入、拟录取生成、教务终审和正式执行；
- 学生查看申请状态、审核意见、考核成绩和最终结果；
- 生效时原子更新学院、专业和班级，并写入不可变的学籍异动记录。

第一版不自动修改成绩、不删除原专业课程、不自动完成课程替代认定。正式转入后只生成“课程认定待处理”状态，供后续模块扩展。

## 3. 现实规则与系统边界

系统能够自动判断的规则包括：

- 当前时间是否处于批次报名期；
- 学生是否为本科生、是否在籍在校、当前学籍状态是否正常；
- 学生年级是否属于目标专业允许范围；
- 目标专业是否启用、是否与当前专业不同；
- 是否已有进行中的申请；
- 是否存在已经生效的成功转专业记录；
- 目标专业名额和考核成绩是否满足配置规则；
- 学困生申请是否上传至少一份证明材料。

当前系统没有学术不端、纪律处分、特殊招生类别、学籍预警和完整成绩系统的权威数据源。这些条件不得伪装成自动校验，而是在原学院审核页面以实名勾选项确认：学籍审核合格、无禁止性违纪、招生类别允许转专业。后续接入相关模块后，可替换为自动读取且保留人工复核。

## 4. 状态机

主流程状态如下：

```text
DRAFT
  -> SUBMITTED
  -> SOURCE_APPROVED
  -> QUALIFIED
  -> ASSESSED
  -> PROPOSED
  -> PENDING_EFFECTIVE
  -> EFFECTIVE
```

终止状态包括：

- `REJECTED`：任一审核阶段不通过或考核未达到录取条件；
- `CANCELLED`：进入原学院审核以后，由管理员依据书面原因取消；
- `EXECUTION_FAILED`：正式执行时因班级失效、并发修改等原因失败，修复后可以重试。

学生只可在 `SUBMITTED` 且原学院尚未作出审核决定时自行撤回。撤回把同一申请恢复为 `DRAFT`，保留目标专业、理由和附件，同时追加一条不可变的“学生撤回”轨迹。进入 `SOURCE_APPROVED` 后只能由管理员取消。

## 5. 审核、考核与录取

原学院审核必须记录三个判断：学籍审核合格、无禁止性违纪、招生类别允许转专业。三项全部为“是”才可通过，并记录审核人、时间和意见。

转入学院资格审核确认申请人满足该专业的附加要求。通过后进入考核阶段。管理员录入笔试和面试成绩，系统按照专业配置的权重计算最终成绩；权重之和必须为 100，未启用的考核项权重为 0。

拟录取生成规则：

1. 只处理资格审核通过、成绩完整且达到合格线的申请；
2. 按最终成绩从高到低排序；
3. 按接收名额确定截止分数，截止分数同分者全部进入拟录取，因此实际人数可以超过名额；
4. 学困生申请使用独立配置，可设置为不受普通名额限制；
5. 未进入拟录取的申请转为 `REJECTED`，原因固定记录为“未达到本专业拟录取排名”；
6. 不把申请调剂到其他专业。

教务终审通过后进入 `PENDING_EFFECTIVE`，并记录公示时间。终审通过不直接修改正式学籍。

## 6. 正式生效

管理员在批次指定日期后为每名待生效学生选择目标专业下的启用班级，并执行转专业。服务端必须在同一资源锁和数据库事务中：

1. 重新读取申请、学生、目标专业和目标班级；
2. 确认申请仍为 `PENDING_EFFECTIVE`，班级属于目标专业，学生正式学籍版本未被其他操作修改；
3. 保存转专业前后的学院、专业、班级和年级快照；
4. 更新学生的专业与班级；
5. 写入 `tblStudentChange` 的 `MAJOR_TRANSFER` 记录；
6. 写入执行记录并把申请改为 `EFFECTIVE`；
7. 初始化课程认定状态为 `PENDING`。

任何一步失败均整体回滚。`EXECUTION_FAILED` 只记录失败原因，不留下部分更新结果。

## 7. 权限

- `STUDENT`：只能查看开放批次和本人申请，只能维护、提交或撤回本人申请；
- `TEACHER`：第一版没有转专业管理入口，也不能读取申请及审核详情；
- `ADMIN`：配置批次和专业、执行各阶段审核、录入成绩、生成拟录取名单、分配班级并正式生效。

当前角色模型没有学院级数据范围，因此第一版由管理员完成各阶段操作，但每次操作仍保存阶段、操作者和时间。以后增加学院管理员时，可以在不改变状态机和数据结构的前提下增加组织范围校验。

## 8. 客户端交互

学生学籍模块增加“学籍档案”和“转专业申请”两个页签。转专业页依次显示：

- 当前批次及报名时间；
- 逐条资格检查结果；
- 当前学院、专业、班级只读快照；
- 目标学院和专业级联选择；
- 申请类型、申请理由和材料；
- 暂存、提交或撤回按钮；
- 提交后的阶段时间线、审核意见、成绩和最终结果。

管理员学籍模块增加“转专业管理”页签，内部提供“批次与专业”“申请审核”“考核录取”“生效办理”四个视图。所有耗时请求异步执行，不阻塞 Swing EDT；关闭页面或刷新后忽略过期响应。

## 9. 附件规则

每份申请最多上传 3 个附件，单个不超过 5 MiB，仅允许 PDF、JPEG 和 PNG。服务端根据文件头验证实际类型，不信任扩展名；文件名只作为展示信息。学困生申请至少需要一个附件，普通申请附件可选。

## 10. 并发、幂等与审计

- 所有写命令使用现有请求去重器；
- 申请状态变更携带 `expectedVersion`，过期版本返回稳定的并发冲突错误；
- 学生申请操作使用 `STUDENT:<studentId>` 锁；
- 生成拟录取名单使用 `TRANSFER_OPTION:<optionId>` 锁；
- 正式执行按固定顺序获取 `TRANSFER_APPLICATION:<applicationId>` 和 `STUDENT:<studentId>` 锁；
- 审核记录只追加不覆盖；撤回后重新提交也保留此前审核轨迹；
- 正式学籍变更继续使用 `tblStudentChange` 作为统一审计入口。

## 11. 发布要求

完成后运行全量 Maven 测试，重建测试 Access 数据库，替换 `vCampus-release` 中对应的客户端 JAR、服务端 JAR、数据库和使用说明，并重新生成发布压缩包。发布数据库包含一个开放批次、两个目标专业以及覆盖草稿、待审核、待生效状态的演示数据。
