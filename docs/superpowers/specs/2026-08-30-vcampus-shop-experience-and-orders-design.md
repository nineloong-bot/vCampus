# vCampus Shop 浏览体验与买家订单设计

## 1. 目标与边界

本阶段在 `SHOP` 分支完善已登录买家的商城体验：接管共享外壳已有的“校园商城”入口，统一 Shop 内部导航与工具栏，提供统一搜索和分类首页，扩充可验证的 Demo 商品数据，并增加“我的”与本人已支付订单。

实现只修改 `common/shop`、`server/shop`、`client/shop`、Shop 数据库、Demo、测试和说明文档。Foundation、User、Socket、Router、事务框架与公共网络接口只作为依赖使用。

## 2. 单一商城入口与 Shop 根容器

共享外壳已经注册 `shop` 页面和 `navigation.shop` 按钮。`ShopUiInstaller` 不再创建 `shop.navigation`，也不再把各 Shop 页面注册到共享 `PageNavigator`。安装器在 EDT 上按稳定组件名找到 `page.shop`，清空占位内容后嵌入一个由 Shop 管理的根容器；根容器使用自己的 `CardLayout` 承载 Shop 页面。

安装器按稳定组件名找到现有 `navigation.shop` 并添加 Shop 进入监听器。共享监听器仍负责显示顶层 `shop` 卡片；Shop 监听器首次进入时打开默认首页，之后只恢复 `ShopNavigator.current()` 对应的现有页面和视图状态。安装过程若找不到唯一入口或唯一占位页，应立即抛出可诊断异常，避免静默追加重复入口。

## 3. 路由、历史与视图状态

`ShopNavigator` 仍是唯一 Shop 历史所有者。打开新路由前，协调器先从当前页面捕获视图状态，再把带状态的当前路由压入有界历史栈。列表路由保存：

- 首页：`HomeProductQuery`、页码和滚动位置。
- 搜索：`ProductSearchQuery`、是否已完成首次搜索、筛选区是否展开和滚动位置。
- 店铺：`ShopProductQuery`、页码和滚动位置。

返回列表时先恢复表单和查询，异步结果渲染完成后再恢复滚动条位置。商品详情、店铺、购物车、“我的”、搜索结果、结算与支付结果均是 Shop 路由。打开购物车和“我的”使用普通 `open`，因此返回会精确回到进入前的页面。

支付成功进入结果页时使用 `replaceCurrent` 替换结算路由，不把已完成的结算步骤留作可返回目标。“继续购物”和“查看已支付订单”使用 `reset` 建立新的根路由，避免再次进入支付或结算流程。

## 4. 公共工具栏与购物车数量

Shop 根容器顶部固定显示：

```text
← 返回   页面标题/位置                         我的   购物车（数量）
```

工具栏由当前路由驱动标题、返回可用状态和按钮显隐。首页无历史时返回禁用；搜索页只隐藏购物车，“我的”和返回保持可见。购物车数量是所有购物车行项目数量之和，而不是行数。

Shop 内部提供一个可观察的 `CartCountModel`。进入商城时异步读取购物车初始化数量；商品加购、购物车修改/删除、结算与成功支付都用最新 `CartView` 或明确的空购物车更新该模型。工具栏只观察模型，不自行复制购物车业务逻辑。

## 5. 首页与统一搜索

首页顺序固定为统一搜索、四个分类、猜你喜欢。四个分类为“文具”“图书”“生活用品”“药品”；点击后打开已完成首次搜索且带分类条件的搜索结果。猜你喜欢始终以 `SALES_DESC` 请求商品，并显示商品名、店铺名、分类、起售价和销量。

首页和搜索页的主搜索区域都只有一个关键词输入框和一个“搜索”按钮，提示语为“搜索商品、店铺或相关信息……”。搜索页在首次成功提交前不显示“筛选”按钮；首次完成搜索后显示该按钮，展开区包含四大分类、最低价、最高价与排序方式。

服务端关键词同时匹配商品名称、店铺名称、商品分类、商品描述和 SKU 名称。SKU 匹配使用相关 `EXISTS` 子查询，商品价格仍由外层可售 SKU 聚合计算，因此多规格命中只返回一个商品。分类筛选使用四大分类的精确值。

## 6. Demo 商品数据

Demo 初始化器生成四个有效店铺和恰好 100 件有效商品：文具店 10 件、书店 30 件、生活超市 55 件、药店 5 件。商品 ID、名称和 SKU ID 固定且唯一；描述包含可用于统一搜索的语义词；价格、库存和销量确定性生成，并为部分商品生成两个规格以验证 SKU 搜索和去重。

初始化数据使用稳定的分类商品清单：文具 10 个明确品名、图书 30 个明确书名、药品 5 个明确品名；生活用品由 11 个明确品类与 5 个明确规格组合成 55 个唯一品名。销量使用全局唯一的递减/错列数值，使首页排序可断言；每类数据跨越至少两页以验证分页的类目，还提供价格范围和规格关键词。

Demo 另写入当前买家一笔 `PAID` 订单及明细、另一买家一笔 `PAID` 订单和一笔非 `PAID` 订单，用于验证本人隔离、状态过滤、支付时间倒序和明细展开。

## 7. “我的”与已支付订单

`ShopUiInstaller` 从登录组合层接收登录成功后的 `UserView`，传递给 Shop 协调器和“我的”页面。页面只读显示用户编号、登录标识、角色和账户状态，不修改 User 模块。

Common 新增不可变、可序列化的已支付订单 DTO：订单编号、店铺、商品与 SKU 明细、数量、成交单价、行金额、订单总金额、支付时间和支付状态。列表响应使用一个拥有防御性副本的包装 DTO。

客户端发送 `SHOP_GET_PAID_ORDERS` 与 `EmptyRequest.INSTANCE`。Handler 先解析当前会话，并只把解析后的 `actor.userId()` 传给 `BuyerOrderService`。仓储查询通过 `tblOrderGroup.buyerUserId` 限定买家，通过订单/支付状态限定 `PAID`，按 `paidAt DESC, orderId` 排序，再读取对应明细。请求体中不接受买家编号，因此客户端无法查询他人订单。

“我的”异步加载订单，默认折叠明细；每张订单可展开商品、SKU、数量、单价和金额。会话过期沿用现有 Shop 会话退出回调。

## 8. 验证策略

所有行为采用红—绿—重构顺序。Common 验证 DTO 序列化与防御性复制；Server 验证统一搜索字段、SKU 去重、销量排序、订单身份隔离与状态排序；Client 验证单入口、内部历史、工具栏规则、表单/滚动状态和“我的”；Demo 验证精确商品分配、固定数据和真实 Socket 链路。

最终执行 Shop Common、Server、Client 测试，Demo 数据和端到端测试，PowerShell 启动脚本行为测试及 AST 语法检查，并运行 `git diff --check`。未跟踪的 `logs/` 始终排除在提交与清理范围外。
