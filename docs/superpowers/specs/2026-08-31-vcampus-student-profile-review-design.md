# vCampus 学籍资料编辑、审核与 PDF 导出设计

## 1. 目标与范围

本次改动把现有学籍模块接入 `ServerMain` 的正式运行时，并将学生资料编辑从“直接修改正式表”升级为“暂存、提交、管理员审核后生效”的闭环。

学生端按参考界面显示“个人基本信息”和“学籍信息”两张规格化信息表。每个分区的小标题右侧放置编辑入口；个人信息允许编辑个人属性和联系方式，学籍信息只有“就读方式”允许编辑。页面底部左侧导出正式档案 PDF，右侧提交当前草稿审核。

管理员端新增资料审核页签。管理员可查看正式值与申请值差异、通过申请或填写原因后驳回。只有通过操作会修改正式档案。

## 2. 权限和字段边界

学生只能读取和编辑自己的资料工作区，客户端请求不得指定其他学生编号。管理员审核需要 `STUDENT_WRITE` 权限。

以下校方权威字段始终只读：一卡通号、学号、学生类别、在籍状态、在校状态、学籍状态、校区、当前年级、院系、专业、班级、培养层次、培养方式、学制、就读学位、就读学历、预计毕业日期、毕业日期、学生来源、学习形式、辅导员姓名及其他由学校维护的学籍字段。

学生可编辑个人基本信息中的个人属性和联系方式，以及学籍信息中的 `attendanceMode`（就读方式）。就读方式使用固定枚举：`DAY_STUDENT`（走读）、`RESIDENT`（住校）、`LODGING`（借宿）、`OTHER`（其他）。

## 3. 正式档案与申请模型

`tblStudent` 是管理员已批准的正式档案，补齐参考界面需要的个人资料、学籍展示字段和就读方式。现有组织、编号、状态和版本约束继续有效。

新增 `tblStudentProfileApplication` 保存完整的可编辑字段快照及审核元数据：

- `applicationId`、`studentId`；
- 个人基本信息和联系方式快照；
- `attendanceMode`；
- `baseStudentVersion`、`applicationVersion`；
- `status`：`DRAFT`、`PENDING`、`APPROVED`、`REJECTED`；
- `submittedAt`、`reviewerUserId`、`reviewedAt`、`reviewComment`；
- `createdAt`、`updatedAt`。

每名学生最多存在一条未结束申请，即状态为 `DRAFT` 或 `PENDING` 的申请。Access 不依赖条件唯一索引；服务端在 `STUDENT:<studentId>` 资源锁和同一事务中查询并强制该约束。

草稿反复保存时覆盖同一条 `DRAFT` 记录。提交后状态转为 `PENDING` 并锁定，直到管理员通过或驳回。关闭申请后学生才可创建下一份草稿。

## 4. 事务与并发

保存草稿只更新申请表，不修改 `tblStudent`。首次保存记录当前正式档案的 `rowVersion` 为 `baseStudentVersion`。

提交操作校验申请仍为 `DRAFT`、存在实际改动且正式档案版本未变化，然后原子转为 `PENDING`。

管理员通过操作在 `STUDENT:<studentId>` 锁和单一数据库事务中完成：

1. 重新读取 `PENDING` 申请和正式档案；
2. 校验 `baseStudentVersion` 仍等于正式档案 `rowVersion`；
3. 将申请快照写入正式档案并增加正式版本；
4. 将申请标记为 `APPROVED`，写入审核人和审核时间；
5. 向 `tblStudentChange` 写入不可变更的 `PROFILE_CHANGE` 记录。

任何一步失败均回滚。管理员驳回只将申请标记为 `REJECTED`，保存非空原因、审核人和审核时间，不修改正式档案。

所有保存、提交、通过和驳回命令经持久化请求去重器保证幂等。正式版本冲突返回明确错误，客户端要求刷新，不静默覆盖。

## 5. 公共 DTO 与消息命令

公共模块新增正式档案、草稿和审核 DTO，包括：

- `StudentProfileData`：页面完整正式信息；
- `StudentProfileApplicationView`：申请快照、状态和审核元数据；
- `StudentProfileWorkspace`：正式档案与当前开放/最近关闭申请；
- `SaveStudentPersonalDraftCommand`；
- `SaveStudentAttendanceDraftCommand`；
- `SubmitStudentProfileCommand`；
- `StudentProfileReviewQuery`；
- `ReviewStudentProfileCommand`。

新增消息命令：

| 命令 | 用途 | 权限 |
|---|---|---|
| `STUDENT_PROFILE_GET_WORKSPACE` | 读取本人正式档案和申请状态 | 学生本人 |
| `STUDENT_PROFILE_SAVE_PERSONAL_DRAFT` | 暂存个人信息 | 学生本人 |
| `STUDENT_PROFILE_SAVE_ATTENDANCE_DRAFT` | 暂存就读方式 | 学生本人 |
| `STUDENT_PROFILE_SUBMIT` | 提交唯一草稿 | 学生本人 |
| `STUDENT_PROFILE_EXPORT_PDF` | 导出正式资料 PDF | 学生本人 |
| `STUDENT_PROFILE_REVIEW_LIST` | 查询待审申请 | 管理员 |
| `STUDENT_PROFILE_REVIEW_GET` | 读取申请差异详情 | 管理员 |
| `STUDENT_PROFILE_APPROVE` | 通过申请 | 管理员 |
| `STUDENT_PROFILE_REJECT` | 驳回并记录原因 | 管理员 |

服务端根据会话用户定位学生，不接受学生端传入目标 `studentId`。审核命令从会话读取真实审核人，不信任客户端操作者字段。

## 6. 学生端界面

`MyStudentProfilePanel` 改为两个表格式分区。宽窗口按三组“字段名＋值”横排，窄窗口自适应为单列并纵向滚动。

“个人基本信息　编辑”入口打开分区编辑状态。保护字段继续只读，可编辑字段变为文本框、日期或受控下拉框。区内提供“保存暂存”和“取消编辑”。

“学籍信息　编辑”入口打开学籍分区编辑状态，只有就读方式变为下拉框，固定显示“走读、住校、借宿、其他”；其他字段仍只读。

页面显示申请状态：无申请、草稿未提交、审核中、已驳回。驳回状态同时显示管理员原因。审核中禁用两个编辑入口。

底部操作区左侧为“基本信息导出”，右侧为“提交审核”。无草稿或无实际改动时提交按钮禁用；提交前二次确认，成功后立即切换为审核中。

## 7. 管理员审核界面

管理员学籍模块增加“资料审核”页签。列表默认只显示 `PENDING` 申请，并展示学生姓名、学号、提交时间和当前状态。

详情按个人基本信息和学籍信息分区并排展示“正式值 → 申请值”，只高亮发生变化的字段。底部提供“通过”和“驳回”：通过需要二次确认，驳回必须填写原因。操作成功后刷新列表并移除已处理申请。

## 8. PDF 导出

PDF 必须由服务端使用正式档案生成，草稿、待审核值和驳回值不得进入文件。响应传输 PDF 字节和建议文件名，客户端使用保存文件选择器写入用户选择的位置。

PDF 使用 A4 纵向规格并嵌入可分发的中文字体，包含学校/系统标识、“学生基本信息表”标题、生成时间、学号、一卡通号、个人基本信息表、学籍信息表、页码和“数据以系统正式档案为准”说明。

默认文件名为 `学籍基本信息_<学号>_<姓名>.pdf`。本地取消保存不视为错误；生成或写入失败不得改变档案和申请状态。

## 9. 错误处理

- 草稿或正式版本冲突：提示“资料已发生变化，请刷新后重新编辑”；
- 审核中再次保存或提交：提示“申请正在审核，暂不可编辑”；
- 无实际改动提交：返回校验错误并保持草稿；
- 管理员审核时正式档案已变化：拒绝审核并要求重新查看差异；
- 驳回原因为空：服务端拒绝；
- PDF 生成或本地保存失败：显示可恢复错误，不影响业务状态；
- 网络断开：保留当前界面值，禁用写操作并允许重试读取。

## 10. 测试与发布

采用测试先行覆盖：

- Access 仓储映射和单一开放申请约束；
- 草稿不修改正式表、提交锁定、通过原子生效、驳回不改正式数据；
- 权限、会话目标绑定、幂等、版本冲突和审核记录；
- `ServerMain` 运行时实际注册全部学籍命令；
- 学生端分区编辑、就读方式选项、申请状态和按钮启用规则；
- 管理员待审列表、差异展示、通过和必填驳回原因；
- PDF 文本完整性及渲染后的中文、分页、裁切和表格对齐；
- 全量 Maven `verify` 和 shaded JAR 打包。

发布时重建测试数据库，将最新客户端/服务端 JAR、数据库及发生变化的配置、脚本和使用说明替换到 `vCampus-release`，保留目录结构并清理临时验证文件。
