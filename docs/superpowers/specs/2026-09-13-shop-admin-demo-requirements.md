# 校园商城与虚拟余额系统开发项目书

版本：2026-09-14 统一基线。适用范围：买家、店主、管理员、独立虚拟余额模块及账户显示对接。

本文整合用户逐项确认的最终规则，作为正式开发依据。网页 Demo 的认可代表交互方向通过，不代表 Java 服务端、Access 持久化或并发实现已经完成。技术建议和尚未确定的业务边界单独列在末尾，不将原型临时行为自动当成需求。

相关文档：后端准备计划见 `../plans/2026-09-14-shop-backend-readiness.md`；页面确认记录见仓库 `prototypes/shop-buyer/PAGE-REVIEW.md`。

正式实现与运行说明见 [商城正式接入与验收](../../shop/commerce-delivery.md)。该文档记录本次 Java/Socket/Access 实现范围、兼容边界及验证方式；本项目书仍作为业务规则基线。

## 1. 范围与模块职责

- JDK 21、Swing 客户端、现有 Socket 消息协议、Microsoft Access（UCanAccess）；数据库源为 `vcampus-database/schema` 和 `seed`。
- 当前用户负责商城及虚拟余额系统。账户模块负责调用余额查询接口并展示；充值、扣款、退款、结算与流水归余额模块负责。
- 全部为校园虚拟货币：平台内充值、消费、退款和经营收入，不涉及真实支付、兑换、提现。
- 配送仅演示订单状态，不采集收货地址、电话或物流单号，不需要读取学籍联系电话。卖家只看到买家昵称；真实姓名、电话、学号等不进入卖家响应。
- 商品图片提交到 GitHub 并随客户端发布，Access 保存图片编号。举报和证照均使用文字资料，审核标注“模拟审核”。
- 管理员负责审核和监督；商家维护自己的商品。管理员有针对商品的警告及紧急下架权限，不代商家编辑商品或价格。

## 3. 店主、图片与商品

### 3.1 开店与工作台

开店填写店名、主体名称、营业执照编号，确认平台经营规则；提交成功、待审核、通过、驳回各状态可查看。驳回展示原因，允许修改后申请。审核通过后“申请开店”变为“我的店铺”。工作台栏目为店铺概览、商品管理、订单管理、经营资质、店铺设置。

### 3.2 商品创建与编辑

- 页面分基本信息、准入类目、规格与库存。每行一个规格，填写名称、价格、库存；初始一行“标准款”，可改名；恰好一个默认规格（SEL-008）。
- 手动草稿只要求非空商品名称，其他信息可后补；已填写价格须大于0且最多两位小数，库存须非负整数。
- 上架检查名称、介绍、有效预置图片、类目资质与完整规格；错误逐项提示。库存0可上架展示缺货，但不可购买。
- 在售商品可直接修改资料、价格和库存，保存成功后生效。历史订单保留商品、规格、店铺和价格快照。
- 商品图片从预置图库选择，服务端校验图片编号；至少一张有效图片才能上架。单独及批量为草稿选择图片，不自动上架（SEL-005～007）。目前 Demo 提供六张封面，批量选图交互尚不完整。

### 3.3 准入与独立限制（ADM-002、009、011～017）

店铺开放经营，不限定只能卖一类商品。普通白名单类目完成主体模拟审核即可经营；专项许可类目须文字资质申请（类型、编号、有效期）并审核通过；禁售类目不提供选择且后端拒绝。

资质到期只限制依赖该资质且失去授权的商品，不停止整店。续期审核通过后，自动恢复仅因资质到期下架的商品；商家主动下架、紧急下架、店铺停业和软删除等限制仍有效。

课程使用明确标注的模拟类目规则，不把讨论中列举的具体商品及许可证对应关系视为已核实的法规清单。

### 3.4 商品下架与删除

店主主动下架后买家不能搜索、浏览或购买，购物车对应商品移除；重新上架不自动加回。已付款订单继续履约。

删除采用不可恢复软删除：在售时禁用并提示“商品在售，请先下架后再删除”。草稿、店主下架、资质到期下架可删除，但关联任何待付款、待发货、待收货、退款处理中订单时阻止，并提示“该商品尚有未完成订单，无法删除，请等待订单全部完结。”

删除后普通商品列表与搜索不展示；保留历史订单、明细、退款记录、审计、SKU记录及库存流水。商家和运维都不能恢复上架；运维只可查询历史。已付款订单完整性不因软删除丢失，也不放宽删除前的未完成订单检查。

## 4. Excel 导入（SEL-001～004）

Excel 由客户端本地解析，只传结构化数据与原始行号给服务器；后端权威校验，预览不写业务数据库。仅允许普通白名单商品，持有效资质的专项许可商品也必须手动创建。

| 模板列 | 校验 |
| --- | --- |
| 商品分组编号 | 本文件内分组，每行一个规格；不是数据库商品ID。 |
| 商品名称、商品介绍、准入类目 | 必填，同组一致；类目必须为普通白名单。 |
| 图片编号 | 可整组留空；非空须存在于预置清单，同组一致。 |
| 规格名称、价格、库存 | 名称必填；价格大于0且最多两位小数；库存为非负整数。 |
| 默认规格 | 是/否；同组恰好一个“是”。 |

1. 预览展示全部数据、原始行号、错误原因及汇总：规格行数、商品组数、有效组数、失败或受影响行数。
2. 组内任一行失败，整组不导入；分别标识直接错误行和同组受影响行。
3. 同名已存在仅提示“店内已有同名商品，请检查”，允许新建草稿，不覆盖已有商品。
4. 取消不创建商品，仍可下载错误报告；确认时只导入完整有效组，全部生成草稿。
5. 确认时服务端重验当前状态与内容，不信任前端的有效标志；同一次确认重复提交不得重复创建。

## 5. 订单、库存和付款

### 5.1 状态及退款

| 当前状态 | 操作 | 结果 |
| --- | --- | --- |
| 待付款 | 付款成功 | 待发货 |
| 待付款 | 买家取消、30分钟超时、整店停业或全部商品失效 | 已取消，释放仍占用库存 |
| 待发货 | 店主发货 | 待收货 |
| 待收货 | 买家确认收货 | 已完成，结算经营收入 |
| 待发货 | 买家申请整单退款 | 退款审核中，暂停发货 |
| 退款审核中 | 店主驳回并说明原因 | 待发货，买家可查看原因 |
| 退款审核中 | 店主同意且退款执行成功 | 已退款，关闭订单 |

发货后和完成后不允许退款；按单个店铺订单整单退款，不支持部分商品/数量退款，不影响同次结算的其他店铺订单。无自动收货。

买家栏目：全部、待付款、待发货、待收货、已完成、退款/已关闭。最后一项包括退款审核中、已退款、已取消，并显示具体状态。

### 5.2 拆单与库存

- 多店统一结算，按店生成独立订单；可统一付款或按店铺订单付款。付款按本次选择的整笔金额处理，余额不足时无部分扣款。
- 创建订单时占用库存；取消/超时释放未消费占用，付款成功转为正式扣减。退款成功恢复相应库存并记录流水。
- 待付款期限为创建后30分钟；查看或懒校验不延长。服务器主动处理超时，重启后补处理，不依赖买家访问。
- 所有库存与资金改变必须可重试且不可重复执行，多个买家同时购买不得超卖。

### 5.3 商品下架的懒校验

商品下架时不遍历所有待付款订单。用户进入订单页或去支付时，后端校验相应订单；扣款提交时再校验，防止检查后状态变化。

| 结果 | 处理 |
| --- | --- |
| 全部正常 | 正常支付。 |
| 部分失效 | 标记失效项、释放这些行占用；有效项继续锁库存，按订单快照价格重算金额；失效记录留存但不参与结算。 |
| 全部失效 | 取消订单，释放全部剩余占用。 |

部分失效提示：“订单内部分商品已下架，付款仅购买剩余有效商品”。全部失效提示：“订单商品均已下架，订单已取消”。支付前展示调整结果。重复校验不重复释放，已失效条目不自动恢复购买。

整店停业单独执行取消该店待付款订单的规则，并清理购物车；已付款继续履约。单商品下架的懒校验策略不应被误写为整店停业时完全不处理订单。

## 6. 虚拟余额

| 项目 | 已确认规则 |
| --- | --- |
| 账号余额 | 每个账号一个可用余额，共用充值、购物和经营收入。 |
| 充值 | 虚拟充值，快捷100/200/500；自定义大于0、最多两位小数，单次≤1000。 |
| 扣款 | 余额不足整笔失败、不扣任何金额，订单仍待付款，提供去充值后重试入口。 |
| 待结算 | 买家付款后进入对应订单待结算，商家暂不可消费。 |
| 结算 | 买家确认收货后，待结算转入该店主账号可用余额。 |
| 退款 | 未发货退款同意并执行成功后，从订单待结算退回买家。 |
| 明细 | 充值、购物扣款、退款到账、经营收入；时间、收支金额、变动后余额、关联订单。充值无需订单。 |

扣款、待结算、订单状态在同一原子边界内变化；结算和退款互斥。响应丢失或重复点击不能重复增减资金。账户模块只查余额，不能直接改余额表。

## 7. 举报、管理员与整改

### 7.1 举报

商品详情、店铺页面提供举报入口。原因单选：涉嫌禁售商品、经营资质问题、商品信息虚假或误导、店铺违规经营、其他问题。文字说明必填。我的举报展示待处理/已处理及管理员结果；卖家不可获得举报人身份。

### 7.2 管理员列表工作区（ADM-001、003、004、008、010）

顶层两个入口：店铺管理、商品管理。以列表和详情为主；开店/资质审核、举报、恢复申请、历史记录放入相应入口内。商品列表列出名称、所属店铺、状态、举报情况。管理员不编辑商品经营信息。

- 警告：填写原因，可关联问题商品与整改说明，不改变营业或上架状态。
- 整店暂停营业：填写原因，店铺仍可访问并显示停业标志，但所有商品不可浏览/搜索/购买；购物车清理且恢复后不加回；待付款订单取消，已付款继续履约。
- 商品紧急下架：填写原因、明确商品、通知商家；其他商品不受影响。此限制独立，不可由商家或资质续期绕过。
- 举报处理选择警告、商品紧急下架、暂停店铺或未发现违规；说明必填，举报结果与处置和审计保持一致，不重复执行。
- 开店和资质审核可通过、驳回；驳回原因必须可查看。使用文字材料及模拟审核标识。

### 7.3 恢复

整店停业后商家提交整改说明申请恢复，管理员通过才允许营业；驳回填写原因并继续停业。没有到期自动恢复。

紧急下架商品由商家修改后申请复核；通过只解除紧急限制，不自动上架，商家自行上架时仍检查店铺、资质、商品完整性及删除状态。

处理记录保存操作人、对象、动作、原因、时间、前后状态及关联举报/申请；商家通知暴露必要处置内容，不暴露举报人身份。

## 8. 编号与验收追踪

原 ADM-001～004、008～017、BUY-001～016、SEL-001～008 在相应章节保留映射；ADM-005～007 继续保留空号。新增流程使用本章场景号对齐后端测试。

| 场景 | 必须验证 |

| AC-11 | 紧急下架→整改→复核通过仍不自动上架；停业/过期独立限制继续生效。 |
| AC-12 | 整店停业清理购物车并取消待付款，已付款可履约；恢复需申请审核。 |
| AC-13 | 非店主不可改店铺商品，非管理员不可审核，卖家响应没有买家敏感资料或举报人ID。 |
| AC-14 | 资质到期仅限对应商品；续期自动恢复不覆盖主动下架、停业、紧急限制、软删除。 |

## 9. Demo 与正式开发的区别

已确认页面覆盖买家、商品与Excel、订单、虚拟余额、商品生命周期、管理员列表及整改。Demo 使用内存、模拟账号、时间推进按钮和角色预览；不能把按钮隐藏、JavaScript锁定值或本地余额当作后端鉴权及持久化证明。

仍需正式实现：独立余额服务、持久化资金与库存流水、完整订单/退款状态、商品与资质独立限制、批量导入会话、后台任务、跨模块查询接口、并发与恢复测试、Swing页面对接。批量选图、完整资质到期/续期任务以及店铺设置细节不能仅凭现有 Demo 视为已完成。

## 10. 开发前逐项收敛的边界

以下只影响对应任务，不阻止余额基础、数据库审查及协议骨架准备：

1. 买家昵称的正式来源、更新规则和无昵称时的显示值；不得直接以真实姓名/学号代替。
2. 正式模拟类目清单、多资质/子类目覆盖、资质撤销（区别于到期）的行为；先明确映射，不自行扩大经营授权。
3. 资质失效对已下单未付款商品的细则；实现前补充确认，不能直接假定与所有主动下架事件完全相同。
4. 库存编辑字段显示总库存还是可售库存、已被订单引用规格的删改规则；持久化必须保留稳定SKU身份，不能使用数组下标。
5. 商品被下架后在首次懒校验前又重新上架，是否按当前状态允许继续支付；跨下架期间的事件语义需明确。
6. 支付/退款失败的用户重试反馈、充值余额总上限、导入批次大小/会话期限；作为对应技术设计项补全，不冒称用户已确认。
7. 店铺设置可编辑字段、审核要求、资质恢复时商品信息不完整的具体提示，集中在后续小范围设计中处理。

技术原则：限制叠加，失效原因可追溯；金额采用精确十进制或整数分；跨模块走窄接口；持久化写入与幂等依据同事务。数据库迁移必须在临时 Access 副本验证，不能直接替换组长的运行库。
