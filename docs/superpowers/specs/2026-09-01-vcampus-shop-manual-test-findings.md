**记录日期：** 2026-09-01
**测试对象：** `SHOP` 分支最终四角色 Demo
**文档性质：** 手工测试问题记录与分类，不作为具体整改设计或实施方案
**当前范围：** `SHOP-TEST-001` 至 `SHOP-TEST-010`，共 10 组、14 个具体问题

## 1. 测试背景与约束

本轮测试由用户使用最终 Demo 进行人工操作，覆盖商城首页、搜索、购物车、确认订单、开店申请、管理员工作区和卖家工作区。本文保存已经确认的问题现象、复现路径、用户期望与验收关注点，供后续统一策划整改方案。

本阶段只收集和整理问题，不在本文中确定具体技术实现。商品图片继续使用简单占位，不因本轮界面问题引入图片资源或数据库升级。

## 3. 按领域归类

### 3.1 页面布局与商品展示

#### SHOP-TEST-001：首次进入商城时页面高度异常

**影响范围：** 所有账号首次登录后进入商城首页。
**严重程度：** 高。

**现象：**

- 第一次进入商城首页时，商品内容区域异常偏长。
- 页面下半部分存在大量没有实际内容的空白。
- 垂直滚动范围明显超过当前商品内容所需高度。
- 点击“下一页”，再点击“上一页”回到第一页后，布局恢复正常。

**复现步骤：**

1. 启动客户端并登录任意固定账号。
2. 第一次进入商城首页。
3. 观察商品区域高度、页面底部空白和垂直滚动条。
4. 点击“下一页”。
5. 点击“上一页”返回第一页。
6. 对比首次进入与翻页后的页面高度。

**期望结果：**

- 第一次加载完成后立即按照窗口宽度和商品数量计算正确的网格高度。
- 页面底部不出现无意义的大面积空白。
- 首次加载与翻页返回后的页面布局一致。

**验收关注点：**

- 所有账号首次进入均正常。
- 不同窗口尺寸下均不会出现异常滚动范围。
- 异步商品加载完成后，布局和滚动容器能够正确刷新。

**人工复测结果（2026-09-01，最终便携 Demo）：** 未通过。用户补充的连续截图证明首次进入第一页时视口确实从顶部开始，问题不是初始滚动位置偏移。第一页的滚动内容总高度被异常放大：商品列表结束后仍有大段空白，分页按钮被推到异常内容区域的最底部。进入第二页后内容高度和分页位置恢复正常。`SHOP-TEST-001` 维持“未解决”状态。

**五张对比截图所证明的现象：**

1. 登录成功后第一页从搜索栏和分类栏正常开始，但右侧滚动条滑块异常短，说明滚动模型中的总内容高度远大于实际可见商品所需高度。
2. 滚动到第一页最后一批商品时仍看不到分页按钮，并且滚动条尚未到达中部。
3. 继续滚到底部后，中间出现大面积无商品内容的空白，分页按钮位于异常长页面的最底端。
4. 点击下一页后，第二页顶部布局正常，滚动条滑块明显变长，说明总内容高度已经按当前商品行数重新计算。
5. 第二页底部紧接最后一行商品显示分页按钮，不再存在第一页那种超长空白。

**此前采取的方案：**

- 引入 `WrappingGridLayout`，按照可用宽度计算列数，并按照商品数量、列数和卡片首选高度计算网格首选高度。
- 将商品卡固定为约 `200` 像素宽，在页面变宽时增加列数。
- 商品图片异步完成并重新渲染卡片后，对卡片槽位、商品网格及其父容器调用 `revalidate()`/`repaint()`。
- `ShopHomePanel` 在数据加载完成后通过下一次 EDT 调度恢复路由中保存的滚动位置。
- 自动化测试验证了窄宽度下网格首选高度包含多行，并验证翻页及从详情返回时保存/恢复滚动值。

**此前方案未能发现问题的原因：**

- `ProductGridPanelTest` 只在脱离真实窗口的面板上手动设置尺寸，断言首选高度“大于 500”，没有断言精确行数、精确内容高度、首行位置或多余空白。
- 测试没有把首页放入真实可见的 `JScrollPane` 和应用外壳后执行首次加载，因此没有覆盖首次布局、异步刷新、视口尺寸和滚动模型之间的组合行为。
- 分页测试直接操纵滚动条模型来验证状态保存，未验证初次进入时滚动值最终必须保持为 `0`。
- 自动化验收结论把局部布局计算通过误写成了问题已基本解决，但文档当时仍注明“待人工复测首屏高度”；本次截图证明该人工验收没有通过。

**当前根因定位：** 已确认是第一页首次布局时商品网格首选高度被过度计算并被外层滚动内容采用，而不是滚动位置恢复错误，也不是服务端返回了更多商品。当前 `WrappingGridLayout` 在网格尚未获得真实宽度（`parent.getWidth() == 0`）时，把可用宽度回退为单张卡片宽度，因此首次首选尺寸计算会暂时按“单列”计算全部商品行数；真实窗口随后可以按多列摆放卡片，但外层 `BoxLayout`/`JScrollPane` 已采用过大的首次高度。翻到第二页时网格已有真实宽度，首选高度重新按多列计算，所以恢复正常。新增回归测试已经复现并锁定这一计算错误。

**自动化整改证据（2026-09-01）：** 新增首次布局回归测试，在父容器已有 `900px` 宽、商品网格自身宽度仍为 `0` 时加载 20 个固定高度商品。修改前测试实际得到单列高度 `3828`，与问题现象一致；预期 4 列、5 行高度为 `948`。最小实现改为在网格尚无宽度时使用首个已有真实宽度的父容器计算列数。相关目录测试 23 项通过，完整 Maven 回归 Common 19、Server 191、Client 172，共 382 项，0 失败、0 错误、0 跳过。当前结论为“自动化已修复，待最终便携 Demo 人工复测”，尚不能仅凭自动化标记为已解决。

#### SHOP-TEST-003.1：商品卡底部按钮重复展示商品信息

**影响范围：** 所有同时展示多个商品的页面。
**严重程度：** 中高。

**现象：**

- 商品卡已经展示商品名、价格等信息。
- 卡片底部又显示包含商品名和价格的按钮，信息重复。
- 商品名称较长时，按钮文字被截断，增加视觉拥挤和理解成本。

**用户期望：**

- 移除卡片底部重复展示商品信息的购买按钮。
- 点击商品图片、名称或描述组成的商品区域即可进入商品详情。
- 该交互应覆盖首页、搜索结果、分类结果、店铺商品和其他多商品展示页面。

**验收关注点：**

- 商品信息不再重复展示。
- 整个商品卡片具有明确、统一的可点击反馈。
- 鼠标与键盘操作均可进入商品详情。
- 调整后不影响分页、滚动和商品网格排列。

#### SHOP-TEST-003.2：首页与搜索结果的店铺信息展示策略

**影响范围：** 商城首页和商品搜索结果。
**严重程度：** 中。

**用户期望：**

- 首页同时展示多个商品时，不显示店铺名称，降低首页信息密度。
- 用户执行搜索后，搜索结果应显示店铺名称，帮助区分商品来源。
- 通过首页分类入口进入的结果属于搜索结果，应按搜索页面规则显示店铺名称。

**验收关注点：**

- 首页商品卡不显示店铺名称。
- 搜索结果稳定显示店铺名称。
- 两类页面可以复用基础商品卡，但展示规则必须能够按使用场景切换。

### 3.2 搜索与筛选

#### SHOP-TEST-006：“筛选”与“应用筛选”语义混淆

**影响范围：** 从首页搜索后进入的商品搜索页面。
**严重程度：** 中。

**现象：**

- 搜索栏附近显示“筛选”按钮。
- 展开筛选区域后又显示“应用筛选”按钮。
- 两个按钮名称相近，但一个用于展开或收起区域，另一个用于执行筛选，容易被理解为重复功能。

**用户期望：**

- 展开或收起筛选区域与执行筛选应有清晰、不同的文字和视觉层级。
- 用户无需猜测两个按钮的差异。

**方案阶段需要确认：**

- 筛选条件是修改后自动应用，还是保留单独确认操作。
- 分类、价格和排序是否采用一致的刷新规则。
- 展开按钮与执行按钮最终采用的文字。

### 3.3 购物车与确认订单

#### SHOP-TEST-007.1：缺少商品小计与订单总价

**影响范围：** 购物车和确认订单页面。
**严重程度：** 严重。

**现象：**

- 购物车只能看到商品单价和数量，看不到单项小计与购物车总价。
- 确认订单页面只能看到商品及单价，看不到数量、小计和最终订单总价。
- 用户在提交订单前无法清楚确认最终支付金额。

**期望结果：**

每件商品至少展示：

- 商品名称与 SKU。
- 单价。
- 数量。
- 小计，即单价乘以数量。

页面汇总区域至少展示：

- 商品总数量。
- 订单总价。
- 进入结算或提交订单操作。

**验收关注点：**

- 修改数量后，单项小计、商品总数量和总价立即同步。
- 删除商品后，汇总金额立即同步。
- 确认订单金额与购物车及服务端计算结果一致。
- 最终金额在“提交订单”附近清晰可见。

#### SHOP-TEST-007.2：商品不应横向连续排列

**影响范围：** 购物车和确认订单页面。
**严重程度：** 高。

**现象：**

- 多件商品横向排列在同一行。
- 商品名称、价格、数量输入和按钮相互挤压。
- 商品较多或名称较长时难以阅读和操作。

**用户期望：**

- 商品采用纵向列表排列。
- 每件商品独占一行或一张横向信息卡。
- 多件商品从上到下排列，内容超过页面时使用纵向滚动。
- 购物车和确认订单保持一致的信息层级。

#### SHOP-TEST-007.3：购物车商品区域应进入商品详情

**关联问题：** `SHOP-TEST-003.1`。
**影响范围：** 购物车商品列表。
**严重程度：** 中。

**用户期望：**

- 点击购物车中的商品图片、商品名称或描述区域，进入对应商品详情。
- 数量输入框、“更新”和“删除”等操作保留自身行为，不触发详情跳转。
- 从商品详情返回后恢复购物车页面及原有滚动位置。
- 查看详情不能导致购物车数量或其他状态丢失。

### 3.4 开店申请

#### SHOP-TEST-002A：完整填写后不能直接提交审核

**影响角色：** 申请开店的学生和教师。
**严重程度：** 高。

**现象：**

- 用户完整填写申请内容并点击“提交审核”时，系统要求先保存草稿。
- 用户必须额外执行一次“保存草稿”，才能提交审核。

**用户期望：**

- 页面当前填写内容通过校验后，可以直接提交审核。
- 提交操作使用页面中的最新内容，不强制依赖已持久化的草稿。
- “保存草稿”继续作为暂时不提交时的独立功能。
- 被驳回申请修改完整后也应允许直接重新提交。

**验收关注点：**

- 新申请和被驳回后重提均支持直接提交。
- 校验失败时保留当前内容，并明确提示有问题的字段。
- 成功提交后状态正确变为待审核。

#### SHOP-TEST-002B：未保存内容离开时没有确认提示

**影响范围：** 开店申请页面的返回及商城工具栏导航。
**严重程度：** 高。

**现象：**

- 用户填写或修改申请内容后，如果没有保存草稿，离开申请区域时没有明确的数据保护提示。

**用户期望：**

当存在未保存修改并准备离开时，应提示用户选择：

- 保存草稿并离开。
- 不保存并离开。
- 取消离开并继续填写。

**验收关注点：**

- 返回、“我的”“购物车”及其他会离开申请页面的入口均遵守同一规则。
- 已保存且之后没有修改时不弹出提示。
- 选择取消后，所有页面内容保持不变。
- 选择保存后，草稿可在再次进入时恢复。

### 3.5 管理员审核

#### SHOP-TEST-004：审核列表未区分未处理与已处理

**影响角色：** 管理员。
**严重程度：** 中高。

**现象：**

- `PENDING`、`APPROVED` 和 `REJECTED` 申请混在同一列表中。
- 管理员无法快速区分需要操作的申请与历史记录。
- 当前列表没有清晰展示排序所依据的时间。

**用户期望：**

- 未处理区域只展示 `PENDING` 申请。
- 已处理区域展示 `APPROVED` 和 `REJECTED` 申请。
- 未处理和已处理都要按照时间排序。
- 管理员打开审核界面后能够优先定位未处理申请。

**验收关注点：**

- 处理完成的申请立即从未处理区域移动到已处理区域。
- 未处理列表展示提交时间，已处理列表展示审核时间。
- 时间相同时使用稳定的次级排序，刷新后顺序不跳动。
- 已处理记录保留审核状态、审核意见和时间。

**方案阶段需要确认：** 时间采用升序还是降序展示。

### 3.6 卖家商品与 SKU 管理

#### SHOP-TEST-005：卖家工作区暴露内部技术字段

**影响角色：** 获批店长；管理员商品管理界面存在相似表现。
**严重程度：** 高。

**现象：**

- 新增 SKU 时要求店长手工填写 `SKU ID`。
- 店长需要理解 ID 格式并自行保证唯一性，显著增加操作难度和出错概率。
- 卖家工作区直接展示较多数据库或接口层字段，整体操作方式偏技术化。

**用户明确要求：**

- SKU ID 不应由店长填写，应由系统自动生成。
- 卖家工作区界面需要整体整改。
- 本阶段先记录问题，后续根据全部问题统一策划方案。

**后续策划范围：**

- 区分商品和 SKU 的业务字段与内部技术字段。
- 梳理店长创建商品、增加 SKU、修改库存和上下架的最短操作路径。
- 评估 `SKU ID`、版本号、布尔状态和封面 URL 的展示方式。
- 明确管理员与店长商品编辑界面的复用边界。
- 图片继续使用占位策略，不升级数据库。

### 3.7 导航与返回逻辑

#### SHOP-TEST-008：我的与购物车污染返回历史

**影响范围：** 商城首页、我的、购物车之间的导航。
**严重程度：** 高。

**现象：**

- 进入首页后反复点击“我的”和“购物车”，每次切换都会继续追加返回历史。
- 点击“返回”时，会在“我的”和“购物车”之间不断切换。
- 用户需要多次返回，并且最终可能无法回到首页。
- 重复点击当前页面也可能增加无意义的历史记录。

**用户期望的导航关系：**

- “我的”和“购物车”属于同一层级的商城工具页。

### SHOP-TEST-009：默认端口被旧服务端占用时，Demo 启动失败且诊断信息不足

**影响范围：** 最终便携 Demo 的服务端启动与人工验收准备。
**严重程度：** 高。

**复现步骤：**

1. 本机已有一个 Java 服务端监听 TCP `8888`。
2. 双击最终发布包中的 `启动服务端.bat`。
3. 启动脚本打印端口 `8888` 后，服务端抛出 `java.net.BindException: Address already in use: bind`。
4. 脚本仅提示检查端口和日志，随后进入暂停或终止批处理提示。

**本次测试证据：**

- Windows `netstat -ano` 显示 PID `37480` 同时监听 `0.0.0.0:8888` 和 `[::]:8888`。
- PID `37480` 为仍在运行的 `java.exe`，启动时间为 `2026-08-31 12:09:50`。
- `8888` 不在 Windows TCP 排除端口范围内。
- 当前 `启动服务端.bat` 只执行一次 `ShopAuthDemoServerMain`，不存在脚本自身重复拉起服务端的情况。
- 因此，本次失败的直接原因是旧 Java 服务端占用统一端口，不是新发布包内服务端在启动过程中自行重复绑定。

**体验问题：**

- 当前报错不能直接告诉测试者“已有服务端正在运行”以及占用进程信息。
- 测试者无法判断现有监听者是可直接复用的 vCampus 服务端、此前遗留的 Shop Demo，还是其他程序。
- 直接要求结束 Java 进程存在误停其他模块服务端的风险；在未确认进程身份前不应自动终止。
- 端口冲突会完全阻断最终 Demo 的后续人工验收。

**期望与后续策划范围：**

- 启动前检查 `8888` 是否已经处于监听状态。
- 端口被占用时给出明确、可操作的中文提示，至少说明端口、占用 PID 和建议的确认步骤。
- 区分“已有兼容的 vCampus 服务端可复用”和“其他进程冲突”两种情况，不能默认结束占用进程。
- 保留显式端口覆盖能力，用于隔离测试；最终联合验收仍以统一端口 `8888` 为基线。
- 增加启动脚本的端口占用自动化测试，并人工验证冲突提示在 Windows 终端中清晰可读。

**人工复测结果（2026-09-01）：** 用户确认该问题已经解决，端口冲突不再阻塞本轮 Demo 测试。上述启动诊断增强可作为后续体验改进，不再作为当前发布验收阻塞项。

### SHOP-TEST-010：卖家商品管理页缩小后左侧商品列表被严重压缩

**影响范围：** 店主开店后的卖家工作区 → 商品管理。
**严重程度：** 高。

**对比场景：**

1. 全屏显示卖家商品管理页时，左侧商品列表具有足够宽度，商品名、状态、SKU 数、最低价、总库存、预留库存和销量均能清楚显示。
2. 将主窗口缩小到普通非全屏尺寸。
3. 右侧商品编辑区仍占据大部分横向空间，左侧商品列表被压缩为很窄的一列。

**现象：**

- 左侧七列表格的表头大量显示为省略号或被截断。
- 商品名称、状态等数据也被缩略，用户无法直接辨认每一列的含义和商品信息。
- 左侧列表与右侧编辑区的宽度分配在缩小窗口后明显失衡。
- 页面仍能操作，但商品选择和信息对照的可读性、观感与使用效率显著下降。

**用户反馈：** 全屏状态显示比较清楚；缩小后左侧部分被严重压缩，明显影响观感。

**用户提出的根因判断：** 当前页面试图在同一个界面内同时容纳商品列表、商品资料、封面选择、规格列表和新增操作，导致左右两侧长期争抢空间；这种“一个界面完成全部功能”的设计思路不适合普通窗口尺寸。

**用户提出的改造方向：**

- 卖家商品管理主界面聚焦商品列表、商品选择和必要的概要查看。
- “创建商品”等新增内容操作改为独立弹窗，填写完成后提交或取消，再刷新主列表。
- “添加规格”同属新增内容操作，应优先采用独立弹窗，避免在主界面常驻完整新增表单。
- 弹窗应具有明确的确认和取消出口，取消时不能污染当前列表选择或已保存数据。
- 当前意见尚未确定“更新现有商品”是否也改为弹窗，后续设计时单独确认，不在本条中扩大范围。

**待后续设计确认：**

- 定义卖家商品管理页支持的最小可用宽度。
- 在新增操作移入弹窗后，重新确定主界面的信息层级与列表可用宽度。
- 确定剩余主界面区域在窗口缩小时的最小宽度、比例和收缩优先级。
- 评估在较窄窗口下采用横向滚动、隐藏次要列或其他响应式布局方式。
- 保证商品列表的关键列在目标窗口尺寸下仍可辨认，不以连续省略号作为正常展示状态。

**验收关注点：**

- 在全屏与普通非全屏窗口尺寸下分别截图验收。
- 缩小窗口后，商品列表不能被压缩为无法阅读的窄条。
- 调整窗口尺寸后布局应即时、稳定地重新分配空间，不要求用户切换标签页才能恢复。
