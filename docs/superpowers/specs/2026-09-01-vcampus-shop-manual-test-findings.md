## 1. 测试背景与约束

本阶段只收集和整理问题，不在本文中确定具体技术实现。商品图片继续使用简单占位，不因本轮界面问题引入图片资源或数据库升级。

## 3. 按领域归类

### 3.1 页面布局与商品展示

#### SHOP-TEST-001：首次进入商城时页面高度异常

**影响范围：** 所有账号首次登录后进入商城首页。
**严重程度：** 高。

**现象：**

- 第一次进入商城首页时，商品内容区域异常偏长。
- 页面下半部分存在大量没有实际内容的空白。
- 垂直滚动范围明显超过当前商品内容所需高度。
- 点击“下一页”，再点击“上一页”回到第一页后，布局恢复正常。

**复现步骤：**

1. 启动客户端并登录任意固定账号。
2. 第一次进入商城首页。
3. 观察商品区域高度、页面底部空白和垂直滚动条。
4. 点击“下一页”。
5. 点击“上一页”返回第一页。
6. 对比首次进入与翻页后的页面高度。

**期望结果：**

- 第一次加载完成后立即按照窗口宽度和商品数量计算正确的网格高度。
- 页面底部不出现无意义的大面积空白。
- 首次加载与翻页返回后的页面布局一致。

**验收关注点：**

- 所有账号首次进入均正常。
- 不同窗口尺寸下均不会出现异常滚动范围。
- 异步商品加载完成后，布局和滚动容器能够正确刷新。

#### SHOP-TEST-003.1：商品卡底部按钮重复展示商品信息

**影响范围：** 所有同时展示多个商品的页面。
**严重程度：** 中高。

**现象：**

- 商品卡已经展示商品名、价格等信息。
- 卡片底部又显示包含商品名和价格的按钮，信息重复。
- 商品名称较长时，按钮文字被截断，增加视觉拥挤和理解成本。

**用户期望：**

- 移除卡片底部重复展示商品信息的购买按钮。
- 点击商品图片、名称或描述组成的商品区域即可进入商品详情。
- 该交互应覆盖首页、搜索结果、分类结果、店铺商品和其他多商品展示页面。

**验收关注点：**

- 商品信息不再重复展示。
- 整个商品卡片具有明确、统一的可点击反馈。
- 鼠标与键盘操作均可进入商品详情。
- 调整后不影响分页、滚动和商品网格排列。

#### SHOP-TEST-003.2：首页与搜索结果的店铺信息展示策略

**影响范围：** 商城首页和商品搜索结果。
**严重程度：** 中。

**用户期望：**

- 首页同时展示多个商品时，不显示店铺名称，降低首页信息密度。
- 用户执行搜索后，搜索结果应显示店铺名称，帮助区分商品来源。
- 通过首页分类入口进入的结果属于搜索结果，应按搜索页面规则显示店铺名称。

**验收关注点：**

- 首页商品卡不显示店铺名称。
- 搜索结果稳定显示店铺名称。
- 两类页面可以复用基础商品卡，但展示规则必须能够按使用场景切换。

### 3.2 搜索与筛选

#### SHOP-TEST-006：“筛选”与“应用筛选”语义混淆

**影响范围：** 从首页搜索后进入的商品搜索页面。
**严重程度：** 中。

**现象：**

- 搜索栏附近显示“筛选”按钮。
- 展开筛选区域后又显示“应用筛选”按钮。
- 两个按钮名称相近，但一个用于展开或收起区域，另一个用于执行筛选，容易被理解为重复功能。

**用户期望：**

- 展开或收起筛选区域与执行筛选应有清晰、不同的文字和视觉层级。
- 用户无需猜测两个按钮的差异。

**方案阶段需要确认：**

- 筛选条件是修改后自动应用，还是保留单独确认操作。
- 分类、价格和排序是否采用一致的刷新规则。
- 展开按钮与执行按钮最终采用的文字。

### 3.3 购物车与确认订单

#### SHOP-TEST-007.1：缺少商品小计与订单总价

**影响范围：** 购物车和确认订单页面。
**严重程度：** 严重。

**现象：**

- 购物车只能看到商品单价和数量，看不到单项小计与购物车总价。
- 确认订单页面只能看到商品及单价，看不到数量、小计和最终订单总价。
- 用户在提交订单前无法清楚确认最终支付金额。

**期望结果：**

每件商品至少展示：

- 商品名称与 SKU。
- 单价。
- 数量。
- 小计，即单价乘以数量。

页面汇总区域至少展示：

- 商品总数量。
- 订单总价。
- 进入结算或提交订单操作。

**验收关注点：**

- 修改数量后，单项小计、商品总数量和总价立即同步。
- 删除商品后，汇总金额立即同步。
- 确认订单金额与购物车及服务端计算结果一致。
- 最终金额在“提交订单”附近清晰可见。

#### SHOP-TEST-007.2：商品不应横向连续排列

**影响范围：** 购物车和确认订单页面。
**严重程度：** 高。

**现象：**

- 多件商品横向排列在同一行。
- 商品名称、价格、数量输入和按钮相互挤压。
- 商品较多或名称较长时难以阅读和操作。

**用户期望：**

- 商品采用纵向列表排列。
- 每件商品独占一行或一张横向信息卡。
- 多件商品从上到下排列，内容超过页面时使用纵向滚动。
- 购物车和确认订单保持一致的信息层级。

#### SHOP-TEST-007.3：购物车商品区域应进入商品详情

**关联问题：** `SHOP-TEST-003.1`。
**影响范围：** 购物车商品列表。
**严重程度：** 中。

**用户期望：**

- 点击购物车中的商品图片、商品名称或描述区域，进入对应商品详情。
- 数量输入框、“更新”和“删除”等操作保留自身行为，不触发详情跳转。
- 从商品详情返回后恢复购物车页面及原有滚动位置。
- 查看详情不能导致购物车数量或其他状态丢失。

### 3.4 开店申请

#### SHOP-TEST-002A：完整填写后不能直接提交审核

**影响角色：** 申请开店的学生和教师。
**严重程度：** 高。

**现象：**

- 用户完整填写申请内容并点击“提交审核”时，系统要求先保存草稿。
- 用户必须额外执行一次“保存草稿”，才能提交审核。

**用户期望：**

- 页面当前填写内容通过校验后，可以直接提交审核。
- 提交操作使用页面中的最新内容，不强制依赖已持久化的草稿。
- “保存草稿”继续作为暂时不提交时的独立功能。
- 被驳回申请修改完整后也应允许直接重新提交。

**验收关注点：**

- 新申请和被驳回后重提均支持直接提交。
- 校验失败时保留当前内容，并明确提示有问题的字段。
- 成功提交后状态正确变为待审核。

#### SHOP-TEST-002B：未保存内容离开时没有确认提示

**影响范围：** 开店申请页面的返回及商城工具栏导航。
**严重程度：** 高。

**现象：**

- 用户填写或修改申请内容后，如果没有保存草稿，离开申请区域时没有明确的数据保护提示。

**用户期望：**

当存在未保存修改并准备离开时，应提示用户选择：

- 保存草稿并离开。
- 不保存并离开。
- 取消离开并继续填写。

**验收关注点：**

- 返回、“我的”“购物车”及其他会离开申请页面的入口均遵守同一规则。
- 已保存且之后没有修改时不弹出提示。
- 选择取消后，所有页面内容保持不变。
- 选择保存后，草稿可在再次进入时恢复。

### 3.5 管理员审核

#### SHOP-TEST-004：审核列表未区分未处理与已处理

**影响角色：** 管理员。
**严重程度：** 中高。

**现象：**

- `PENDING`、`APPROVED` 和 `REJECTED` 申请混在同一列表中。
- 管理员无法快速区分需要操作的申请与历史记录。
- 当前列表没有清晰展示排序所依据的时间。

**用户期望：**

- 未处理区域只展示 `PENDING` 申请。
- 已处理区域展示 `APPROVED` 和 `REJECTED` 申请。
- 未处理和已处理都要按照时间排序。
- 管理员打开审核界面后能够优先定位未处理申请。

**验收关注点：**

- 处理完成的申请立即从未处理区域移动到已处理区域。
- 未处理列表展示提交时间，已处理列表展示审核时间。
- 时间相同时使用稳定的次级排序，刷新后顺序不跳动。
- 已处理记录保留审核状态、审核意见和时间。

**方案阶段需要确认：** 时间采用升序还是降序展示。

### 3.6 卖家商品与 SKU 管理

#### SHOP-TEST-005：卖家工作区暴露内部技术字段

**影响角色：** 获批店长；管理员商品管理界面存在相似表现。
**严重程度：** 高。

**现象：**

- 新增 SKU 时要求店长手工填写 `SKU ID`。
- 店长需要理解 ID 格式并自行保证唯一性，显著增加操作难度和出错概率。
- 卖家工作区直接展示较多数据库或接口层字段，整体操作方式偏技术化。

**用户明确要求：**

- SKU ID 不应由店长填写，应由系统自动生成。
- 卖家工作区界面需要整体整改。
- 本阶段先记录问题，后续根据全部问题统一策划方案。

**后续策划范围：**

- 区分商品和 SKU 的业务字段与内部技术字段。
- 梳理店长创建商品、增加 SKU、修改库存和上下架的最短操作路径。
- 评估 `SKU ID`、版本号、布尔状态和封面 URL 的展示方式。
- 明确管理员与店长商品编辑界面的复用边界。
- 图片继续使用占位策略，不升级数据库。

### 3.7 导航与返回逻辑

#### SHOP-TEST-008：我的与购物车污染返回历史

**影响范围：** 商城首页、我的、购物车之间的导航。
**严重程度：** 高。

**现象：**

- 进入首页后反复点击“我的”和“购物车”，每次切换都会继续追加返回历史。
- 点击“返回”时，会在“我的”和“购物车”之间不断切换。
- 用户需要多次返回，并且最终可能无法回到首页。
- 重复点击当前页面也可能增加无意义的历史记录。

**用户期望的导航关系：**

- “我的”和“购物车”属于同一层级的商城工具页。
- 两者之间切换时不应互相叠加返回历史。
- 从首页首次进入工具页时记住首页为来源。
- 在工具页之间切换时只替换当前工具页。
- 无论切换多少次，点击一次“返回”都回到首页。
- 重复点击当前工具页不产生新历史。

**必须通过的场景：**

1. 首页 → 我的 → 返回 → 首页。
2. 首页 → 购物车 → 返回 → 首页。
3. 首页 → 我的 → 购物车 → 返回 → 首页。
4. 首页 → 购物车 → 我的 → 返回 → 首页。
5. 首页 → 我的 → 购物车 → 我的 → 返回 → 首页。
6. 首页 → 购物车 → 我的 → 我的 → 返回 → 首页。

**后续策划范围：**

- 区分首页、搜索、店铺、详情等内容导航历史。
- 区分“我的”“购物车”等同级工具页切换。
- 单独定义结算、支付完成等流程页面的返回规则。

## 5. 后续策划顺序

以下顺序只用于安排后续设计讨论，不代表已经确定具体实现：

1. **优先保障金额与导航正确表达。** 先策划购物车、确认订单金额展示，以及“我的”“购物车”的返回模型。
2. **处理数据丢失风险。** 策划申请直接提交和未保存内容退出保护。
3. **整改关键业务工作区。** 统一策划卖家商品/SKU 操作与管理员审核信息架构。
4. **统一商品列表交互。** 处理商品卡点击区域、重复按钮、店铺字段和首次布局问题。
5. **简化搜索筛选。** 最后确定筛选区展开、条件应用和即时刷新规则。

在进入实施前，应针对每一类问题形成经过确认的交互方案和测试计划，再按优先级分批修改，避免把多个独立导航或页面状态问题混在同一批实现中。
