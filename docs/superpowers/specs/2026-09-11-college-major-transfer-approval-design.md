# 学院管理员参与转专业审批设计

## 1. 背景与目标

当前分支已经实现转专业完整流程，`feat/user-management` 分支实现了账户管理、分级管理员角色以及学院管理员与学院的绑定关系。本次工作先将该分支合并到当前分支，再让学院管理员承担转专业流程中的转出学院审批和转入学院审批。

目标是形成明确且不可绕过的职责分离：学籍管理员负责转专业批次和录取执行，学院管理员只审批与自己学院有关的申请。所有授权判断均由服务端依据数据库中的当前绑定关系完成。

## 2. 角色和职责

沿用 `feat/user-management` 中的基础角色，不新增转专业专用角色。

| 角色 | 转专业职责 |
| --- | --- |
| `STUDENT_ADMIN` | 管理批次、志愿专业和名额；录入成绩；生成拟录取；终审；办理生效；取消异常申请 |
| `COLLEGE_ADMIN` | 查看与所管学院有关的申请；代表原学院执行转出审批；代表目标学院执行转入审批 |
| `STUDENT` | 保存、提交和撤回本人的转专业申请，管理本人附件 |
| 其他角色 | 不获得转专业业务权限 |

`STUDENT_ADMIN` 不能代替学院执行转出或转入审批。`COLLEGE_ADMIN` 不能配置批次、名额、成绩、拟录取、终审或生效。

## 3. 学院范围模型

复用 `tblStudentCollegeAdministrator`：

- 一个启用学院可绑定多名有效学院管理员。
- 一名学院管理员同一时间只能绑定一个学院。
- 每个启用学院至少保留一名有效学院管理员。
- 分配、调岗或停用后，后续请求立即使用新的绑定关系；不信任客户端提交的学院编号。

转专业申请已经保存 `fromDepartmentId`，它是提交申请时的原学院快照。目标学院从申请关联的 `tblMajorTransferOption.targetDepartmentId` 获取。审批范围以这两个字段为准，避免学生学籍后续变化改变历史申请的审批责任。

## 4. 授权规则

### 4.1 转出审批

处理 `MAJOR_TRANSFER_REVIEW_SOURCE` 时：

1. 请求者必须为有效的 `COLLEGE_ADMIN`。
2. 请求者当前绑定的学院必须等于申请的 `fromDepartmentId`。
3. 申请必须处于 `SUBMITTED` 状态。
4. 原有三项资格确认、驳回原因和乐观锁规则保持不变。

### 4.2 转入审批

处理 `MAJOR_TRANSFER_REVIEW_QUALIFICATION` 时：

1. 请求者必须为有效的 `COLLEGE_ADMIN`。
2. 请求者当前绑定的学院必须等于申请志愿的 `targetDepartmentId`。
3. 申请必须处于 `SOURCE_APPROVED` 状态。
4. 原有批准、驳回原因和乐观锁规则保持不变。

### 4.3 查询和附件

- `STUDENT_ADMIN` 可以查看全部批次、志愿、申请详情和附件。
- `COLLEGE_ADMIN` 只能查看原学院或目标学院等于其当前绑定学院的申请，以及这些申请的附件和审核记录。
- 学院管理员列表查询在服务端过滤；直接使用其他学院的申请 ID 或附件 ID 时返回统一的无权访问结果，不泄露记录是否存在。
- 学生原有的本人工作台与本人附件权限保持不变。

### 4.4 其他管理命令

保存批次、保存志愿、录入成绩、生成拟录取、终审、生效和取消仅允许 `STUDENT_ADMIN`。`SUPER_ADMIN`、用户管理员和学院管理员不因管理身份自动取得这些权限。

## 5. 服务端结构

新增转专业学院范围授权组件，职责为：

- 根据管理员用户编号查询其唯一有效学院绑定。
- 根据申请编号一次性解析原学院和目标学院。
- 提供“可查看申请”“可执行转出审批”“可执行转入审批”三个明确判断。
- 对附件先解析所属申请，再执行相同的申请范围校验。

Handler 负责角色和命令边界，授权组件负责学院范围，`MajorTransferService` 继续负责状态机、事务、锁和业务校验。审批权限在进入状态变更事务前校验，并在同一业务操作中再次读取申请，避免依赖客户端数据。

查询接口接收当前操作者上下文。仓储层优先使用带学院条件的查询，避免先读取所有申请再在内存中过滤。

## 6. 客户端行为

- `STUDENT_ADMIN` 进入转专业管理页后看到批次、志愿、成绩、拟录取、终审和生效操作，不显示学院审批按钮。
- `COLLEGE_ADMIN` 进入学院审批工作台，只看到与本学院相关的申请。
- 当本学院是原学院且状态为 `SUBMITTED` 时显示“转出审批”。
- 当本学院是目标学院且状态为 `SOURCE_APPROVED` 时显示“转入审批”。
- 其他状态只读展示，不出现无权操作按钮。
- 服务端拒绝结果统一显示“无权处理该学院的转专业申请”，避免把内部角色或绑定细节暴露给客户端。

客户端隐藏按钮只是交互优化，不能替代服务端鉴权。

## 7. 合并与冲突处理原则

合并 `feat/user-management` 时：

- 保留目标分支的账户管理、登录会话、分级角色、模块管理员和学院管理员治理功能。
- 保留当前分支的转专业、培养方案、数据库初始化兼容修复和演示数据。
- 对 `ServerMain`、学籍 Handler、角色权限种子和发布文件执行语义合并，不直接选择任一侧完整版本。
- 不把二进制数据库或 JAR 的冲突版本直接作为最终结果；代码和种子合并完成并通过测试后统一重新生成发布包。
- 与本功能无关的报告文档删除或重命名不参与业务冲突决策，保持目标分支已有提交历史。

## 8. 数据与演示账号

种子数据为每个启用学院创建至少一名有效 `COLLEGE_ADMIN` 并建立学院绑定。账号命名使用可识别且稳定的学院代码前缀，初始密码只用于本地测试并在说明文档列出。

现有 `ADMIN` 账号按用户管理分支规则迁移为 `SUPER_ADMIN`；另提供 `STUDENT_ADMIN` 用于中央学籍管理测试。发布数据库必须同时包含学生、组织、转专业和培养方案演示数据。

## 9. 并发、安全与审计

- 学院审批沿用申请资源锁、事务和 `applicationVersion` 乐观锁。
- 同一阶段只能生成一条审核记录，重复或并发审批返回稳定的并发/状态错误。
- 审核记录保存实际 `reviewerUserId`，学院管理员调岗不改写历史记录。
- 学院绑定变更沿用会话撤销机制；重新登录后客户端导航与新权限一致。
- 越权读取、越权审批和无效会话均返回统一错误，不返回 SQL、内部表名或目标记录详情。

## 10. 测试与验收

至少覆盖以下自动化测试：

1. 原学院管理员可审批本学院学生的 `SUBMITTED` 申请。
2. 非原学院管理员不能执行该申请的转出审批。
3. 目标学院管理员可审批目标学院的 `SOURCE_APPROVED` 申请。
4. 非目标学院管理员不能执行该申请的转入审批。
5. `STUDENT_ADMIN` 不能调用两项学院审批命令。
6. `COLLEGE_ADMIN` 不能调用批次、成绩、拟录取、终审、生效和取消命令。
7. 学院管理员列表、详情和附件查询不会返回无关学院的数据。
8. 管理员调岗后，旧学院权限立即失效，新学院权限立即生效。
9. 并发审批不会产生重复审核或非法状态跳转。
10. 数据库初始化后每个启用学院均有有效管理员，转专业及培养方案演示数据完整。
11. 用户管理、学籍、转专业和培养方案相关回归测试全部通过。
12. 重新构建并核验 `vCampus-release` 中的客户端、服务端和数据库。
