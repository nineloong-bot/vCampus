# 学生学籍与转专业数据质量改造设计

## 1. 背景与目标

当前转专业流程已经具备批次、招生选项、学生申请、分阶段审核和生效执行模型，但资格规则没有集中表达：服务端未强制校验大一与年龄范围，也未禁止同学院专业变动。现有大规模测试数据生成器还没有生成转专业专项场景，部分 Swing 页面直接拼接枚举值，导致英文状态暴露。

本次改造的目标是：

- 所有转专业写入口在同一事务和锁保护下执行一致的资格校验；
- 清理已有不满足规则的转专业申请，且不触碰既有测试账号；
- 生成可重复、可验证的大规模 Access 测试数据，包含大量计算机学院大一转入数学学院场景；
- 统一 Swing 客户端的状态、审核阶段和审核决定中文显示；
- 保持 Access/UCanAccess、三季制培养方案和现有跨模块端口边界不变。

## 2. 现状与约束

项目使用 JDK 21、Maven、Java Swing 客户端和 Microsoft Access/UCanAccess。数据源为 `vcampus-database/schema` 与 `vcampus-database/seed`，现有独立测试数据生成器位于 `vcampus-database/demo/full-test-data/tools`。

转专业申请保存了来源学院、专业、班级和年级快照；目标学院由 `tblMajorTransferOption.targetDepartmentId` 表达，目标专业与学院的正式关系由组织仓储读取。客户端身份、来源组织和授权学院不能作为可信输入。

工作区已有未提交的 `vcampus-distribution/data/vCampus.accdb` 修改，本次不回滚、不直接编辑该数据库文件。所有数据库重建都使用临时路径，验证通过后才允许替换生成物。

## 3. 方案与选择

### 3.1 规则校验

新增集中式 `MajorTransferEligibilityPolicy`，以学生正式组织关系、学生生日、批次开始时间和目标选项为输入，输出结构化失败原因或通过结果。服务调用方在 `saveDraft`、`submit` 以及会改变申请状态或目标关系的管理员写操作中调用策略；在已有锁和事务内重新读取学生与组织关系，避免校验与写入之间的数据漂移。

规则固定为：

1. 仅 `UNDERGRADUATE` 且正常在籍、在校学生可以申请；
2. 申请时点的年级必须为大一。年级按批次申请开始日所在学年与班级 `enrollmentYear` 计算；
3. 申请开始日计算出的年龄为 17–20 岁，首尾均包含；
4. 目标专业必须属于当前批次、已启用且与当前专业不同；
5. 当前专业所属学院必须与目标专业所属学院不同；
6. 已生效转专业或其他批次进行中的申请继续按既有规则拒绝。

资格检查展示也复用同一策略，避免 UI 显示“可申请”而服务端拒绝。错误使用既有稳定业务错误码体系，客户端只接收安全的中文业务提示，不暴露 SQL、路径或内部异常。

### 3.2 脏数据清洗

新增 Java 清洗入口，参数为数据库路径和审计/执行模式。工具以 Access 连接开启事务，先查询违规申请 ID，再按外键依赖顺序删除 `tblMajorTransferAttachment`、`tblMajorTransferReview`、`tblMajorTransferExecution` 和 `tblMajorTransferApplication`。执行模式只删除违规申请及其依赖记录，不更新或删除 `tblUser`，因此保留所有既有测试账号及密码。

同时提供 Access 兼容审计 SQL，检查：非大一、年龄不在 17–20、当前学院与目标学院相同、目标关系失效，以及快照与正式关系冲突。清洗完成后再次执行同一审计查询，违规数必须为零；删除数量和保留账号数量输出为可审查摘要。

### 3.3 大规模 Seed

沿用现有 Python 生成器，而不是创建第二套数据模型。将学生规模、计算机学院专项人数和随机种子做成命令行可配置值；基础学生按学院、专业、班级和四个入学 cohort 生成，专项学生固定为当前批次可申请的大一 cohort，并生成 17–20 岁生日。

生成过程在输出 SQL 前执行本地资格断言：专项学生必须为大一、年龄合规、来源学院为计算机学院、目标学院为数学学院且两者不同。随后生成批次、数学学院招生选项及大量 `SUBMITTED` 申请，申请来源快照从同一学生数据派生。

保留策略：不删除、不更新、不覆盖现有测试账号；bulk 账号使用独立 `bulk-*` ID，既有测试账号仍由原有 seed 提供。生成器不得写入正在使用的 `.accdb`，只输出 SQL、数量快照和账号清单。更新后的数据集验证器检查账号、学生、专项申请的数量与规则一致性。

### 3.4 Swing 中文状态字典

新增模块内集中字典，将 `MajorTransferStatus`、`MajorTransferBatchStatus`、`MajorTransferDecision`、`MajorTransferReviewStage` 转换为中文。字典对未知值返回“未知状态/未知阶段/未知决定”，禁止直接使用 `name()`、`toString()` 或字符串拼接渲染可见状态。

统一替换批次列表与编辑页、学生时间线、学院处理列表、申请详情和流程图中的状态展示。业务判断仍使用 enum，不将中文标签反向用于状态流转。新增测试验证每个公开枚举都有中文标签且关键 UI 文本不包含英文枚举值。

## 4. 数据流与错误处理

学生写请求进入 Handler 后，由服务在学生资源锁内开启 Access 事务；服务重新查询学生、班级、当前专业、当前学院、目标专业和目标学院，再调用策略。失败时回滚事务并返回稳定的业务错误码。管理员操作同样重新检查目标学院授权和申请快照，不依赖客户端传入的学院或目标名称。

清洗工具遇到 SQL 或约束错误时回滚整个事务，保留原库不变，并以非零退出码结束。审计模式只读。Seed 生成器遇到断言失败时不输出可作为数据库输入的生成 SQL。

## 5. 测试策略与验收标准

- common/server：先写规则单元测试，覆盖非大一、年龄边界、年龄越界、同学院、跨学院和合法大一案例；测试先 RED，再实现后 GREEN；
- server：覆盖学生保存草稿/提交入口，确认非法数据无法写入；覆盖清洗工具的外键删除顺序和测试账号保留；
- Python：覆盖专项学生数量、计算机→数学跨学院关系、年龄/年级和申请快照；保留原有四 cohort、三季制课程与培养方案断言；
- client：覆盖所有状态字典和关键面板，确认状态展示使用中文；
- 数据集：在临时 Access 数据库中建库、导入、运行验证器和审计 SQL；
- 最终在 JDK 21 下运行 `mvn test`，并检查精确 diff，不提交日志、`target`、缓存、锁文件或秘密。

## 6. 范围外事项

本次不引入 MySQL、远程数据库、Vue/React 前端、新的培养方案副本、年龄以外的身份核验规则，也不改变转专业状态机、审批角色模型、课程三季制或现有测试账号密码。
