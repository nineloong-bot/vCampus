# vCampus 多模块统一集成设计

**日期：** 2026-09-02  
**目标分支：** `integration/user-all-modules`  
**用户与登录基线：** `origin/feat/user-management@e00aa3c`  
**业务模块来源：** `origin/course-user-management`、`origin/nineloong`、`origin/user-library`、`origin/SHOP`

## 目标

将用户管理、学籍、课程、图书馆和商城合并为一个可启动、可登录、共享会话与数据库的“虚拟校园”程序。最终交付一个服务端进程、一个客户端入口、一份可重复生成的 Access 发行数据库，以及覆盖所有模块主要功能的人工测试数据和说明。

## 集成原则

1. 保留各分支 Git 历史，依次合并 Course、Student、Library、Shop。
2. 登录界面、账号生命周期、会话、用户权限模型以最新 User Management 为准。
3. 各业务模块内部领域逻辑、页面和测试以对应模块最新版为准。
4. 对 `ClientMain`、`MainFrame`、`ServerMain`、权限种子和数据库初始化进行语义整合，不机械选择任一冲突侧。
5. 不合并各模块提交的 `vcampus-distribution/lib/*.jar`；统一源码完成后重新构建发行 JAR。
6. 不合并二进制 `vCampus.accdb` 内容；最终数据库由统一 schema 和 seed 从空库生成。
7. 默认服务端端口保持 `8888`。

## 总体架构

### 客户端

`ClientMain` 只负责创建网络连接并启动 User Management 登录流程。认证成功后，`UserUiCoordinator` 将当前 `UserView`、权限集合和共享 `ClientConnection` 交给统一 `MainFrame`。

`MainFrame` 作为唯一应用外壳，注册以下页面：

- 学籍管理：使用 Student 模块的页面工厂和客户端服务。
- 课程中心：使用 Course 模块的 UI composition 和客户端 service。
- 图书馆：使用 Library 模块的页面与客户端 service。
- 校园商城：使用 Shop 模块的 UI installer/coordinator 和客户端 service。
- 账户管理：保留 User Management 的账户、管理员用户管理与退出登录流程。

页面可见性由登录结果中的角色和权限决定；服务端仍是最终授权边界。关闭主界面或退出登录时，只关闭一次共享连接并清理当前会话。

### 服务端

保留 User Management 的 `ServerMain`、`ApplicationRuntime`、`SessionRegistry`、认证与审计实现。统一启动时使用一个 `MessageRouter`，依次注册 User、Student、Course、Library、Shop handlers，最后在端口 `8888` 启动一个 Socket 服务。

各模块通过适配器读取同一会话身份：

- Student、Course、Library 使用统一用户 UUID、登录号和 `STUDENT`/`TEACHER`/`ADMIN` 角色。
- Shop 的买家与店主身份通过统一会话解析；是否为店主由 Shop 申请和店铺记录决定，不增加全局 `SELLER` 角色。
- 管理员能力由 `ADMIN` 角色对应的权限集合授予，管理员必须能够进入并操作五个模块的管理功能。

服务端不能启动多个模块专用端口或并行 Demo runtime。各模块 Demo main 只保留为独立开发与回归入口，不作为最终发行启动方式。

## 权限设计

全局基础角色保持三种：

| 角色 | 用户管理 | 学籍 | 课程 | 图书馆 | 商城 |
| --- | --- | --- | --- | --- | --- |
| `STUDENT` | 本人账户 | 本人学籍及允许的申请 | 查询、选课、退课、课表 | 检索、借阅及本人记录 | 浏览、购物；通过申请成为店主 |
| `TEACHER` | 本人账户 | 只开放模块已有的教师能力 | 查询及教师课表 | 检索与教师借阅能力 | 浏览与购物 |
| `ADMIN` | 用户、角色、状态、审计 | 学籍管理与审核 | 学期、课程、教学班及调整管理 | 馆藏、借阅与管理功能 | 店铺申请、店铺和商品管理 |

统一 `010_roles_permissions.sql` 必须包含所有模块声明并实际检查的权限码。权限码保留各模块既有命名，避免无必要地改动网络契约。自动化测试验证管理员权限为各模块权限并集，同时验证学生和教师不能调用管理员命令。

## 数据库构建

### Schema 顺序

数据库从空白 Access 文件开始，按依赖顺序安装：

1. `001_common.sql`
2. `010_user.sql`
3. `020_student.sql`
4. Course schema
5. Library schema
6. `050_shop.sql`

若模块 schema 文件编号冲突，调整文件名和初始化清单顺序，不修改既有表名或网络 DTO。外键引用统一使用 `tblUser.userId` 或模块当前已经采用的稳定用户标识；确有差异时在模块适配器中转换，不复制用户表。

### Seed 顺序

1. 角色、权限和角色权限映射。
2. 测试用户账户。
3. 学籍组织结构、学生和教师关联数据。
4. 课程学期、课程、教学班、选课与成绩数据。
5. 图书馆馆藏、读者、借阅与逾期数据。
6. 商城申请、店铺、商品、商品种类、购物车、订单与支付数据。

数据库生成器必须可以安全地从空目标路径生成数据库。为避免掩盖脚本问题，测试生成时删除的是测试临时目录中的目标文件，不覆盖开发者现有数据库。发行数据库由受控构建脚本显式生成。

## 测试账号与业务数据

所有人工测试账号使用文档中明确公开的统一测试密码；测试库不得包含真实个人信息。最终账号表至少包含：

| 测试身份 | 角色/状态 | 覆盖目标 |
| --- | --- | --- |
| 综合管理员 | `ADMIN`、正常 | 五个模块全部后台权限与用户管理 |
| 普通学生 | `STUDENT`、正常 | 学籍查询、选课、借阅、购物 |
| 店主学生 | `STUDENT`、正常且已有店铺 | 店铺资料、商品/种类、上下架、订单 |
| 申请中学生 | `STUDENT`、申请待审核 | 店主申请与管理员审核 |
| 草稿申请学生 | `STUDENT`、申请草稿 | 保存、恢复和提交申请 |
| 普通教师 | `TEACHER`、正常 | 教师课表及图书馆教师流程 |
| 首次登录账号 | 任一基础角色、必须改密 | 首次登录改密流程 |
| 冻结账号 | 任一基础角色、冻结 | 禁止登录 |
| 锁定测试账号 | 任一基础角色、正常 | 连续错误密码与锁定倒计时 |

业务数据必须覆盖：

- Student：完整学籍、不同院系/专业/班级、至少一项可审核或可查看的变更记录。
- Course：当前学期、选课期和调整期数据；可选、已选、容量已满、时间冲突、退课、重修及成绩导入场景。
- Library：可借、已借、逾期、不可借馆藏，以及普通读者与管理员操作场景。
- Shop：待审核/已通过申请，正常/暂停店铺，上架/下架/草稿商品，多商品种类与库存，未选/部分选中购物车，待支付/已支付/失败或取消订单。

跨模块身份必须复用同一 `userId`：普通学生、店主学生和教师在 User、Student、Course、Library、Shop 中的数据彼此对应。

## 合并与实现顺序

1. 合并 Course，保留 User Management 登录与用户服务契约，接入 Course composition。
2. 合并最新 Student，保留其新增学籍功能并适配统一装配。
3. 合并 Library，统一客户端/服务端入口和权限种子，忽略其发行 JAR 与二进制数据库版本。
4. 合并 Shop，接入统一客户端、服务端、会话身份与数据库初始化。
5. 建立统一数据库生成器与综合 seed。
6. 重建发行 JAR 和启动脚本，补充人工测试说明。

每次行为改动遵循测试驱动：先增加能表达缺失集成行为的测试并确认因预期原因失败，再实现最小改动并运行模块回归。纯 Git 合并和冲突标记本身不要求人为制造失败测试，但解决后的行为必须由现有或新增测试验证。

## 错误处理与兼容性

- 网络消息类型和模块公开 DTO 保持兼容；不为统一 UI 随意重命名内部契约。
- 重复路由注册应在启动测试中立即失败，并指出冲突消息类型。
- schema 或 seed 安装失败必须终止数据库生成，不能留下被当成成功结果使用的半初始化发行库。
- UI 将各模块服务端错误映射为中文提示；未知错误显示稳定的通用中文消息并保留日志诊断信息。
- 首次改密、冻结、锁定和会话失效行为由 User Management 统一处理，业务模块不得绕过受限会话检查。

## 验证与交付

自动化验证包括：

1. 各模块定向单元测试。
2. 统一客户端页面注册与角色可见性测试。
3. 统一服务端路由注册、会话身份和管理员授权测试。
4. 从空库生成数据库并校验账号、权限、外键和各业务状态的数据测试。
5. 使用统一数据库的端到端 Socket 测试。
6. `mvn clean verify` 全仓回归。
7. 发行构建及 PowerShell/批处理启动脚本测试。

人工交付材料包括：

- 服务端与客户端启动命令，默认端口 `8888`。
- 测试账号、密码、角色及用途表。
- 按模块和跨模块流程组织的人工验收清单。
- 已知限制和自动化测试证据。

最终人工验收至少验证：同一账号登录后能够在一个主界面切换被授权模块；管理员能够管理全部模块；学生、教师、店主的权限互不越权；所有测试数据状态能够在对应页面中观察并驱动完整操作流程。

## 范围边界

本轮只为完成五模块统一运行所需的装配、适配、权限、数据库、发行与测试工作。各模块内部未阻塞集成的功能优化、视觉重构和新业务需求不纳入本轮。
