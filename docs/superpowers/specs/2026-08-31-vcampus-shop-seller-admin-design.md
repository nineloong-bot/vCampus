# vCampus Shop 卖家与管理员设计

## 1. 目标与边界

本阶段在现有买家商城基础上补齐学生/教师开店、店主经营和管理员治理能力，同时修复人工测试发现的导航、库存校验、SKU 展示、搜索筛选和商品列表交互问题。

实现范围限于 `common/shop`、`server/shop`、`client/shop`、Shop 数据库、Demo、测试和说明文档。Foundation、User、Socket、Router、事务框架与公共网络接口只作为依赖使用。登录用户、角色与会话信息由现有 User 和连接层提供，Shop 只消费这些信息并在自己的服务端入口执行授权。

## 2. 身份、能力与所有权

Shop 识别三类现有用户角色：

| 身份 | 买家能力 | 开店能力 | 店铺管理 | 商城治理 |
| --- | --- | --- | --- | --- |
| 学生 | 可购买其他店铺商品 | 可申请，最多拥有一家店 | 审批通过后管理自己的店 | 无 |
| 教师 | 可购买其他店铺商品 | 可申请，最多拥有一家店 | 审批通过后管理自己的店 | 无 |
| 管理员 | 不可加入购物车、结算或支付 | 不可申请 | 可管理任意指定店铺商品 | 审批、店铺停用/恢复、全局商品管理 |

卖家不是 User 模块中的新角色。Shop 根据当前用户是否拥有已审批店铺动态确定卖家身份。店主仍可购买其他店铺商品，但服务端禁止购买自己店铺的商品。管理员只允许浏览与管理；买家写操作、开店申请和自购限制都必须在服务端校验，不能只依赖按钮显隐。

每位学生或教师最多存在一份开店申请记录，并最多拥有一家店铺。申请、店铺、商品和卖家订单的所有权均由当前会话中的用户编号确定，请求体不接受可替代当前用户的 owner/buyer 参数。

## 3. “我的”入口与状态化操作

“我的”继续显示当前用户的只读基本信息和本人历史已支付订单，并根据身份和开店状态显示操作入口。

学生和教师始终可“查看订单”，第二个入口按状态变化：

| 当前状态 | 入口 | 行为 |
| --- | --- | --- |
| 无申请 | 我要开店 | 打开空白申请表 |
| 草稿 | 继续填写 | 恢复草稿表单 |
| 待审核 | 查看审核状态 | 只读显示已提交材料和状态 |
| 已拒绝 | 修改并重新提交 | 显示拒绝原因并允许编辑原申请 |
| 已通过 | 管理我的店铺 | 进入卖家工作区 |

管理员显示“查看订单”和“商城管理”。管理员不能新建买家订单；“查看订单”仅保留对既有历史记录的只读兼容。

所有这些页面都进入 `ShopNavigator` 历史栈，公共工具栏的返回按钮必须回到准确的前一 Shop 页面。支付成功后的“查看已支付订单”先把商城首页设为安全根路由，再打开“我的”，因此返回时进入商城首页，不会回到已经完成的结算或支付页面。

## 4. 开店申请

### 4.1 申请材料

开店申请采用结构化文本，包含：

- 店铺名称；
- 主营分类；
- 店铺描述；
- 联系方式；
- 申请说明/经营计划。

申请人编号和角色从会话获得。主营分类只能从“文具、图书、生活用品、药品、其他”中选择。表单允许保存草稿和提交审核；待审核期间材料只读；被拒绝后显示管理员填写的拒绝原因，申请人可编辑同一份申请并再次提交。

### 4.2 状态流转

```text
无申请 → 草稿 → 待审核 → 已通过
                    └→ 已拒绝 → 待审核
```

审批通过后，Shop 在同一事务中创建并启用申请人的店铺，申请变为已通过。状态变化采用版本号进行乐观并发控制；对过期版本的保存、提交或审批返回明确冲突错误，界面重新加载最新记录。

店铺名称去除首尾空白后按不区分大小写的规范值全局唯一。保存草稿不占用名称；提交、审批通过和已通过店铺改名时都重新检查。被拒绝的申请不保留名称。名称检查与写入使用 Shop 事务和规范化名称锁，避免两个并发请求通过先查后写产生重复店名。

## 5. 卖家工作区

卖家工作区包含店铺概况、商品管理和订单查询三个区域。

### 5.1 店铺概况

显示店铺名称、主营分类、描述、联系方式、启用状态和管理员停用原因。店主可修改店铺名称、描述和联系方式；主营分类在审批通过后锁定。店铺被管理员停用时，店主仍能查看资料、商品和订单，但不能创建、修改或上下架商品。

### 5.2 商品管理

商品以表格展示，列为：商品名称、状态、SKU 数量、最低价、总库存、已预留、销量。点击一行打开编辑器。

一个商品表示买家看到的通用商品类型，SKU 表示该商品的具体规格。例如商品名称为“中性笔”，其 SKU 可以是“黑色 0.5mm”“蓝色 0.5mm”和“黑色 0.7mm”。颜色、尺寸、包装等规格信息写入 SKU 名称，不拆成“黑色中性笔”“蓝色中性笔”等多个商品。

店主可在自己的店铺内：

- 新增商品；
- 修改商品名称、描述和封面图片 URL；
- 新增或修改多个 SKU；
- 修改 SKU 名称、价格、库存和启用状态；
- 上架或下架商品。

新增与编辑界面先填写通用商品名称、描述和可选封面图片 URL，再在同一商品内用 SKU 表格维护全部具体规格。同一店铺内，去除首尾空白并忽略大小写后的商品名称必须唯一；创建重名商品时提示店主打开已有商品并增加 SKU，从录入端保证同类规格归在同一商品下。

封面图片 URL 只接受合法的 `https://` 地址，最大长度为 2048 个字符，不允许包含用户名或密码。封面属于商品类型，商品下所有 SKU 共用该封面。未填写 URL 或图片加载失败时使用商品分类默认图。

商品分类继承店铺主营分类，店主不能单独修改。上架前至少存在一个启用、价格有效且库存大于零的 SKU。库存不得调低到已预留数量以下。所谓删除商品统一实现为下架（`INACTIVE`），保留订单历史和审计关联。

### 5.3 卖家订单

卖家只能只读查询自己店铺的订单，列表显示订单号、买家标识、商品和 SKU、数量、成交金额、支付时间及支付状态，并可展开查看明细。本阶段不提供发货、退款或人工修改订单状态能力。

## 6. 管理员工作区

管理员从“我的”进入“商城管理”，工作区包含开店审批、店铺管理和全部商品三个页签。

### 6.1 开店审批

审批表格显示申请人、角色、店铺名称、主营分类、联系方式、提交时间和状态，并支持状态筛选。点击一行打开完整材料详情。

“通过”操作需要二次确认，并再次检查申请版本、申请资格、单店限制和店名唯一性。“拒绝”必须填写拒绝原因。审批结果写入 Shop 业务日志，记录管理员、申请、前后状态和原因。

### 6.2 店铺管理

管理员可查询全部店铺并查看店主、分类、状态和商品概况。停用店铺必须填写原因；停用后该店铺及其商品不再出现在买家首页、搜索、店铺页和可购买校验中。管理员可恢复店铺，恢复后只有原本为上架状态且可售的商品重新对买家可见。

店铺停用期间，卖家只能查看资料和订单。停用与恢复采用版本保护并写入 Shop 业务日志。

### 6.3 全部商品

管理员先选择目标店铺，再复用商品管理表格和编辑器。管理员可在指定店铺内新增、编辑和上下架商品，也可修改任意 SKU 的库存与价格。商品仍归属于所选店铺，分类仍继承该店铺主营分类。管理员的每次商品写操作都记录目标店铺、商品、操作者和变更摘要。

## 7. 买家界面修正

### 7.1 商品卡片网格

首页、搜索结果和店铺商品页共享同一个商品卡片网格。搜索、分类、价格范围、排序和筛选组成顶部功能栏，商品区域按照可用宽度自动计算列数并换行排列。

每张卡片依次显示商品封面图片、通用商品名称和起售价，整张卡片可点击并进入商品详情。每个通用商品类型只出现一张卡片；例如列表显示“中性笔”，黑色、蓝色和笔尖粗细在详情页作为 SKU 选择。起售价取该商品全部可售 SKU 的最低价格，销量汇总全部 SKU 并继续用于销量排序。

### 7.2 搜索与筛选

首次搜索前只显示关键词输入框和“搜索”。首次搜索成功后，分类、最低价、最高价、排序方式和“筛选”按钮自动展开，并在该搜索页面生命周期内保持显示。

分类和价格条件在点击“筛选”后生效；排序方式一经选择立即重新查询，并把页码重置为第一页。排序选项显示中文名称，如“销量优先”和“价格优先”。从详情、购物车或“我的”返回时，恢复关键词、分类、价格、排序、页码和滚动位置；恢复控件状态时抑制监听器，避免产生额外查询。

### 7.3 SKU 与库存校验

商品详情先显示通用商品名称、店铺、分类和描述，再列出该商品的可售规格。SKU 下拉框显示“黑色 0.5mm”等规格名称，内部仍保存 SKU 编号用于请求；选择规格后同步显示该 SKU 的价格和可售库存。加入购物车前先提交并校验数量编辑器中的文本；数量必须是整数且处于 1 到当前 SKU 可售库存之间。输入无效或超过库存时显示明确提示，不发送加购请求，也不改变购物车数量。

服务端仍是最终库存和权限边界：加购、修改购物车和结算均重新校验 SKU、商品、店铺状态、可售库存、管理员购买限制和店主自购限制。并发库存变化导致失败时，客户端刷新详情或购物车并展示服务端错误。

### 7.4 可替换的 UI 边界

买家商品区拆分为稳定的数据/交互层和可替换的展示层。Shop 查询与导航只向商品网格传递 `ProductSummary`、分页状态和打开详情回调；Shop 内部的卡片渲染器负责把摘要与已解析图片生成 Swing 卡片，图片加载器负责异步解析 URL、缓存和默认图。

网格容器不依赖卡片内部控件，卡片渲染器不发起查询或改变路由。卡片尺寸、间距、字体、颜色、图片裁剪和附加视觉信息集中在 `client/shop` 的目录型 UI 组件中。后续统一 UI 时可以替换卡片渲染器、图片加载策略和样式配置，保留商品 DTO、查询、分页、筛选、点击回调和 Shop 导航行为。

图片加载在后台执行，Swing 组件只在 EDT 更新。加载器设置连接和读取超时，限制响应体与解码尺寸，使用有界内存缓存；下载失败、格式不支持或超出限制时返回对应分类默认图，不影响商品列表其余内容。

## 8. Common 协议与客户端边界

Common 增加不可变、可序列化的申请、店铺管理、商品库存和卖家订单 DTO，以及带版本号的写命令。商品摘要、详情、创建和编辑 DTO 增加可选 `coverImageUrl`；Common 只传输 URL 字符串，不承担图片下载。客户端能力接口按用途拆分：

- `ShopClientPort`：现有买家只读与购买操作；
- `SellerShopClientPort`：本人申请、本人店铺、本人商品和本人店铺订单；
- `AdminShopClientPort`：审批、全部店铺和指定店铺商品管理。

Demo 的同一个客户端服务可以组合实现这些接口，但页面和协调器只接收所需能力，减少误用。服务端在现有 `BuyerShopHandlers` 之外注册卖家和管理员 Handler；所有 Handler 先解析会话，再把可信 actor 传给应用服务。写操作沿用现有请求去重机制。

主要新增请求组包括：

- 本人申请的查询、保存草稿和提交；
- 本人店铺查询与资料更新；
- 本人商品查询、创建、编辑和状态变更；
- 本人店铺订单查询；
- 管理员申请列表、详情与审批；
- 管理员店铺列表、停用和恢复；
- 管理员指定店铺商品查询、创建、编辑和状态变更。

管理员校验改为基于当前会话的 Shop 授权：读取现有 `UserView` 的管理员角色后才调用管理服务。Shop 不修改 User 管理实现，也不依赖客户端传入管理员标志。

## 9. 服务、仓储与数据库

复用现有 `SellerApplicationService`、`SellerService`、`ProductService` 和 `ShopAdminService`，补齐会话授权、查询模型和缺失操作。数据库在 Shop 范围内扩展申请说明/经营计划、拒绝原因、停用原因、规范化店名、提交/审批时间和版本字段；仓储增加：

- 按当前用户读取唯一申请和唯一店铺；
- 按状态分页读取申请；
- 按规范化名称检查有效占用；
- 管理员分页读取店铺；
- 读取商品的 SKU 数量、总库存、已预留和最低价；
- 按店铺和规范化商品名称检查商品类型唯一性；
- 按店铺读取卖家订单及明细。

`tblProduct` 增加可空的封面图片 URL 字段。服务端在商品创建与编辑时完成 URL 语法、协议、凭据和长度校验，数据库只保存 URL 文本。店铺停用、商品上下架、库存调整和审批均在 Shop 事务内完成。商品查询以 `productId` 为一项进行分组，SKU 只参与关键词匹配、最低价格、总库存和销量聚合，不产生重复商品。买家商品查询统一限定启用店铺、上架商品和至少一个可售 SKU；订单历史查询不因店铺或商品后来停用而丢失。

## 10. 错误、并发与审计

Shop 为以下情况提供稳定错误码和中文提示：身份无权操作、管理员尝试购买、店主尝试自购、申请状态冲突、重复店名、封面 URL 无效、过期版本、店铺已停用、库存低于已预留、库存不足和会话失效。会话失效沿用现有退出回调返回登录页。

查询页面继续使用请求序号隔离异步响应，较旧响应不能覆盖新筛选或新排序结果。所有表格加载、写操作和错误提示在 EDT 规则下更新 Swing 状态。

Shop 业务日志至少记录申请提交与审核、店铺资料修改、停用/恢复、商品创建与编辑、上下架、价格和库存变化；日志包含操作者、目标对象、结果和必要原因，不记录密码。

## 11. Demo 数据与账号

Demo 提供五家启用店铺和恰好 100 个通用商品类型：

| 店铺 | 分类 | 商品数 |
| --- | --- | ---: |
| 校园文具店 | 文具 | 10 |
| 校园书店 | 图书 | 30 |
| 校园生活超市 | 生活用品 | 45 |
| 校园药店 | 药品 | 5 |
| 校园综合店 | 其他 | 10 |
| 合计 |  | 100 |

100 的统计口径是 `tblProduct` 中的通用商品类型数量，不包含 `tblProductSku` 的规格数量。每个商品至少有一个 SKU，代表性商品配置多个颜色、尺寸、包装或版本 SKU；例如“中性笔”作为一个商品，黑色、蓝色和不同笔尖粗细作为其 SKU。Demo 商品配置确定性的 HTTPS 封面 URL，并保留分类默认图片以支持离线或图片源不可用的测试。商品覆盖不同价格、库存、已预留和销量，用于验证搜索、分页、排序、库存保护和卡片聚合。Demo 同时准备已拒绝申请和相互隔离的订单数据；待审核、已通过和店铺停用状态通过固定账号的人工流程及自动化测试夹具验证，保持五家启用店铺和 100 个可浏览商品类型的初始状态。

固定账号为：

## 12. 验证与验收

实现按红—绿—重构推进。测试覆盖：

- Common DTO 序列化、防御性复制和版本字段；
- 学生/教师保存、提交、拒绝后修改重提和审批自动建店；
- 单人单申请/单店、规范化店名唯一性和并发版本冲突；
- 店主只能管理自己的店铺和商品，卖家订单按店铺隔离；
- 店主自购、管理员购买和管理员申请均被服务端拒绝；
- 管理员审批、拒绝原因、停用/恢复和跨店商品管理；
- 停用店铺隐藏、库存不低于已预留、上架条件和软下架；
- 支付结果到“我的”的安全返回路径；
