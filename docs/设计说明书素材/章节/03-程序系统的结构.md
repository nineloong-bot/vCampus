# 3 程序系统的结构

## 3.1 系统总体结构

虚拟校园系统采用 C/S 架构，由两个可独立运行的程序和一个单文件数据库组成：

- **客户端（`vCampusClient.jar`）**：Java Swing 桌面程序，负责界面呈现、输入校验、会话缓存与网络
  请求封装。客户端不直接访问数据库。
- **服务器端（`vCampusServer.jar`）**：独立 Java 进程，负责 Socket 接入、会话与权限校验、业务
  处理、并发控制与数据库读写。
- **数据库（`vCampus.accdb`）**：Access 单文件数据库，由服务器端通过 UCanAccess JDBC 独占访问。

![图 3-1 vCampus 虚拟校园系统总体架构](图/fig-3-1-总体架构.png)

客户端与服务器端之间使用 TCP 长连接传输可序列化的 `Message` 对象。一次完整的请求／响应经过如下
层次：客户端页面调用模块客户端服务 → 封装 `Message` → 客户端通信层通过对象流写出 → 服务器端
接收线程读取 → 消息路由器按命令名找到处理器 → 处理器鉴权并调用业务服务 → 业务服务通过仓储
访问数据库 → 结果逐层包装为 `ResponseBody` 返回客户端。客户端连接双方各只创建一次
`ObjectOutputStream` 与 `ObjectInputStream`，并且必须先创建输出流并 `flush()` 之后再创建输入流。

## 3.2 功能模块结构

系统按业务划分为五个必做模块，每个模块由一名成员端到端负责（界面、客户端服务、请求处理器、
业务服务、仓储、数据库表、测试与文档）。公共模块、网络模块、多线程模块与数据库贯穿全部业务
模块，由项目组共同维护。

## 3.3 工程结构

工程为 Maven 聚合多模块结构，父 POM 位于仓库根，基础包名为 `edu.seu.vcampus`。

| 序号 | 模块 | 内容 |
| --- | --- | --- |
| 1 | `vcampus-common` | 公共协议、各模块 DTO 与值对象、错误码与通用校验。不依赖 Swing、JDBC 或服务端实现 |
| 2 | `vcampus-client` | Swing 页面、会话、导航、网络连接与五个模块的客户端服务 |
| 3 | `vcampus-server` | 启动、网络、会话、权限、路由、并发、事务、持久化与五个模块的服务端实现 |
| 4 | `vcampus-database` | Access 数据库结构脚本（`schema/`）、初始化数据脚本（`seed/`）与批量测试数据工具 |
| 5 | `vcampus-distribution` | 可运行 JAR、配置、数据库、Windows/macOS/Linux 启动脚本与发行文档 |

## 3.4 客户端逻辑分层

客户端按"视图层 → 应用服务层 → 通信层"三层组织，对应课程要求的 `view` 与 `biz/srv` 划分：

| 层次 | 职责 | 典型类 |
| --- | --- | --- |
| 视图层（view） | 界面呈现与用户交互；只调用客户端服务，不感知网络细节 | `LoginFrame`、`MainFrame`、`StudentSearchPanel`、`OfferingSearchPanel`、`BookSearchPanel`、`ShopModulePanel` |
| 应用服务层（biz/srv） | 把界面操作转换为命令请求，缓存会话数据，提供异步结果 | `UserClientService`、`StudentClientService`、`CourseClientService`、`LibraryClientService`、商城各客户端端口 |
| 通信层 | 建立并维护 Socket 连接，发送 `Message`，按 `requestId` 匹配响应，维护连接状态 | `ClientConnection`、`PendingRequests`、`ConnectionState` |

客户端的公共能力由 `core.ui.shell` 与 `core.ui.theme` 提供：`MainFrame` 使用 `CardLayout` 承载
各模块页面，顶部 `IdentityHeader` 显示当前用户与角色，左侧 `PermissionNavigation` 按登录返回的
权限集合显示导航项，底部 `ApplicationStatusBar` 显示连接状态与操作结果。页面切换统一通过
`PageNavigator` 完成。

客户端不直接访问数据库，也不持有跨进程共享状态；登录成功后仅在本进程内存中保存服务端下发的
会话令牌，退出登录或关闭主界面时清理会话并关闭共享连接。

## 3.5 服务器端逻辑分层

服务器端按"网络接入层 → 路由与安全层 → 业务服务层 → 数据访问层"四层组织：

| 层次 | 职责 | 典型类 |
| --- | --- | --- |
| 网络接入层 | 监听端口、接受连接、读取与写出 `Message` | `SocketServer`、`ClientConnection` |
| 路由与安全层 | 按命令名分发、解析请求体类型、校验会话与权限、请求幂等去重、异常到错误码的映射 | `MessageRouter`、各模块 `*Handlers`、`AuthorizationService`、`SessionRegistry`、`RequestDeduplicator` |
| 业务服务层 | 业务规则校验、事务边界、资源加锁、跨模块协作 | `UserServiceImpl`、`StudentServiceImpl`、`CourseServiceImpl`、`LibraryService` 系列、商城各服务 |
| 数据访问层 | 把领域语义转换为 SQL 并读写 Access | 各模块 `Access*Repository` |

服务端各业务模块内部统一遵循 `handler → service → repository` 的调用方向；跨模块调用只能通过
对方发布的 `Port` 接口完成，禁止直接读取其它模块的仓储或数据库表。

## 3.6 跨模块依赖与调用边界

| 调用方 | 被调用方 | 协作方式 |
| --- | --- | --- |
| 学籍管理 | 用户管理 | 通过 `UserAccountProvisioningPort` 在同一事务内创建学生账户 |
| 选课系统 | 学籍管理 | 通过 `StudentQueryPort` 查询学生选课资格与在读状态 |
| 选课系统 | 用户管理 | 通过统一会话快照完成鉴权 |
| 图书馆 | 用户管理 | 通过统一会话快照获取用户身份与角色 |
| 校园商城 | 用户管理 | 通过统一会话快照获取买家／店主身份 |

约束如下：

1. 学籍模块不依赖选课模块；新生录取由学籍模块的录取协调器在同一事务内按固定顺序加锁后调用
   用户模块的账户开通端口，任一步失败整体回滚且不消耗已分配的编号。
2. 用户模块不得自行提交、回滚或开启嵌套事务，事务边界统一由调用方持有。
3. 需要组合多个模块数据的页面，由上层查询协调器分别调用各模块后组装 DTO，不在数据库层做跨模块
   联表。
4. 涉及多模块写入的操作（如注销账户）只能通过专门的协调服务执行，并显式声明完整的加锁顺序。
