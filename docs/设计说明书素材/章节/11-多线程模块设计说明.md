# 11 多线程模块设计说明

## 11.1 并发设计目标

系统必须支持多个客户端同时在线操作，并在高竞争场景下保证数据正确。并发设计的目标为：

1. **不超选**：多个学生竞争同一个教学班的最后一个名额时，最多只能有一人成功；
2. **不超卖**：商城有限库存不得被超卖，同一图书副本不得同时借给两人；
3. **编号唯一**：并发录取必须产生唯一且连续的一卡通号与学号，回滚不得消耗编号；
4. **不脏读**：任一写操作要么整体成功，要么整体回滚，不得留下半完成状态；
5. **不阻塞界面**：客户端的网络等待不得阻塞 Swing 事件分发线程。

## 11.2 服务端并发模型

![图 11-1 服务端并发模型与线程结构](图/fig-11-1-并发模型.png)

服务端采用"单接收线程 + 有界工作线程池 + 资源锁 + 串行事务"的并发模型：

1. `ServerSocket` 在调用线程上运行接受循环，积压队列长度为 50；
2. 每接受一条连接，就作为一个任务提交给 `ThreadPoolExecutor`；任务执行期间独占一个工作线程，
   在该连接上循环读取并处理请求，直到连接关闭；
3. 线程池的核心线程数与最大线程数相同（`server.workerThreads`），任务队列是容量为
   `server.maxConnections` 的 `ArrayBlockingQueue`；线程池与队列均已满时，接收线程直接回送
   `COMMON_SERVER_BUSY` 并关闭该连接，实现快速失败而不是无限排队；
4. 每个连接持有一把连接级互斥锁，保护该连接的对象输出流；
5. 业务层使用 `StripedResourceLockManager`（256 条带）提供以资源键为粒度的互斥；
6. 所有数据库事务经 `TransactionManager.inTransaction()` 执行，方法为 `synchronized`，
   因此事务提交在进程内全局串行，配合 `rowVersion` 乐观锁与数据库唯一索引共同保证一致性。

## 11.3 线程与队列配置

| 序号 | 配置项 | 默认值 | 说明 |
| --- | --- | --- | --- |
| 1 | `server.port` | `8888` | 服务监听端口 |
| 2 | `server.workerThreads` | `8` | 工作线程数（同时处理的连接数上限） |
| 3 | `server.maxConnections` | `100` | 任务队列容量，同时也是允许挂起的最大连接数 |
| 4 | `session.timeoutMinutes` | `30` | 会话空闲超时 |
| 5 | `inventory.reservationMinutes` | `15` | 商城库存预留有效时长 |
| 6 | `dedup.retentionHours` | `24` | 请求幂等记录保留时长 |
| 7 | `ServerSocket` 积压队列 | `50` | 已完成三次握手但尚未被 `accept()` 的连接数 |

### 11.3.1 客户端线程结构

| 序号 | 线程 | 职责 |
| --- | --- | --- |
| 1 | EDT（事件分发线程） | 执行全部 Swing 组件创建与更新；不得进行网络等待或数据库访问 |
| 2 | 响应读取线程 | `ClientConnection` 内部的单线程执行器，阻塞在 `readObject()` 上接收响应 |
| 3 | 超时调度线程 | `ClientConnection` 内部的单线程调度器，负责请求超时与定时清理 |

## 11.4 连接级写锁

同一个 `ObjectOutputStream` 不是线程安全的。若两个业务线程同时向同一连接写入对象，会破坏流的
内容结构，导致对端反序列化失败。因此在以下两处均使用连接级互斥锁：

- **服务器端**：`ClientConnection.send(Message)` 在写锁内完成 `writeObject`、`flush` 与 `reset`；
- **客户端**：`ClientConnection.write(Message)` 使用 `ReentrantLock` 保护写入。

写入后调用 `reset()` 清空对象流的句柄缓存，避免长连接下因缓存已发送对象而产生内存持续增长。

## 11.5 资源锁管理器

`edu.seu.vcampus.server.concurrency` 提供以业务资源为粒度的逻辑锁。

| 序号 | 类型 | 说明 |
| --- | --- | --- |
| 1 | `ResourceKey(resourceType, resourceId)` | 资源键，由资源类型与资源标识组成 |
| 2 | `ResourceLockManager` | 锁管理接口，提供 `withLock(type, id, action)` 与 `withLocks(sortedKeys, action)` |
| 3 | `StripedResourceLockManager` | 实现类，使用 256 条带的锁，把资源键散列到固定数量的锁上，避免为每个资源创建对象 |

### 11.5.1 各模块资源键

| 序号 | 模块 | 资源键 |
| --- | --- | --- |
| 1 | 用户 | `LOGIN_ID:<规范化登录名>`、`USER:<userId>`、`SESSION:<sessionToken>`、`ADMIN:ACTIVE` |
| 2 | 学籍 | `NUMBER_SEQUENCE:CAMPUS_CARD_GLOBAL`、`NUMBER_SEQUENCE:STUDENT_NUMBER:<专业>:<年>:<班>`、`STUDENT:<studentId>` |
| 3 | 选课 | `STUDENT:<studentId>`、`OFFERING:<offeringId>` |
| 4 | 图书馆 | `LIBRARY_USER:<userId>`、`BOOK_COPY:<copyId>`、`LOAN:<loanId>` |
| 5 | 商城 | `SELLER_APPLICATION:<applicationId>`、`PAYMENT:<paymentId>`、`ORDER_GROUP:<orderGroupId>`、`PRODUCT:<productId>`、`SKU:<skuId>`、`CART:<userId>` |
| 6 | 公共 | `REQUEST:<requestId>`（请求幂等去重） |

### 11.5.2 加锁顺序规则

1. 涉及多资源加锁的操作必须使用 `withLocks` 并按固定顺序加锁，禁止嵌套 `withLock` 造成不一致的
   获取顺序；
2. 单资源操作使用 `withLock`；
3. 同一资源集不得在不同操作中以相反顺序加锁，否则会产生死锁；
4. 跨模块协调器必须在设计文档中显式列出完整的加锁顺序；未公布顺序的资源集按
   `resourceType + resourceId` 字典序排序后加锁。

典型固定顺序：

- **新生录取（学籍 ↔ 用户）**：`NUMBER_SEQUENCE:CAMPUS_CARD_GLOBAL` →
  `NUMBER_SEQUENCE:STUDENT_NUMBER:<专业>:<年>:<班>` → `LOGIN_ID:<一卡通号>`；
- **手动建档**：`LOGIN_ID` → `STUDENT_NUMBER` → `ID_DOCUMENT`；
- **学生选课**：`STUDENT:<studentId>` → `OFFERING:<offeringId>`；
- **图书借还**：`LIBRARY_USER:<userId>` → `BOOK_COPY:<copyId>` → `LOAN:<loanId>`；
- **商城结算**：`PAYMENT:<paymentId>` → `ORDER_GROUP:<orderGroupId>` → 按 `skuId` 排序的
  `SKU:<skuId>` 序列。

## 11.6 事务与并发控制

系统同时使用三种机制保证并发正确性：

| 序号 | 机制 | 说明 | 典型场景 |
| --- | --- | --- | --- |
| 1 | 资源锁 | 以业务资源为粒度互斥，把并发请求串行化到关键区 | 选课、借书、结算、录取取号 |
| 2 | 数据库事务 | `TransactionManager.inTransaction()` 在成功时提交、失败时回滚；方法为 `synchronized`，事务在进程内串行执行 | 所有写操作 |
| 3 | 乐观锁 | 可变业务表带 `rowVersion` 字段，更新时以旧版本号为条件，影响行数为 0 则抛出并发修改异常并返回 `COMMON_CONCURRENT_MODIFICATION` | 学籍修改、教学班更新、库存扣减 |
| 4 | 唯一约束 | 由数据库唯一索引兜底，防止重复数据 | 选课 `(studentId, offeringId)`、学号、一卡通号、ISBN、订单号 |
| 5 | 条件更新 | 库存扣减使用带条件的 `UPDATE`（要求剩余库存足够），把校验与扣减合并为一条原子语句 | 商城库存扣减 |

并发场景下的典型保证：

- **课程名额**：在 `OFFERING:<offeringId>` 锁内校验 `enrolledCount < capacity` 后自增，
  20 人竞争最后一个名额时只有 1 人成功，其余返回 `COURSE_OFFERING_FULL`；
- **图书副本**：在 `BOOK_COPY:<copyId>` 锁内校验副本状态为可借后写入借阅记录，
  同一副本只能有一人借出成功；
- **商品库存**：结算时创建库存预留，扣减使用条件更新，有限库存不会超卖；
- **编号分配**：在序列资源锁内读取并自增 `tblNumberSequence.currentValue`，
  事务回滚时序列值一并回滚，不消耗编号。

## 11.7 客户端多线程

| 序号 | 规则 | 说明 |
| --- | --- | --- |
| 1 | 不在 EDT 上等待网络 | 页面调用客户端服务后立即返回 `CompletableFuture`，不得调用 `get()` 阻塞 |
| 2 | 用 `SwingUtilities.invokeLater` 更新控件 | 未来完成后必须切回 EDT 再刷新界面 |
| 3 | 提交期间禁用按钮 | 防止用户重复点击产生重复请求 |
| 4 | 失败保留用户输入 | 请求失败时不清空表单，便于用户修正后重试 |
| 5 | 并发冲突提示刷新 | 收到 `COMMON_CONCURRENT_MODIFICATION` 时提示数据已被他人修改，引导刷新 |
| 6 | 页面状态完整 | 每个查询页面实现加载、正常、空结果、错误与断线五种状态 |

客户端主程序在 EDT 上启动：

```java
public static void main(String[] args) {
    SwingUtilities.invokeLater(() -> new MainFrame(title).setVisible(true));
}
```

## 11.8 定时与后台任务

| 序号 | 任务 | 所在位置 | 职责 |
| --- | --- | --- | --- |
| 1 | 请求超时 | 客户端 `PendingRequests` 的调度线程 | 到期后以 `TimeoutException` 完成对应未来 |
| 2 | 会话空闲过期 | 服务端 `SessionRegistry` | 每次访问刷新空闲计时，超过 `session.timeoutMinutes` 的会话在下次访问时判定失效并移除 |
| 3 | 库存预留释放 | 商城服务端 | 支付超时（默认 15 分钟）的预留记录置为 `RELEASED` 并回滚库存，订单置为 `CANCELLED` |
| 4 | 逾期借阅判定 | 图书馆服务端 | 借阅记录按应还日期动态判定逾期并计算罚金阶梯，不依赖额外的状态写任务 |
| 5 | 幂等记录清理 | 服务端 | `tblRequestDedup` 中超过 `dedup.retentionHours`（默认 24 小时）的记录可清理 |
