## 1. 模块背景

学籍管理模块是虚拟校园系统的核心业务模块，负责维护院系、专业、班级三级组织结构，学生档案与联系方式，学籍状态流转，以及学生唯一身份编号（一卡通号、学号）的分配。模块在管理员录取新生时于**单一数据库事务**内原子完成编号分配、学生登录账户创建（跨模块调用用户模块）、学生档案写入、学籍变更审计与请求幂等结果落库，任一步失败必须整体回滚且不消耗编号。一卡通号同时是学生的登录标识，但其账户、密码与会话仍由用户模块维护，学籍模块只在 `tblStudent` 中保存 `userId` 与学号，一卡通号以用户模块 `tblUser.loginId` 为唯一权威值，不重复存储。模块向选课模块仅暴露只读的 `StudentQueryPort` 资格查询入口，自身**从不依赖选课模块**；不维护课程、选课记录与成绩。学生可通过"暂存—提交—管理员审核"的闭环自助维护个人基本资料与就读方式，管理员可审核申请、导出正式档案 PDF，也可在组织树上执行"新增学院 / 新增专业 / 新增班级 / 新增学生"的手动逐级建档。

## 2. 需求分析

### 2.1 功能点清单

| 编号 | 功能点 | 需求说明 | 涉及命令 |
|---|---|---|---|
| F-01 | 院系管理 | 维护院系代码（唯一）、名称、启用状态；停用前须确认无仍启用的下级组织 | `STUDENT_SAVE_DEPARTMENT` |
| F-02 | 专业管理 | 维护专业的三字符专业代码（`^[0-9A-Z]{3}$`，如 `090`、`09J`）、名称、所属院系、启用状态 | `STUDENT_SAVE_MAJOR` |
| F-03 | 班级管理 | 维护班级代码、名称、四位入学年份（2000–2099）、班号（1–9，同专业同年级内唯一）、启用状态 | `STUDENT_SAVE_CLASS` |
| F-04 | 组织查询 | 按层级列出院系 / 专业 / 班级，供组织树、录取、审核等页面使用 | `STUDENT_LIST_DEPARTMENTS`、`STUDENT_LIST_MAJORS`、`STUDENT_LIST_CLASSES` |
| F-05 | 学生录取建档（自动） | 管理员选定学生类型、专业、年级、班级与基本信息，系统自动生成一卡通号与学号并原子建档 | `STUDENT_CREATE` |
| F-06 | 学生录取建档（手动） | 管理员手工输入一卡通号、学号、证件信息，在同一事务内建立账户与档案；不触碰自动编号序列 | `STUDENT_CREATE_MANUAL` |
| F-07 | 一卡通号生成 | 9 位、全局统一顺序、跨学生类型与入学年份共享、永不重置 | 由 `CampusCardNumberGenerator` 在录取事务内实现 |
| F-08 | 学号生成 | 8 位、按"专业代码 + 入学年份 + 班号"分组、每班独立从 `01` 起 | 由 `StudentNumberGenerator` 在录取事务内实现 |
| F-09 | 学籍查询 | 本人查询（含一卡通号、学号、档案与联系方式）；教师/管理员按关键字、组织、状态分页查询只读摘要 | `STUDENT_GET_CURRENT`、`STUDENT_GET`、`STUDENT_SEARCH` |
| F-10 | 学籍信息修改 | 修改本人联系方式；管理员转班、变更学籍状态、修改学籍核心字段与全部学籍字段 | `STUDENT_UPDATE_CONTACT`、`STUDENT_UPDATE_ENROLLMENT`、`STUDENT_CHANGE_STATUS`、`STUDENT_UPDATE_INFO`、`STUDENT_UPDATE_ACADEMIC` |
| F-11 | 学籍异动 | 转班生成新学号并记录 `CLASS_CHANGE`；状态变更按状态机校验并记录 `STATUS_CHANGE`；学籍字段修改记录 `ACADEMIC_CHANGE` | 同 F-10 |
| F-12 | 学籍变更历史 | 管理员查看某学生的不可变更审计记录；教师不可见 | `STUDENT_GET_CHANGES` |
| F-13 | 个人信息核对与暂存 | 学生查看正式档案工作区，按分区暂存个人基本信息与就读方式草稿（不写正式表） | `STUDENT_PROFILE_GET_WORKSPACE`、`STUDENT_PROFILE_SAVE_PERSONAL_DRAFT`、`STUDENT_PROFILE_SAVE_ATTENDANCE_DRAFT` |
| F-14 | 个人信息提交与撤回 | 提交草稿进入待审；待审期间可撤回为草稿并继续编辑 | `STUDENT_PROFILE_SUBMIT`、`STUDENT_PROFILE_WITHDRAW` |
| F-15 | 资料审核 | 管理员查询待审列表、查看"正式值 → 申请值"差异、通过或填写原因驳回 | `STUDENT_PROFILE_REVIEW_LIST`、`STUDENT_PROFILE_REVIEW_GET`、`STUDENT_PROFILE_APPROVE`、`STUDENT_PROFILE_REJECT` |
| F-16 | 正式档案读取 | 管理员读取指定学生的完整正式档案（个人 + 学籍分区） | `STUDENT_GET_PROFILE` |
| F-17 | PDF 导出 | 服务端用**正式档案**生成 A4 中文《学生基本信息表》PDF，客户端保存到用户选定位置 | `STUDENT_PROFILE_EXPORT_PDF` |
| F-18 | 字段校验 | 共享校验器 `StudentFieldValidator` 提供即时与权威双层校验，客户端悬停格式提示 | 无独立命令，贯穿手工建档与资料暂存 |
| F-19 | 选课资格查询 | 向选课模块暴露 `StudentQueryPort`（身份、资格、在职学生判定），不返回联系方式 | 模块内 Port 调用 |
| F-20 | 幂等与并发控制 | 所有写命令以全局唯一 `requestId` 去重；组织、编号、档案更新使用资源锁 + `rowVersion` 乐观锁 | 贯穿全部写命令 |

### 2.2 角色权限（来自模块设计文档第 2 节）

| 用例 | 学生 | 教师 | 管理员 |
|---|---:|---:|---:|
| 查看本人档案和一卡通号 | 是 | 否 | 是 |
| 修改本人联系方式 | 是 | 否 | 是 |
| 查询学生只读摘要 | 否 | 是 | 是 |
| 录取新生、转班、变更状态 | 否 | 否 | 是 |
| 维护院系 / 专业 / 班级 | 否 | 否 | 是 |

教师查询只返回一卡通号、学号、姓名、班级、专业和学籍状态，**不返回**电话等非必要联系方式，也**不返回**学籍变更记录（`STUDENT_GET_CHANGES` 仅限管理员角色）。

### 2.3 学籍状态与学生类型

- 学籍状态 `StudentStatus`：`ACTIVE`、`SUSPENDED`、`GRADUATED`、`WITHDRAWN`；只有 `ACTIVE` 具备选课资格。
- 学生类型 `StudentType`：`UNDERGRADUATE`（一卡通类型位 `1`）、`MASTER`（`2`）、`DOCTORATE`（`3`）。
- 状态迁移（`StudentServiceImpl.validTransition`，源码实现）：
  - `ACTIVE → SUSPENDED | GRADUATED | WITHDRAWN`
  - `SUSPENDED → ACTIVE | WITHDRAWN`
  - `GRADUATED → （无）`、`WITHDRAWN → （无）`
- 已毕业、休学和退学档案保留历史，**不物理删除**。
- 学生类型建档后不得在普通页面直接修改；`STUDENT_UPDATE_ACADEMIC` 中如提交的学生类型与现状不同，会被记入 `ENROLLMENT_CHANGE` 审计。

## 4. 业务流程

### 4.1 新生录取建档流程（自动录取 `STUDENT_CREATE`）

实现类：`StudentAdmissionCoordinator`（实现 `StudentAdmissionService`）。

**参与方**：`RequestDeduplicator`、`TransactionManager`、`ResourceLockManager`、`OrganizationRepository`、`CampusCardNumberGenerator`（`AccessCampusCardNumberGenerator`）、`StudentNumberGenerator`（`AccessStudentNumberGenerator`）、用户模块 `UserAccountProvisioningPort`、`StudentRepository`、`StudentChangeRepository`。

**编号步骤：**

1. 以 `requestId` 调用 `deduplicator.replayCompleted(requestId)`；若已有完成记录，直接返回原 `StudentAdmissionResult`，**不再分配编号**。
2. 开启只读事务 1 调用 `validate`：按 `majorId` 查专业、按 `classId` 查班级、按专业 `departmentId` 查院系；任一不存在返回 `STUDENT_ORGANIZATION_MISMATCH`。
3. 校验三层组织启用状态（`department.active() && major.active() && studentClass.active()`），任一停用返回 `STUDENT_CLASS_INACTIVE`。
4. 校验 `classId` 所属专业等于 `majorId`，且班级 `enrollmentYear` 等于命令中的 `enrollmentYear`，否则返回 `STUDENT_ORGANIZATION_MISMATCH`。
5. 计算班级学号序列键：`STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>`（`YY` 为 `enrollmentYear % 100` 两位补零）。
6. **取得锁**（固定顺序）：`NUMBER_SEQUENCE:CAMPUS_CARD_GLOBAL` → `NUMBER_SEQUENCE:<上述班级序列键>`。
7. 持锁后**再次**检查 `requestId` 幂等（双检，避免锁等待期间被其他请求完成）。
8. 开启数据库事务 2（`transactions.inTransaction`）：
   1. 事务内第三次检查幂等 `deduplicator.replayCompleted(tx, requestId)`；
   2. 调用 `campusCards.next(tx, studentType, enrollmentYear)`：读 `CAMPUS_CARD_GLOBAL`，若 `currentValue >= maxValue` 抛 `STUDENT_CAMPUS_CARD_SEQUENCE_EXHAUSTED`；否则 `advance`（`currentValue+1`、`rowVersion+1`、更新 `updatedAt`）并格式化 `"2" + typeDigit + "3" + YY + %04d(序号)`；
   3. 调用 `studentNumbers.next(tx, majorCode, enrollmentYear, classNumber)`：`getOrCreate(key, 99)` 取得或插入班级序列，容量检查后 `advance` 并格式化 `PPP + YY + C + %02d(序号)`；专业代码规范化失败返回 `STUDENT_MAJOR_CODE_INVALID`，班号越界返回 `STUDENT_CLASS_NUMBER_INVALID`，年份越界返回 `STUDENT_ENROLLMENT_YEAR_INVALID`；
   4. 触发故障注入点 `AFTER_NUMBERS`（仅测试）；
   5. **取得第三层锁** `LOGIN_ID:<campusCard>`（一卡通号同时将作为登录标识，故以其为锁键）；
   6. **跨模块调用用户模块**：`accounts.createStudentAccount(tx, campusCard, "12345678".toCharArray())`，传递当前 `TransactionContext`，用户模块在**同一事务**内创建账户并返回 `userId`；用户模块不得自行提交、回滚或开启嵌套事务；
   7. 触发 `AFTER_ACCOUNT`；
   8. 构造 `Student` 记录（`studentId = UUID`、`studentStatus = ACTIVE`、`rowVersion = 0`、`enrollmentDate = 取录取事务当日（UTC 日期）`、`createdAt = updatedAt = now`），调用 `students.insert` 写入 `tblStudent`；邮箱与电话经 `blankToNull` 归一；
   9. 触发 `AFTER_PROFILE`；
   10. 调用 `changes.insertAdmission` 写入 `tblStudentChange`，`changeType = 'ADMISSION'`、`reason = '新生录取'`、`newValue = "studentNumber=<学号>;classId=<班级>"`、`oldValue = NULL`；
   11. 触发 `AFTER_AUDIT`；
   12. 由专业、院系、班级补全 `departmentName / majorName / className` 组装 `StudentView`，构造 `StudentAdmissionResult(view, campusCard, studentNumber, mustChangePassword = true)`；
   13. 在同一事务内调用 `deduplicator.storeCompleted(tx, requestMessage, ResponseBody.success(result))` 写入幂等完成记录；
   14. 触发 `AFTER_DEDUP`；
9. 事务提交后返回结果。客户端在成功页一次性显示一卡通号、学号与"初始密码为 12345678，请首次登录后修改"提示。

**锁顺序（全局固定，禁止反向获取）**：

```text
NUMBER_SEQUENCE:CAMPUS_CARD_GLOBAL
  → NUMBER_SEQUENCE:STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>
    → LOGIN_ID:<campusCardNumber>
```

**失败回滚**：上述事务 2 中任意一步抛出异常，`TransactionContext` 整体回滚，同时撤销**序列表更新、用户账户、学生档案、`ADMISSION` 审计记录、请求幂等完成状态**五类写入；已回滚的序号分配不视为成功占用，因此序列值随事务一起回滚，下次录取复用。`persist` 中非运行时异常统一包装为 `STUDENT_NUMBER_GENERATION_FAILED`，不向客户端泄露 SQL 异常；`StudentNumberingException` 的稳定错误码原样上抛。已进入事务的处理**不允许生成新 `requestId` 重试**。

**手动建档流程（`STUDENT_CREATE_MANUAL`，`createManual`）差异点：**

1. 先经 `StudentFieldValidator.normalizeManual` 规范化，再以 `validateManual(command, LocalDate.now(ZoneOffset.UTC))` 做权威校验；失败抛 `STUDENT_MANUAL_FIELD_INVALID`。
2. 检查幂等；**锁顺序**为 `LOGIN_ID:<campusCardNumber>` → `STUDENT_NUMBER:<studentNumber>` → `ID_DOCUMENT:<idDocumentNumber>`。
3. 持有锁后再次检查幂等，然后开启事务：事务内第三次检查幂等 → `validateManualOrganization` 由 `classId` 反查班级、专业、院系并要求三层均存在且启用（否则 `STUDENT_ORGANIZATION_MISMATCH` / `STUDENT_CLASS_INACTIVE`）→ 校验学号唯一（`STUDENT_NUMBER_DUPLICATE`）与证件号唯一（`STUDENT_ID_DOCUMENT_DUPLICATE`）。
4. 调用用户模块 `createStudentAccount(tx, campusCardNumber, "12345678")` 创建账户（一卡通号即登录标识）。
5. 触发 `AFTER_ACCOUNT` → `students.insertManual(...)` 写入学生核心档案与初始身份资料（邮箱、手机号为 `NULL`；学籍状态固定 `ACTIVE`）。
6. 触发 `AFTER_PROFILE` → 写 `tblStudentChange`，`changeType = 'MANUAL_CREATE'`、`reason = '管理员手动新增学生'`。
7. 触发 `AFTER_AUDIT` → 组装 `StudentAdmissionResult(..., mustChangePassword = true)` → 事务内写幂等完成记录 → 触发 `AFTER_DEDUP` → 提交。
8. 手动建档**不读取、不修改**一卡通号与学号自动序列，因此不影响后续自动录取的编号预期。

### 4.2 学籍信息变更流程

**(A) 联系方式修改 `STUDENT_UPDATE_CONTACT`**（`StudentServiceImpl.updateContact`）

1. Handler 校验：`principal.hasRole("ADMIN")` 或 `principal.userId().equals(student.userId())`，否则 `COMMON_FORBIDDEN`。
2. 经 `StudentWriteExecutor` 幂等包装后执行。
3. 加锁 `STUDENT:<studentId>`。
4. 事务内 `requireById` 确认学生存在（否则 `STUDENT_NOT_FOUND`）；`normalizeEmail` 校验邮箱格式（不匹配抛 `IllegalArgumentException` → `COMMON_INVALID_REQUEST`）；`blankToNull` 归一电话。
5. `students.updateContact(..., expectedVersion, now)` 带 `rowVersion` 条件更新；版本不匹配抛 `ConcurrentModificationException` → `COMMON_CONCURRENT_MODIFICATION`。
6. 返回最新 `StudentView`。本操作**不写** `tblStudentChange`。

**(B) 转班 `STUDENT_UPDATE_ENROLLMENT`**（`StudentServiceImpl.updateEnrollment`）

1. Handler `admin()` 校验：`ADMIN` 角色或 `STUDENT_WRITE` 权限；经写执行器幂等包装。
2. 只读事务查目标班级并要求启用，否则 `STUDENT_CLASS_INACTIVE`；再查其专业并要求启用。
3. 计算目标序列键 `STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>`。
4. **加锁**（顺序固定）：`NUMBER_SEQUENCE:<目标序列键>` → `STUDENT:<studentId>`。
5. 事务内 `requireById` 读取学生现状（含原班级、原学号）；调用 `AccessStudentNumberGenerator.next(...)` 在目标班级序列中分配**新学号**（容量不足返回 `STUDENT_CLASS_SEQUENCE_EXHAUSTED`）。
6. `students.updateEnrollment(...)` 更新 `classId` 与 `studentNumber`（带 `expectedVersion`）。
7. 写 `tblStudentChange`：`changeType = 'CLASS_CHANGE'`，`oldValue = "<原classId>:<原学号>"`，`newValue = "<新classId>:<新学号>"`，`reason` 必填（空则 `IllegalArgumentException`），`operatorUserId` 取会话真实用户。
8. 返回最新 `StudentView`。**一卡通号与 `tblUser.loginId` 不变**；转班不自动更改已生成的学号以外的任何身份标识。

**(C) 学籍状态变更 `STUDENT_CHANGE_STATUS`**（`StudentServiceImpl.changeStatus`）

1. Handler `admin()` 校验 + 幂等包装；命令的 `status`、`effectiveDate` 非空，`reason` 必填。
2. 加锁 `STUDENT:<studentId>`。
3. 事务内读取学生现状，按 `validTransition` 校验状态机；非法迁移返回 `STUDENT_STATUS_TRANSITION_INVALID`。
4. `students.updateStatus(...)` 带 `expectedVersion` 更新。
5. 写 `tblStudentChange`：`changeType = 'STATUS_CHANGE'`，`oldValue = 原状态名`，`newValue = 新状态名`。
6. 返回最新 `StudentView`。学籍变化与审计记录**同成同败**。

**(D) 学籍核心字段修改 `STUDENT_UPDATE_INFO`**（`StudentServiceImpl.updateStudentInfo`）

1. `admin()` 校验 + 幂等包装；`studentNumber` 经 `normalizeStudentNumber` 校验为 8 位数字，否则 `STUDENT_NUMBER_INVALID`；`classId`、`status`、`effectiveDate` 非空；`reason` 必填。
2. 加锁 `STUDENT:<studentId>`。
3. 事务内读取学生现状；查目标班级并允许"仍为原班级"这一特例（`value.active() || before.classId().equals(value.classId())`），否则 `STUDENT_CLASS_INACTIVE`；同样校验其专业。
4. 判定 `enrollmentChanged`（班级或学号变化）与 `statusChanged`；两者均为假时返回 `STUDENT_INFO_UNCHANGED`。
5. 若状态变化则先做状态机校验（`STUDENT_STATUS_TRANSITION_INVALID`）。
6. `students.updateAcademicInfo(...)` 一次更新班级、学号、状态（带 `expectedVersion`）。
7. 按需分别写入 `ENROLLMENT_CHANGE` 与 `STATUS_CHANGE` 审计记录（同一事务）。
8. 返回最新 `StudentView`。

**(E) 全部学籍字段修改 `STUDENT_UPDATE_ACADEMIC`**（`StudentServiceImpl.updateStudentAcademic`）

流程同 (D)，但更新 `tblStudent` 的班级、学号、学生类型、学籍状态、`enrolled`、`onCampus`、`campus`、`educationLevel`、`trainingMode`、`programLengthYears`、`attendanceMode`、`degreeName`、`educationName`、`expectedGraduationDate`、`graduationDate`、`studentSource`、`graduateStudyMode`、`counselorName`、`counselorContact` 等字段；审计策略为：班级 / 学号 / 学生类型变化写 `ENROLLMENT_CHANGE`，状态变化写 `STATUS_CHANGE`，若二者均未变化则写一条 `ACADEMIC_CHANGE`（`newValue = "学籍字段修改"`），保证任何正式学籍写入都留有审计。

### 4.3 个人信息申请与审核流程

**状态机**：`DRAFT`（草稿）→ `PENDING`（待审）→ `APPROVED`（通过）/ `REJECTED`（驳回）；`PENDING` 可 `withdraw` 回到 `DRAFT`。每名学生**最多存在一条未结束申请**（`DRAFT` 或 `PENDING`），Access 不使用条件唯一索引，由服务端在 `STUDENT:<studentId>` 资源锁与同一事务中查询并强制。所有编辑类命令的学生目标**只能从会话获取**，不接受客户端传入 `studentId`。

**(1) 读取工作区 `STUDENT_PROFILE_GET_WORKSPACE`**
   - 从会话取 `userId`，事务内 `students.findByUserId` 定位学生（否则 `STUDENT_NOT_FOUND`）；
   - 用 `UserQueryPort.findByUserId(...).loginId()` 取一卡通号，组装正式档案 `StudentProfileData`；
   - 读取当前开放申请（`DRAFT`/`PENDING`）或最近一条申请，返回 `StudentProfileWorkspace(formalProfile, application)`。

**(2) 暂存个人基本信息 `STUDENT_PROFILE_SAVE_PERSONAL_DRAFT`**
   1. 对 `personal` 快照先做一次 `StudentFieldValidator.validatePersonal(personal, LocalDate.now())`，失败抛 `STUDENT_PROFILE_FIELD_INVALID`（消息为首个错误字段说明）。
   2. 事务内由 `userId` 定位 `studentId`。
   3. **加锁** `STUDENT:<studentId>`。
   4. 事务内读取正式档案与 `applications.findOpen`：
      - 若开放申请为 `PENDING` → 抛 `STUDENT_PROFILE_PENDING`（"资料申请正在审核，暂不可编辑"）；
      - 若不存在开放申请 → 以正式档案的个人分区与就读方式为基线；
      - 否则以开放申请快照为基线。
   5. 校验传入的 `expectedApplicationVersion`：新建草稿时必须为 `0`，否则 `ConcurrentModificationException`（→ `COMMON_CONCURRENT_MODIFICATION`）。
   6. 以正式档案当前 `rowVersion` 作为 `baseStudentVersion`，`applicationVersion = 1`，`status = DRAFT`，插入 `tblStudentProfileApplication`（首次保存）；已存在 `DRAFT` 时执行 `updatePersonal`，SQL 条件为 `applicationId=? AND applicationStatus='DRAFT' AND applicationVersion=?`，并 `applicationVersion = applicationVersion + 1`。
   7. 二次调用 `validatePersonal(changed.personal(), now, formal.core().enrollmentDate())` 做含入学年龄规则的权威校验。
   8. 返回最新 `StudentProfileWorkspace`。**本命令不修改 `tblStudent`。**

**(3) 暂存就读方式 `STUDENT_PROFILE_SAVE_ATTENDANCE_DRAFT`**
   - 流程同上，但只更新 `attendanceMode`（`updateAttendance`，同样 `DRAFT` + 版本条件 + `applicationVersion+1`），不重新校验个人分区。
   - `AttendanceMode` 枚举：`DAY_STUDENT`（走读）、`RESIDENT`（住校）、`LODGING`（借宿）、`OTHER`（其他）。

**(4) 提交审核 `STUDENT_PROFILE_SUBMIT`**
   1. 定位 `studentId`，加锁 `STUDENT:<studentId>`。
   2. 事务内读取正式档案与开放申请；无开放申请 → `STUDENT_PROFILE_DRAFT_NOT_FOUND`（"没有可提交的暂存资料"）。
   3. 申请状态必须为 `DRAFT`，否则 `STUDENT_PROFILE_PENDING`。
   4. `baseStudentVersion` 必须等于正式档案当前 `rowVersion`，否则 `ConcurrentModificationException`（→ `COMMON_CONCURRENT_MODIFICATION`，客户端要求刷新）。
   5. 比较正式值与申请值（`sameEditableValues`：个人分区 `equals` 且就读方式相同）；无实际改动 → `STUDENT_PROFILE_NO_CHANGES`（保持草稿）。
   6. `applications.submit(...)`：`applicationStatus='PENDING'`、写入 `submittedAt`、`applicationVersion+1`，SQL 条件为 `applicationStatus='DRAFT' AND applicationVersion=?`。
   7. 返回最新 `StudentProfileWorkspace`；提交后申请被锁定，学生不可再编辑，直至管理员通过、驳回，或学生撤回。

**(5) 撤回申请 `STUDENT_PROFILE_WITHDRAW`**
   1. 定位 `studentId`，加锁 `STUDENT:<studentId>`。
   2. 事务内 `findOpen` 并过滤 `PENDING`，否则 `STUDENT_PROFILE_NOT_PENDING`（"当前没有可撤回的待审申请"）。
   3. `applications.withdraw(...)`：`applicationStatus='DRAFT'`、清空 `submittedAt`、`applicationVersion+1`，保留个人资料与就读方式快照，SQL 条件为 `applicationStatus='PENDING' AND applicationVersion=?`；版本冲突 → `ConcurrentModificationException`。
   4. 撤回与管理员通过 / 驳回使用**同一学生资源锁**，因此只有一方能先生效；若管理员已处理，撤回返回错误并刷新页面，不重新打开已关闭申请。
   5. 返回最新 `StudentProfileWorkspace`。

**(6) 管理员查询待审列表 `STUDENT_PROFILE_REVIEW_LIST`**
   - `admin()` 校验；校验分页参数（`page >= 1`、`1 <= pageSize <= 100`，否则 `IllegalArgumentException`）；
   - 事务内 `applications.listPending` 取全部 `PENDING`（按 `submittedAt` 升序），在内存分页后返回 `PageResult`。

**(7) 管理员读取差异详情 `STUDENT_PROFILE_REVIEW_GET`**
   - `admin()` 校验；按 `applicationId` 查申请（不存在 → `STUDENT_PROFILE_APPLICATION_NOT_FOUND`），再用申请的 `studentId` 读正式档案，返回 `StudentProfileWorkspace` 供客户端并排展示"正式值 → 申请值"。

**(8) 管理员通过 `STUDENT_PROFILE_APPROVE`** —— 在 `STUDENT:<studentId>` 锁与**单一数据库事务**内完成：
   1. 先无损读取申请的 `studentId`（否则 `STUDENT_PROFILE_APPLICATION_NOT_FOUND`）。
   2. 加锁 `STUDENT:<studentId>`。
   3. 重新读取申请并要求状态为 `PENDING`，否则 `STUDENT_PROFILE_NOT_PENDING`（"资料申请已处理"）。重新读取正式档案。
   4. 校验 `student.rowVersion() == pending.baseStudentVersion()`，不等则 `ConcurrentModificationException`（拒绝审核并要求重新查看差异）。
   5. `students.applyApprovedProfile(connection, pending, now)`：将申请快照写入正式档案并增加正式 `rowVersion`。
   6. `applications.markApproved(...)`：`applicationStatus='APPROVED'`、写入 `reviewerUserId`、`reviewedAt`、`reviewComment`（可空）、`applicationVersion+1`。
   7. `changes.insertChange(...)` 写入不可变更的 `PROFILE_CHANGE` 记录：`oldValue = "version=<baseStudentVersion>"`、`newValue = "application=<applicationId>"`、`reason = "学生资料审核通过"`、操作人为会话中的真实审核人。
   8. 任一步失败整体回滚；成功返回最新申请视图。

**(9) 管理员驳回 `STUDENT_PROFILE_REJECT`**
   - `reviewComment` 为空或全空白 → `IllegalArgumentException`（"驳回原因不能为空"）；
   - 其余流程同 (8)，但只执行 `applications.markRejected(...)`（状态 `REJECTED`、去空白后的原因、审核人、审核时间），**不修改正式档案**，也不写 `PROFILE_CHANGE`。

**(10) 导出 PDF `STUDENT_PROFILE_EXPORT_PDF`**
   - Handler 要求 `STUDENT` 角色；取工作区的 `formalProfile()`（正式档案）与 `Instant.now()` 调用 `StudentProfilePdfGenerator.generate`；
   - `StudentProfilePdfService` 基于 PDFBox 生成 A4 纵向文档，嵌入可分发中文字体，包含学校/系统标识、"学生基本信息表"标题、生成时间、学号、一卡通号、个人基本信息表、学籍信息表、页码与"数据以系统正式档案为准"说明；
   - 返回 `PdfDocument(filename, content)`，默认文件名 `学籍基本信息_<学号>_<姓名>.pdf`（服务端净化），客户端用保存文件选择器写入用户选定位置；
   - **草稿、待审核值与驳回值不得进入文件**；本地取消保存不视为错误；生成或写入失败不得改变档案与申请状态。

## 5. 类分析

### 5.1 实体类 / 领域模型（`vcampus-server/.../server/student/domain`）

| 类 | 说明 | 关键约束 |
|---|---|---|
| `Department` | 院系元数据 record | `departmentId`、`departmentCode`、`departmentName` 非空白；`rowVersion >= 0` |
| `Major` | 专业元数据 record，携带学号前缀 | `majorCode` 写入前 `toUpperCase`，必须匹配 `^[0-9A-Z]{3}$`；其余同 `Department` |
| `StudentClass` | 专业与入学年份下的班级 record | `enrollmentYear` 限定 `2000–2099`；`classNumber` 限定 `1–9`；文本字段非空白 |
| `Student` | 学生档案持久化模型 record | 注意：**一卡通号不在其中**，由用户模块持有 |
| `NumberSequence` | 一条编号序列的持久状态 record | `sequenceKey` 非空白；`0 <= currentValue <= maxValue` 且 `maxValue >= 1`；`incremented()` 同时 +1 序号与版本 |

## 8. 学生编号规范表

### 8.1 一卡通号

固定 9 位数字，格式 `2T3YYNNNN`，校验表达式 `^2[123]3[0-9]{6}$`。

| 位置 | 长度 | 含义 | 规则 |
|---|---:|---|---|
| `2` | 1 | 固定首位 | 必须为 `2` |
| `T` | 1 | 学生类型 | `1` 本科生、`2` 硕士生、`3` 博士生（对应 `StudentType.digit()`） |
| `3` | 1 | 固定第三位 | 必须为 `3` |
| `YY` | 2 | 入学年份 | 四位年份的后两位，支持 2000–2099（`enrollmentYear % 100`，两位补零） |
| `NNNN` | 4 | 录取顺序号 | 全校统一连续序号，`0001–9999`，左侧补零 |

示例：`213242478` = 本科生、2024 级、全局录取顺序 2478。
关键性质：全局顺序在**本科、硕士、博士以及不同入学年份之间共用**，不按类型或年份重置；成功提交的一卡通号永久占用，不得回收或复用；一卡通号同时是学生登录标识（`tblUser.loginId`），账户、密码、会话由用户模块维护。

### 8.2 学号

固定 8 个字符，格式 `PPPYYCSS`，校验表达式 `^[0-9A-Z]{3}[0-9]{5}$`。

| 位置 | 长度 | 含义 | 规则 |
|---|---:|---|---|
| `PPP` | 3 | 专业代码 | 三个大写字母或数字，匹配 `^[0-9A-Z]{3}$`（普通计算机 `090`，计算机拔尖班 `09J`） |
| `YY` | 2 | 入学年份 | 四位年份的后两位，支持 2000–2099 |
| `C` | 1 | 班号 | `1–9`，同专业、同年级内唯一 |
| `SS` | 2 | 班内顺序号 | 每个"专业 + 年级 + 班级"独立从 `01` 到 `99` |

示例：`09024110` = 专业 `090`、2024 级、1 班、班内 10 号；`09J24110` = 专业 `09J` 的对应学生。
关键性质：学号序列按 `专业代码 + 入学年份 + 班号` 分组（序列键 `STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>`），每班从 `01` 开始；成功提交的学号永久占用，不得回收或复用；转班不自动更改已生成的学号以外的标识，且任何操作都不得修改一卡通号、`tblUser.loginId` 或学生登录方式。

### 8.3 序列容量与边界

| 序列 | 键 | `maxValue` | 溢出错误码 |
|---|---|---:|---|
| 一卡通全局序列 | `CAMPUS_CARD_GLOBAL` | 9999 | `STUDENT_CAMPUS_CARD_SEQUENCE_EXHAUSTED` |
| 班级学号序列 | `STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>` | 99 | `STUDENT_CLASS_SEQUENCE_EXHAUSTED` |

事务回滚的分配不视为成功占用，序列值随事务一起回滚；序列更新受**资源锁、同一 Access 事务、`rowVersion` 三重保护**。

### 8.4 编号单元测试样例（来自模块设计文档第 14.1 节）

| 输入 | 期望输出 |
|---|---|
| 本科生、2024 年、全局序号 2478 | `213242478` |
| 硕士生、2024 年、全局序号 1 | `223240001` |
| 博士生、2025 年、全局序号 2 | `233250002` |
| 专业 `090`、2024 年、1 班、班内序号 10 | `09024110` |
| 专业 `09J`、2024 年、1 班、班内序号 10 | `09J24110` |
| 专业代码 / 年份 / 班号 / 序号越界 | 返回对应错误码，**不截断、不循环** |

## 10. 关键设计规则 / 约束

### 10.1 跨模块边界

1. 学籍模块**不依赖选课模块**；选课模块通过 `StudentQueryPort` 调用 `getEnrollmentEligibility` 判定资格，该 Port 是选课模块的**唯一学籍入口**，不返回联系方式或完整档案。
2. 录取时通过用户模块发布的 `UserAccountProvisioningPort.createStudentAccount(transaction, campusCardNumber, password)` 在**同一 `TransactionContext`** 内创建学生账户；用户模块**不得自行提交、回滚或开启嵌套事务**，也不得写 `tblNumberSequence` 或 `tblStudent`。
3. 学籍模块可消费 `UserAccountProvisioningPort` 与 `UserQueryPort`，**不得**依赖用户模块 Repository、课程包，也**不得**读取 `tblEnrollment`。
4. 一卡通号权威值在 `tblUser.loginId`；学号权威值在 `tblStudent.studentNumber`；二者互不替代。学生视图的一卡通号由 `UserQueryPort.findByUserId(...).loginId()` 组装；按一卡通号搜索先 `findByLoginId` 定位 `userId`。
5. 一个用户账户最多绑定一个学生档案，一个学生档案固定绑定一个一卡通登录账户。
6. 注销账户由上层协调器检查学籍状态，学籍模块只提供查询结果。

### 10.2 并发与锁

1. **录取锁顺序固定**，禁止反向获取：
   `NUMBER_SEQUENCE:CAMPUS_CARD_GLOBAL` → `NUMBER_SEQUENCE:STUDENT_NUMBER:<majorCode>:<YY>:<classNumber>` → `LOGIN_ID:<campusCardNumber>`。
2. **手动建档锁顺序固定**：
   `LOGIN_ID:<campusCardNumber>` → `STUDENT_NUMBER:<studentNumber>` → `ID_DOCUMENT:<idDocumentNumber>`。
3. 转班锁顺序：`NUMBER_SEQUENCE:<目标班级序列键>` → `STUDENT:<studentId>`。
4. 联系方式、转班、状态更新、学籍字段修改、资料草稿 / 提交 / 撤回 / 审核的锁键统一为 `STUDENT:<studentId>`，并校验 `rowVersion` / `applicationVersion`。
5. 序列更新使用**资源锁 + 同一 Access 事务 + `rowVersion` 三重保护**；`advance` 采用 `UPDATE ... WHERE sequenceKey=? AND rowVersion=?`，未命中即抛并发异常。
6. 同一资源集不得在不同操作中反向加锁；未公布顺序的资源集按 `resourceType + resourceId` 排序。

### 10.3 事务与一致性

1. 录取（自动 / 手动）的编号分配、账户创建、档案写入、变更审计、请求幂等结果**必须同成同败**。
2. 转班 / 状态更新 / 学籍字段修改与 `tblStudentChange` 在**同一事务**提交，禁止静默覆盖。
3. 资料审核通过与正式档案写入、申请状态更新、`PROFILE_CHANGE` 审计在**同一事务**提交；驳回只改申请状态，不动正式档案。
4. 保存草稿**只更新申请表**，从不修改 `tblStudent`；首次保存记录正式档案 `rowVersion` 为 `baseStudentVersion`。
5. 每名学生最多一条未结束申请（`DRAFT` / `PENDING`）；草稿反复保存覆盖同一条 `DRAFT`；`PENDING` 期间锁定，关闭后才可创建下一份草稿。
6. 批量/顺序失败时，已进入事务的处理**不允许生成新的 `requestId` 重试**。

### 10.4 幂等

1. 所有写命令携带全局唯一 UUID `requestId`，仅以 `requestId` 作为幂等键；`clientInstanceId` 只用于追踪，不参与唯一性判定；`tblRequestDedup` 保存 24 小时。
2. `STUDENT_CREATE` 在编排器内做"事务前 — 取锁后 — 事务内"三重幂等检查，重放返回**完全相同**的 `StudentAdmissionResult` 且不再分配编号。
3. 其余写命令经 `DeduplicatingStudentWriteExecutor`（`RequestDeduplicator.executeOnce`）保证幂等。
4. 相同请求处理中返回 `COMMON_REQUEST_IN_PROGRESS`。

### 10.5 数据与校验

1. 一卡通号、学号、身份证件号均建立唯一约束（`uk_tblStudent_studentNumber`、`uk_tblStudent_idDocumentNumber`、`uk_tblStudent_userId`）。
2. 身份证件号按**规范化值**唯一；手动建档遇重复证件号返回明确错误，不暴露已存在学生的其他资料。
3. 共享校验器 `StudentFieldValidator` 表达全部字段规则，客户端用于即时反馈与焦点定位，服务端对每次命令**再次执行权威校验**，不信任客户端结果；客户端保存前收集全部字段错误，页面底部显示首个可操作中文错误并**不发送网络请求**。
4. 日期统一 `yyyy-MM-dd`；出生、证件签发、入团、入党日期不得晚于当天；`enrollmentDate >= birthDate.plusYears(18)`；证件签发日期不得早于出生日期；入团 / 入党日期不得早于出生日期。
5. 身高 100–280 cm、体重 20–300 kg 的整数；身高 / 体重为空时保留为空。
6. 证件类型与证件号必须同时为空或同时非空；团员 / 党员勾选时对应加入日期必填，取消勾选时该日期必须为空。
7. 邮箱最长 128 字符并匹配常用格式且不允许空白或控制字符；电话最长 32 字符，允许 11 位大陆手机号或带区号与可选分机号的固定电话。
8. 一卡通号、学号、`userId`、初始密码**不得**由管理员在录取页面手工填写；初始密码固定 `12345678`，首次登录必须修改。
9. 政治面貌、民族、婚姻状态、证件类型、户口性质、港澳台侨外、健康状况、血型使用受控下拉；为兼容旧数据，正式档案中的历史非规范值可显示并保留，但用户一旦改动必须选择规范值。
10. 组织异步加载使用**代次号**废弃过时响应，旧响应不得覆盖新树选择；树重新加载后若无法稳定恢复原选中 ID，回到无选择状态。

### 10.6 界面与权限约束

1. 校方权威字段始终只读：一卡通号、学号、学生类别、在籍状态、在校状态、学籍状态、校区、当前年级、院系、专业、班级、培养层次、培养方式、学制、就读学位、就读学历、预计毕业日期、毕业日期、学生来源、学习形式、辅导员姓名及其他学校维护字段。
2. 学生可编辑个人基本信息中的个人属性与联系方式，以及学籍信息中的 `attendanceMode`；页面底部申请状态为"审核中"时禁用两个编辑入口。
3. 学生只能读取和编辑**自己的**资料工作区，客户端请求不得指定其他学生编号；审核命令从会话读取真实审核人，不信任客户端操作者字段。
4. 教师模式只发送 `STUDENT_GET`，不发送 `STUDENT_GET_PROFILE` 与 `STUDENT_GET_CHANGES`，界面不构建"变更记录"标题、表格、空状态或占位区域；教师权限不因拥有某个通用写权限而扩展为完整档案读取。
5. 手动建档命令仅允许 `ADMIN` 角色，**不仅**依赖可能分配给其他角色的通用写权限。
6. 编辑页面必须显示当前 `rowVersion`；并发冲突后提示刷新（"资料已发生变化，请刷新后重新编辑"）。
7. 组织管理四个新增按钮始终可见，仅按树选择启用其一；断网、加载中或写入进行中时四个按钮全部禁用。
8. Swing EDT 不得执行网络等待；页面通过客户端服务取得 `CompletableFuture`，用 `SwingUtilities.invokeLater` 更新控件；提交期间禁用按钮，失败时保留输入。

### 10.7 身份标识不变式

1. 学生更换班级、修正学号或变更学籍状态，都**不得**改变一卡通号、`tblUser.loginId` 或登录方式。
2. 已成功提交的一卡通号与学号永久占用，不得回收或复用；事务回滚的分配不算成功占用。
3. 学生类型建档后不得在普通页面直接修改；确需纠错时由管理员执行专用数据修复流程并保留审计。
4. 已进入 `GRADUATED` / `WITHDRAWN` 的档案保留历史，不做物理删除，且不允许再迁出该状态。

### 10.8 代码与工程边界

```text
vcampus-common/.../student/{command, query, view, StudentStatus, StudentType, StudentFieldValidator}
vcampus-client/.../student/{ui, service}
vcampus-server/.../student/{handler, service, repository, domain, numbering, pdf}
vcampus-server/src/test/.../student
```

- 模块可消费 `UserAccountProvisioningPort` 与 `UserQueryPort`，不得依赖用户 Repository、课程包或读取 `tblEnrollment`。
- 用户模块不得写 `tblNumberSequence` 或 `tblStudent`。
- 数据库结构变更须同步 `vcampus-database/schema/020_student.sql` 与 Access 模板数据库（模板为可执行结构的权威来源，SQL 文件用于评审与初始化说明）。
