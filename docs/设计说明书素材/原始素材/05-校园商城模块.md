## 1. 模块背景

校园商城（Shop）是 vCampus 在既有「学生 / 教师 / 管理员」用户体系之上扩展出的多商户 C/S 电商子系统，用于模拟主流电商平台的完整购物链路：商城首页与分类、关键词搜索、价格区间筛选、销量/价格排序、商品与 SKU、店铺主页、持久化购物车、跨店订单组、店主开店与经营、管理员平台治理，以及微信/支付宝/银行卡三渠道的**模拟**支付。模块遵循项目既有的 Java 21 + Maven 多模块结构，代码边界固定在 `vcampus-common/.../shop`（公共协议 DTO 与枚举）、`vcampus-server/.../shop`（Handler、服务、仓储、领域对象、模拟支付）与 `vcampus-client/.../shop`（Swing 页面、导航、样式与服务端口）三个包内，数据库表集中在 `vcampus-database/schema/050_shop.sql`。商城不接入任何真实金融平台，不保存支付账号、卡号、验证码或密码，不实现退款；支付以服务端事务内的库存预留与幂等状态机保证「不超卖、不重复扣减、不重复累计销量」，即使模拟支付失败或超时也能释放预留并保持库存守恒。买家侧以统一入口（共享外壳的「校园商城」页）进入，客户端使用 Shop 自有的 `CardLayout` 根容器、分层导航器和统一工具栏；服务端不新增用户角色，店主身份由「当前用户是否拥有已审批店铺」动态推导，管理员能力则由既有会话角色校验后再进入 Shop 授权流程。

当前 Demo 数据提供 5 家启用店铺与恰好 100 个通用商品类型（文具 10、图书 30、生活用品 45、药品 5、其他 10，见 2026-08-31 设计；2026-08-30 早期草案为 4 店 100 品，Demo 实现已按 5 店清单落地），固定账号为 `DEMO_BUYER`、`DEMO_OTHER_BUYER`、`DEMO_TEACHER`、`DEMO_ADMIN`（统一密码 `123456`，仅用于 Demo 与测试）。

## 2. 需求分析

### 2.1 角色与能力

| 身份 | 买家能力 | 开店能力 | 店铺管理 | 商城治理 |
| --- | --- | --- | --- | --- |
| 学生 | 可购买其他店铺商品 | 可申请，最多拥有一家店 | 审批通过后管理自己的店 | 无 |
| 教师 | 可购买其他店铺商品 | 可申请，最多拥有一家店 | 审批通过后管理自己的店 | 无 |
| 管理员 | **不可**加入购物车、结算或支付 | 不可申请 | 可管理任意指定店铺的商品 | 审批申请、停用/恢复店铺、全局商品管理 |

- 卖家不是 User 模块中的新角色，而是 Shop 根据「当前用户是否拥有已审批店铺」动态判定的能力。
- 店主仍可购买其他店铺商品，但服务端禁止购买自己店铺的商品（`SHOP_SELF_PURCHASE_FORBIDDEN`）。
- 管理员只允许浏览与管理；买家写操作、开店申请与自购限制全部在服务端校验（`BuyerGuard`），不依赖按钮显隐。
- 每位学生/教师最多一份申请、最多一家店铺；所有权一律取自会话中的用户编号，请求体不接受可替代 `owner`/`buyer` 的参数。
- 申请资格：必须是状态为有效的学生或教师账户（`ShopUser.sellerEligible()`）。

### 2.2 买家需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| B1 | 浏览商品 | 商城首页展示统一搜索、四大分类（文具/图书/生活用品/药品）与「猜你喜欢」；默认按销量降序 |
| B2 | 搜索商品 | 单一关键词输入框；服务端同时匹配商品名称、店铺名称、商品分类、商品描述与 SKU 名称（SKU 用 `EXISTS` 相关子查询，多规格命中只返回一个商品） |
| B3 | 价格筛选与排序 | 可选最低价/最高价（闭区间、`BigDecimal`、非负、下限≤上限），排序 `SALES_DESC`（默认）与 `PRICE_DESC`；主要排序值相同时按商品创建时间从新到旧 |
| B4 | 商品详情 | 通用商品名称、店铺摘要（`ShopSummary`）、分类、描述、封面、销量，以及该商品**可售 SKU** 列表；SKU 下拉框显示规格名称、内部使用 SKU 编号，选择后同步显示价格与可售库存 |
| B5 | 店铺主页 | 展示店铺名称、简介、经营分类、联系方式与分页商品列表；只展示正常营业店铺及其可售商品；商品详情可「进入店铺」，店内商品可再次进入详情 |
| B6 | 购物车 | 服务端持久化，一个用户一个活动购物车；同 SKU 重复加购合并数量；加购/改量前校验数量为 1..可售库存；价格仅作预览 |
| B7 | 结算下单 | 勾选项按 `shopId` 拆成多个子订单并生成一个订单组；事务内重新读取实时价格、状态与库存；任一商品无效、价格未确认或库存不足则整单不创建 |
| B8 | 模拟第三方支付 | 收银台仅展示模拟标识、渠道（微信/支付宝/银行卡）、订单号、金额与成功/失败/取消按钮；不采集真实账号、卡号、密码、验证码 |
| B9 | 订单查看 | 查看本人已支付订单（订单号、店铺、商品与 SKU 明细、数量、成交单价、行金额、订单总额、支付时间、支付状态），明细默认折叠可展开 |

### 2.3 卖家（店主）需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| S1 | 入驻申请 | 结构化材料：店铺名称、主营分类、店铺描述、联系方式、申请说明/经营计划；分类只能从五类中选择；可存草稿、可提交、被拒后可编辑同一份申请重新提交；待审核期间材料只读 |
| S2 | 店铺管理 | 查看店铺概况（名称、分类、描述、联系方式、启用状态、管理员停用原因）；可改店铺名称、描述、联系方式；主营分类审批通过后锁定 |
| S3 | 商品与 SKU 管理 | 商品为「买家看到的通用商品类型」，规格（颜色/尺寸/包装等）写入 SKU 名称；一个商品用一个编辑器维护多个 SKU |
| S4 | 上下架 | 上架前至少存在一个启用、价格有效且可售库存 > 0 的 SKU；库存不得低于已预留数量；「删除商品」统一实现为下架（`INACTIVE`），保留订单历史与审计关联 |
| S5 | 订单处理 | 只读查询本人店铺订单（订单号、买家标识、商品与 SKU、数量、成交金额、支付时间、支付状态），可展开明细 |

### 2.4 管理员需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| A1 | 审核申请 | 审批表格显示申请人、角色、店铺名称、主营分类、联系方式、提交时间与状态，支持状态筛选；「通过」需二次确认并复查申请版本、资格、单店限制与店名唯一性；「拒绝」必须填写原因 |
| A2 | 店铺封禁/恢复 | 查询全部店铺并查看店主、分类、状态与商品数量概况；停用必须填原因，停用后店铺及其商品不出现在买家首页、搜索、店铺页与可购买校验中；恢复后原本上架且可售的商品重新可见 |
| A3 | 商品管理 | 先选择目标店铺，再复用商品管理表格与编辑器；可新增、编辑、上下架商品，可修改任意 SKU 的库存与价格；商品仍归属所选店铺，分类继承该店铺主营分类；每次写操作记录目标店铺、商品、操作者与变更摘要 |

### 2.5 跨功能需求

- 全部写命令幂等（统一走请求去重机制），并采用乐观锁版本号防止丢失更新。
- 界面在 EDT 上更新，异步响应以请求序号隔离，旧响应不得覆盖新筛选/新排序结果。
- Shop 业务日志记录申请提交与审核、店铺资料修改、停用/恢复、商品创建与编辑、上下架、结算、支付状态与订单状态变化；不记录密码或真实支付凭据。
- 会话失效沿用既有退出回调返回登录页。

## 4. 业务流程

### 4.1 买家下单支付流程（含库存预留、支付超时释放、幂等）

1. 客户端发送 `SHOP_GET_CART`，服务端按会话用户编号定位唯一购物车并返回 `CartView`（含 `displayedTotal`，仅供预览）。
2. 用户在结算页勾选行项目并提交 `SHOP_CHECKOUT`，请求体为 `CheckoutCommand{items[], acceptLatestPrice}`。
3. 服务端 `CheckoutService` 先 `requireBuyer`：解析会话、要求账号有效，并拒绝管理员（`SHOP_BUYER_FORBIDDEN`）。随后校验 `items` 非空、`cartItemId` 非空、`displayedUnitPrice` 非负且 `cartItemId` 不重复。
4. 事务内解析每个 `cartItemId` 对应的 `skuId`，并确认这些行都属于自己的购物车；否则返回 `SHOP_CART_EMPTY`。
5. 对所有 `skuId` 去重升序后逐把加锁 `SKU:<skuId>`，最后加锁 `CART:<userId>`，从而固定加锁顺序、避免死锁。
6. 在事务内重新 `JOIN tblCartItem → tblProductSku → tblProduct → tblShop` 读取实时数据，并逐行校验：店铺必须 `ACTIVE`（否则 `SHOP_SUSPENDED`）、商品必须 `ACTIVE`（否则 `SHOP_PRODUCT_INACTIVE`）、SKU 必须启用（否则 `SHOP_SKU_UNAVAILABLE`）、买家不得是店铺所有者（`SHOP_SELF_PURCHASE_FORBIDDEN`）。
7. 价格确认：若 `displayedUnitPrice` 与事务内实时 `unitPrice` 不一致且 `acceptLatestPrice=false`，返回 `SHOP_PRICE_CHANGED` 且**不创建任何订单**；界面重新加载最新价格供用户确认。
8. 库存校验：按 `skuId` 汇总数量，若超过 `stockQuantity - reservedQuantity`，返回 `SHOP_INSUFFICIENT_STOCK`，整单不创建。
9. 按 `shopId` 分组：写入 1 条 `tblOrderGroup`（`totalAmount` = 全部明细金额之和），每个店铺写入 1 条 `tblOrder`（订单号 `"O" + 31 位十六进制`），并为每行写入 `tblOrderItem` 快照（商品名称、规格名称、店铺名称、成交单价、数量、行金额）。
10. 写入 1 条 `tblPayment`（支付单号 `"P" + 31 位十六进制`，`amount` = 订单组总额，状态 `PENDING`）。订单组与支付单一一对应。
11. **库存预留**：对每个 SKU 执行条件更新 `reservedQuantity = reservedQuantity + ? WHERE skuId = ? AND stockQuantity - reservedQuantity >= ?`，影响行数不为 1 即抛 `SHOP_INSUFFICIENT_STOCK`；随后插入 `tblInventoryReservation`（状态 `ACTIVE`，`expiresAt = now + 15 分钟`）。
12. 删除本次已结算的购物车行（删除语句带 `cartId` 归属子查询，影响行数不为 1 即抛 `SHOP_CART_EMPTY`）；以上任一步失败则整个事务回滚。
13. 返回 `CheckoutResult{orderGroupId, paymentId, paymentNumber, totalAmount, expiresAt, orders[]}`，并写业务日志 `event=CHECKOUT`（订单组、行数、子订单数、金额）。
14. 客户端打开 `SimulatedCashierDialog`；用户选择渠道（`WECHAT`/`ALIPAY`/`BANK_CARD`）与模拟结果（成功/失败/取消），发送 `SHOP_SIMULATE_PAYMENT`（`simulatedResult` 不允许为 `STARTED`）。
15. 服务端读取该支付单的预留明细，计算锁集合 `PAYMENT:<paymentId>`、`ORDER_GROUP:<orderGroupId>`、以及排序后的 `SKU:<skuId>`，然后进入事务。该锁集合与超时任务完全一致，保证回调与释放互斥。
16. 校验支付单归属买家与状态：已是 `SUCCEEDED` → `PAYMENT_ALREADY_COMPLETED`；非 `PENDING`（`CANCELLED`/`EXPIRED`）→ `PAYMENT_NOT_PENDING`。
17. 金额不变量校验：`tblPayment.amount == tblOrderGroup.totalAmount == SUM(tblOrder.orderAmount)`，否则 `PAYMENT_AMOUNT_MISMATCH`。
18. 追加一条 `tblPaymentAttempt`（渠道、结果、`createdAt`/`completedAt`），失败尝试也留痕。
19. 按模拟结果分支处理：
    - `FAILED`：**只追加本次尝试**，支付单保持 `PENDING`，预留不变；用户可在预留期内重试，重试不重复预留。
    - `CANCELLED`：释放预留（`reservedQuantity -= qty`，条件更新防负），预留置 `RELEASED`，支付单置 `CANCELLED`，订单组与全部子订单置 `CANCELLED`。
    - `SUCCEEDED`：逐条校验预留仍为 `ACTIVE` 且 `now < expiresAt`（否则 `PAYMENT_NOT_PENDING`）；扣减实际库存与预留（`stockQuantity -= qty AND reservedQuantity -= qty`，条件更新失败即 `SHOP_INSUFFICIENT_STOCK`）；预留置 `CONSUMED`；按订单组聚合各 `productId` 的成交数量并累加 `tblProduct.salesCount`；支付单置 `SUCCEEDED` 并写 `successfulChannel` 与 `completedAt`；订单组与全部子订单置 `PAID` 并写 `paidAt`。
20. **幂等性**：所有写命令先经 `RequestDeduplicator.executeOnce(message, userId, connectionId, ...)`；支付终态更新使用 `UPDATE tblPayment ... WHERE paymentId = ? AND paymentStatus = 'PENDING'`，影响行数必须为 1，因此重复成功回调只生效一次，库存只扣一次、销量只累计一次。状态校验与销量累加处于同一事务。
21. **超时释放**：`ReservationExpiryJob.expirePendingPayments()` 扫描「支付单 `PENDING` 且存在 `ACTIVE` 预留 `expiresAt <= now`」的候选支付单，逐单按与回调相同的锁集合串行处理；在锁内重新确认支付单仍为 `PENDING` 且确有已过期预留后，释放预留、预留置 `RELEASED`、支付单置 `EXPIRED`、订单组与子订单置 `CANCELLED`，返回处理计数。过期任务与成功回调并发时最终状态唯一、库存守恒。
22. 不创建结算路径的失败或仍待处理的支付尝试不会产生支付完成态，用户停留在可重试的结算流程中。

### 4.2 卖家入驻审核流程

1. 学生/教师在「我的」看到「我要开店」（无申请）/「继续填写」（草稿）/「查看审核状态」（待审核）/「修改并重新提交」（已拒绝）/「管理我的店铺」（已通过）五种状态化入口。
2. 保存草稿：`SHOP_SELLER_SAVE_APPLICATION`（`SaveSellerDraftCommand`）。
   1. `SellerApplicationService` 要求会话用户 `sellerEligible()`（有效学生或教师），否则安全异常（协议层映射为 `COMMON_VALIDATION_FAILED`）。
   2. 校验店名、描述、分类、联系方式必填；分类必须属于「文具/图书/生活用品/药品/其他」（否则 `SHOP_CATEGORY_INVALID`）；长度限制店名 50、联系方式 50、经营计划 500。
   3. 加锁 `USER:<applicantUserId>`。
   4. 新建（`applicationId == null`）时要求 `expectedVersion == 0`，且该用户既无既有申请也无店铺，否则 `SHOP_SELLER_APPLICATION_EXISTS`；写入状态 `DRAFT`。
   5. 编辑既有申请时，仅当状态为 `DRAFT` 或 `REJECTED` 且 `rowVersion` 与 `expectedVersion` 一致才允许，否则 `SHOP_SELLER_APPLICATION_STATUS_INVALID`；仅所有者可改，否则 `SHOP_NOT_OWNER`。
3. 提交审核：`SHOP_SELLER_SUBMIT_APPLICATION`（`SubmitSellerApplicationCommand{applicationId, expectedVersion}`）。
   1. 加锁 `USER:<uid>`、`SELLER_APPLICATION:<applicationId>`、`SHOP_NAME:<规范化店名>`。
   2. 要求状态为 `DRAFT`、版本一致、资料与申请说明齐全。
   3. 店名规范化（`strip()` 后 `toLowerCase(Locale.ROOT)`）在 `tblShop.normalizedShopName` 上已存在 → `SHOP_NAME_EXISTS`。
   4. 状态置 `PENDING` 并写 `submittedAt`；此后材料只读。
4. 管理员查看队列：`SHOP_ADMIN_SEARCH_APPLICATIONS`（`SellerApplicationQuery{applicantUserId, mode, pageNumber, pageSize}`）；`mode = PENDING` 按 `submittedAt DESC, applicationId` 排序，`mode = PROCESSED` 只取 `APPROVED/REJECTED` 并按 `reviewedAt DESC, applicationId` 排序。
5. 审批：`SHOP_ADMIN_REVIEW_APPLICATION`（`ReviewSellerApplicationCommand{applicationId, decision, reason, expectedVersion}`）。
   1. 加锁 `SELLER_APPLICATION:<id>`、`USER:<申请人>`、`SHOP_NAME:<规范化店名>`。
   2. 事务内重新读取申请，要求仍为 `PENDING` 且版本一致，否则 `SHOP_CONCURRENT_MODIFICATION`（界面需重新加载最新记录）。
   3. **拒绝**：必须填写原因，置 `REJECTED` + `reviewReason` + `reviewerUserId` + `reviewedAt`，写业务日志 `STATE_CHANGE`；申请人可编辑同一份申请再次提交。
   4. **通过**：再次确认申请人尚无店铺（否则 `SHOP_SELLER_APPLICATION_EXISTS`）、规范化店名未被占用（否则 `SHOP_NAME_EXISTS`）；在同一事务中插入状态为 `ACTIVE` 的 `tblShop` 并把申请置 `APPROVED`——「审批通过」与「创建并启用店铺」原子完成。
6. 店铺状态治理：`SHOP_ADMIN_SUSPEND_SHOP`（必须填原因，`ACTIVE → SUSPENDED`，写 `suspensionReason`/`suspendedByUserId`/`suspendedAt`）；`SHOP_ADMIN_RESUME_SHOP`（`SUSPENDED → ACTIVE`）。两者都在 `SHOP:<shopId>` 锁内以「预期状态 + `rowVersion`」条件更新，冲突返回 `SHOP_CONCURRENT_MODIFICATION`，并写业务日志。
7. 店铺资料修改：店主 `SHOP_SELLER_UPDATE_SHOP` 加锁 `USER:<uid>` 与 `SHOP_NAME:<新规范化名>`，检查新名未被其他店铺占用，主营分类保持已审批值不变。

### 4.3 发货 / 完成流程

**设计约定的状态机**（见 2026-08-24 设计第 8 节，`OrderStatus` 枚举与 `tblOrder` 的 `shippedAt`/`completedAt` 字段已为其预留）：

1. 支付成功后，订单组与组内所有子订单由 `PENDING_PAYMENT` 同时变为 `PAID`。
2. 店主在自己店铺的订单中把 `PAID` 推进为 `PREPARING`（备货）。
3. 店主发货，订单变为 `SHIPPED`，记录 `shippedAt`。
4. 买家确认收货，订单变为 `COMPLETED`，记录 `completedAt`；订单组在全部子订单完成后变为 `COMPLETED`。
5. 买家只可取消待支付订单组（`PENDING_PAYMENT → CANCELLED`）；超出课程范围的退款请求以客服提示结束，不改变支付状态。
6. 商品下架不影响历史订单；订单明细使用下单时的名称/规格/价格/店铺名称快照，不依赖商品当前值展示历史。

**实现现状（重要）**：截至当前代码，服务端**没有**注册任何卖家订单状态写命令或买家确认收货命令（`SellerOrderService` 只有 `getOwnedOrders` 只读查询，`BuyerShopHandlers` 亦无取消订单/确认收货/RPC 注册）。因此当前实际可达的订单状态只有：

- `PENDING_PAYMENT → PAID`（模拟支付成功，支付服务在同一事务内更新订单组与全部子订单）；
- `PENDING_PAYMENT → CANCELLED`（用户明确取消或预留超时释放）。

`PREPARING`、`SHIPPED`、`COMPLETED` 目前仅作为枚举值与数据库约束预留（2026-08-31 设计明确：本阶段不提供发货、退款或人工修改订单状态能力，卖家订单为只读）。撰写正式说明书时，建议将第 4.3 节前半部分列为「设计目标/后续迭代」，并如实说明当前为只读履约视图。

## 8. 状态机

### 8.1 店主申请（`SellerApplicationStatus`）

```text
（无申请） → DRAFT → PENDING → APPROVED
                        └────→ REJECTED → （编辑）→ PENDING
```

| 当前状态 | 事件 | 目标状态 | 说明 |
| --- | --- | --- | --- |
| 无申请 | 保存草稿 | `DRAFT` | 新建申请；要求 `expectedVersion = 0` 且无既有申请与店铺 |
| `DRAFT` | 保存草稿 | `DRAFT` | 仅所有者、且 `rowVersion` 匹配 |
| `DRAFT` | 提交审核 | `PENDING` | 写 `submittedAt`；复查资料齐全与规范化店名唯一 |
| `PENDING` | 管理员通过 | `APPROVED` | 同一事务插入 `ACTIVE` 店铺；要求申请人尚无店铺且店名未被占用 |
| `PENDING` | 管理员拒绝 | `REJECTED` | 必填 `reviewReason`，写 `reviewerUserId`、`reviewedAt` |
| `REJECTED` | 保存草稿/再提交 | `DRAFT` / `PENDING` | 编辑同一份申请后重新提交 |

版本保护：保存、提交、审批都要求 `rowVersion == expectedVersion`，不匹配返回 `SHOP_SELLER_APPLICATION_STATUS_INVALID`（保存/提交）或 `SHOP_CONCURRENT_MODIFICATION`（审批）。

### 8.2 店铺（`ShopStatus`）

```text
ACTIVE ⇄ SUSPENDED
```

- `ACTIVE → SUSPENDED`：管理员 `SHOP_ADMIN_SUSPEND_SHOP`，必填原因，写 `suspensionReason`/`suspendedByUserId`/`suspendedAt`。
- `SUSPENDED → ACTIVE`：管理员 `SHOP_ADMIN_RESUME_SHOP`，清空停用信息。
- 店铺停用期间：不出现在买家首页/搜索/店铺页/可购买校验中；店主仍可查看资料、商品和订单，但不能创建、修改或上下架商品（`requireOwnedActiveShop` 抛 `SHOP_SUSPENDED`）。

### 8.3 商品（`ProductStatus`）

```text
DRAFT → INACTIVE → ACTIVE
          ↑           │
          └───────────┘
```

- 新建商品初始为 `DRAFT`。
- 允许的店主状态迁移：`DRAFT → INACTIVE`、`INACTIVE → ACTIVE`、`ACTIVE → INACTIVE`；其他迁移返回 `SHOP_STATUS_INVALID`。
- 约束：`DRAFT → INACTIVE` 要求至少一个启用 SKU；`→ ACTIVE` 要求至少一个「启用且 `stockQuantity - reservedQuantity > 0`」的 SKU，否则 `SHOP_SKU_UNAVAILABLE`。
- 「删除商品」统一实现为 `INACTIVE`（软下架），保留订单历史与审计关联；有预留的 SKU 不得移除。
- 管理员可在所选店铺内直接设置目标状态（`AdminProductService.changeStatus`），上架同样要求可售 SKU。

### 8.4 订单组（`tblOrderGroup.groupStatus`）

```text
PENDING_PAYMENT → PAID
PENDING_PAYMENT → CANCELLED
```

- 结算创建时为 `PENDING_PAYMENT`。
- 支付成功：与组内全部子订单一起变为 `PAID`（同一事务）。
- 用户明确取消支付或预留超时：变为 `CANCELLED`。
- `COMPLETED` 取值存在于约束与枚举中，但当前无写入路径（见 4.3 实现现状）。

### 8.5 子订单（`OrderStatus`）

```text
PENDING_PAYMENT → PAID → PREPARING → SHIPPED → COMPLETED
PENDING_PAYMENT → CANCELLED
```

- 当前**实际可达**：`PENDING_PAYMENT → PAID`、`PENDING_PAYMENT → CANCELLED`。
- `PREPARING`、`SHIPPED`、`COMPLETED` 为设计目标，枚举、数据库约束与 `shippedAt`/`completedAt` 字段已预留，但无对应写命令。
- 订单明细以快照展示，商品下架/店铺停用不影响历史订单。

### 8.6 支付单（`PaymentStatus`）

```text
PENDING → SUCCEEDED
PENDING → CANCELLED
PENDING → EXPIRED
```

- `SUCCEEDED`：模拟支付成功，扣库存与预留、销量累加、渠道写入 `successfulChannel`。
- `CANCELLED`：用户明确取消，释放预留。
- `EXPIRED`：`ReservationExpiryJob` 在预留超时后释放预留并终结支付单。
- 终态不可再次迁移：已成功返回 `PAYMENT_ALREADY_COMPLETED`，其他终态返回 `PAYMENT_NOT_PENDING`。

### 8.7 支付尝试（`PaymentAttemptStatus`）

```text
STARTED → SUCCEEDED | FAILED | CANCELLED
```

- 每次 `SHOP_SIMULATE_PAYMENT` 追加一条尝试记录，请求只接受终态（`STARTED` 被拒绝）。
- `FAILED` 不影响支付单状态，支付单仍为 `PENDING` 并允许在预留期内重试。

### 8.8 库存预留（`tblInventoryReservation.reservationStatus`）

```text
ACTIVE → CONSUMED   （支付成功）
ACTIVE → RELEASED   （用户取消或超时过期）
```

- `ACTIVE`：`reservedQuantity` 已占用，`expiresAt` 为下单后 15 分钟。
- `CONSUMED`：支付成功，预留转为实际扣减。
- `RELEASED`：释放回可售库存，写 `releasedAt`。
- 释放与消费都使用 `WHERE ... AND reservationStatus = 'ACTIVE'` 的条件更新，保证只执行一次。

## 10. 关键设计规则与约束

### 10.1 权限与所有权

1. 卖家不是新角色，由「拥有已审批店铺」动态推导；学生/教师最多一份申请、一家店铺（`tblSellerApplication.applicantUserId` 唯一索引 + `tblShop` 所有者唯一约束双重保证）。
2. 管理员不能加购、结算或支付；店主不能购买自己店铺商品；两类限制都在服务端（`BuyerGuard`）执行，不依赖界面按钮显隐。
3. 所有权一律取自会话：申请、店铺、商品、订单的读写都不接受请求体中的 owner/buyer 参数。
4. 管理员校验基于当前会话：先读取既有 `UserView` 的管理员角色 → `ShopUserKind.ADMINISTRATOR`，再调用管理服务；Shop 不修改 User 模块。

### 10.2 商品、SKU 与价格

5. 一个商品是买家看到的通用商品类型，颜色/尺寸/包装等规格写入 SKU 名称，不拆成多个商品；同店铺内规范化商品名唯一，重名时提示店主打开已有商品追加 SKU。
6. 商品至少有一个 SKU 才能上架；上架要求至少一个「启用且可售库存 > 0」的 SKU。
7. 列表、筛选、排序统一使用「最低可售 SKU 价格」（`MIN(k.unitPrice)`），界面显示为「¥xx 起」；无可用 SKU 的商品不进入列表；销量按商品全部 SKU 汇总。
8. 价格使用 `BigDecimal`（库中 `DECIMAL(12,2)`），价格区间为闭区间；任一边界为空表示该方向不限；非法区间直接报 `SHOP_PRICE_FILTER_INVALID` 且不执行查询。
9. 排序：`SALES_DESC` 默认按 `salesCount DESC`，`PRICE_DESC` 按最低可售价 `DESC`；并列时按 `createdAt DESC`，再以 `productId` 兜底保证稳定。
10. 列表价格只用于展示与筛选，结算必须在事务内重新读取实时价格与库存。
11. 商品分类继承店铺主营分类，店主不能单独修改；店铺主营分类审批通过后锁定。
12. 封面 URL 只接受合法 `https://`（长度 ≤ 2048、有 host、不含凭据）或与分类匹配的内置预设（`builtin://`）；未填写或加载失败时使用分类默认图；Common 只传 URL 字符串，图片下载完全在客户端。
13. 「删除商品」统一为软下架（`INACTIVE`），保留订单历史与审计关联。

### 10.3 购物车、结算与订单

14. 购物车持久化在服务端，一个用户一个活动购物车；同 SKU 重复加购合并数量；更新锁定 `CART:<userId>`。
15. 结算按 `skuId` 升序加锁所有相关 SKU，再锁购物车，避免死锁；事务内重新读取价格、状态与可售库存。
16. 任一商品无效、价格未确认或库存不足时，整个结算不创建任何订单（全有或全无）。
17. 勾选项按 `shopId` 拆成多个子订单并创建一个订单组；一个支付单关联一个订单组；支付成功后组内所有子订单同时变为 `PAID`。
18. 订单明细保存下单时的商品名称、规格名称、店铺名称、成交单价与数量快照，历史展示不依赖商品当前值。
19. 买家订单查询通过 `tblOrderGroup.buyerUserId` 限定本人、通过订单与支付状态限定 `PAID`，按 `paidAt DESC, orderId` 排序；请求体不接受买家编号。
20. 卖家订单查询按店主店铺隔离，只读，含明细快照。

### 10.4 库存、支付与并发

21. 结算成功后预留库存 15 分钟；可售库存定义为 `stockQuantity - reservedQuantity`。
22. 预留、扣减、释放均使用带条件的 `UPDATE`（库存充足/预留充足），以行数校验成败，避免超卖。
23. 支付锁定 `PAYMENT:<paymentId>`、`ORDER_GROUP:<orderGroupId>` 与排序后的 `SKU:<skuId>`；超时任务使用完全相同的锁集合，保证回调与释放互斥。
24. 一次支付尝试只产生 `SUCCEEDED`、`FAILED` 或 `CANCELLED`；失败只追加 `tblPaymentAttempt`，不释放预留，支付单在预留期内保持 `PENDING` 并允许重试。
25. 支付终态更新带 `WHERE paymentStatus = 'PENDING'`，状态校验与销量累加在同一事务内，重复成功回调只生效一次（库存只扣一次、`salesCount` 只累加一次）。
26. 明确取消或超时只释放预留、不扣实际库存；释放与消费都只作用于 `ACTIVE` 预留，保证只释放一次。
27. 所有写命令幂等：客户端请求先经 `RequestDeduplicator.executeOnce(requestId, userId, connectionId)`。
28. 序列化写操作使用乐观锁 `rowVersion`：申请、店铺、商品、SKU、购物车行均带版本号，过期版本返回明确冲突错误，界面重新加载最新记录。
29. 店铺名称与商品名称的「先查后写」都在 Shop 事务内、配合规范化名称锁（`SHOP_NAME:<normalized>`）与唯一索引，避免并发下产生重复名称。
30. 数据库约束兜底：金额/价格/数量非负、`reservedQuantity <= stockQuantity`、订单金额 = 明细之和、支付金额 = 订单组总额。

### 10.5 界面、导航与异步

31. 商城只有一个入口：`ShopUiInstaller` 在 EDT 上按稳定组件名 `page.shop`、`navigation.shop` 安装；找不到唯一入口或唯一占位页立即抛出可诊断异常，不静默追加重复入口。
32. `ShopNavigator` 是唯一导航所有者；导航状态由固定语义槽组成（内容路径最多 3 个节点、覆盖路径最多 3 个节点、至多 1 个支付完成态），同层替换不累积深度，首页为不可淘汰根层，不使用 `MAX_HISTORY`。
33. `Product` 路由归属由进入上下文决定：从内容页进入属于详情层，从购物车/确认订单进入属于临时预览层，从而同时满足「购物车 → 商品 → 返回购物车」与「列表 → 商品 → 返回列表」。
34. 支付完成态清除购物车、结算与临时预览，任何返回路径都不得重新进入已完成的结算页。
35. 工具栏在「我的」左侧固定显示「返回首页」，与左侧「校园商城」入口调用同一 `resetToDefaultHome()` 语义（默认首页、第 1 页、顶部、清空导航层），但遵守未保存内容的离开保护（保存/丢弃/取消）。
36. 页面只提交 `productId`/`shopId` 等导航意图，不直接创建或持有目标页面；`ProductSummary` 不内嵌完整 `ShopDetail`，`ProductDetail` 只含一个 `ShopSummary`，避免 Socket DTO 循环引用与重复传输。
37. 离开首页/搜索/店铺前捕获查询、页码与滚动位置并写回对应语义槽，返回时先恢复表单与查询、异步结果渲染后再恢复滚动条；同层替换会丢弃被替换目标的视图状态。
38. 异步响应以请求序号隔离（`LatestRequest`），较旧响应不得覆盖新筛选或新排序结果；所有 Swing 状态更新在 EDT 上进行，图片加载在后台执行并使用有界缓存与默认图回退。
39. 搜索页首次成功搜索前只显示关键词与「搜索」按钮，成功后展开分类/价格/排序并保持；排序一经选择立即重新查询并重置为第 1 页。
40. 商品详情加购前先校验数量编辑器文本（整数且 1..当前 SKU 可售库存），无效或超库存时不发送请求、不改变购物车数量；服务端仍是最终库存与权限边界。

### 10.6 日志与隐私

41. 记录申请提交与审核、店铺资料修改、停用/恢复、商品创建与编辑、上下架、价格与库存变化、结算、支付状态与订单状态变化；日志包含操作者、目标对象、结果与必要原因。
42. 命令级日志记录 `command`、`requestId`、`userId`、`code`、`durationMs`；结算与支付额外记录订单组、行数、金额、渠道与结果。
43. 不记录真实支付账号、卡号、验证码或密码；模拟支付只记录渠道、支付单、金额和结果。收银台界面同样不采集任何真实凭据。
44. 会话失效沿用既有退出回调返回登录页，Shop 不自行实现登录流程。

### 10.7 模块边界

45. 代码边界：`common/shop/{command,query,view,enum}`、`client/shop/{buyer,seller,admin,service,...}`、`server/shop/{handler,service,repository,domain,payment,port,...}`，以及 `server/src/test/.../shop` 与对应客户端测试。
46. 商城模块只消费 `AuthorizationPort` 与用户身份，不修改用户角色；模拟支付位于 `shop.payment` 并通过接口/锁协议与订单服务隔离，不嵌入订单服务。
47. 每个实现任务只修改商城包、商城表与已批准的公共 DTO；公共协议基础结构及其他模块 Repository 禁止修改。
48. 本轮分层导航整改把改动限制在 `client/shop` 及对应 Shop 测试与说明文档，不需要数据库升级，也不修改公共网络接口。
